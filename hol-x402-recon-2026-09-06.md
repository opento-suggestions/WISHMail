# HOL Registry Broker + x402 — read-only reconnaissance for WISHMail

**Date:** 2026-09-06
**Scope:** Target A = the HOL Registry and its "registry broker" (Hashgraph Online / hol.org). Target B = x402 (the purchase leg).
**Mode:** Read-only. Every repository was cloned with `--filter=blob:none` and never modified. Every HTTP request was an idempotent GET. No registration, no purchase, no write, no Hedera transaction, no key material touched.

**Method note (digests).** Every `sha256` in `hol-x402.pins.draft.json` is computed over **raw git blob bytes** — `git cat-file blob <blobSha> | sha256sum` — never over the working-tree checkout. This machine runs `core.autocrlf=true`, so a checked-out file's digest differs from its object-store digest. To re-verify, use `git cat-file`, not `sha256sum` on the file.

**Mainnet note.** Some evidence below comes from Hedera **mainnet** mirror-node reads. These are public HTTP GETs against `mainnet-public.mirrornode.hedera.com`. No Hedera `Client` was opened and no key was loaded, so the `assertTestnet()` kill-switch in `ontologic-hello-world/src/config.ts` was never in play. The mainnet data is reported because that is where the `hol` registry's largest anchor set lives; it is not a recommendation to point anything at mainnet.

## CONTRADICTIONS

Ordered by how much they change the design, not by section.

### C-1 — There is no "HOL Registry." There is a cross-registry broker, and `hol` is 33 of its 249,167 agents.

The brief treats "the HOL Registry" as the thing and `registry=hol` as its UAID namespace. What exists is a **broker that aggregates sixteen third-party registries**, of which `hol` is the fourth-smallest.

Three of the sixteen are Hedera-native and mutually distinct: `hashgraph-online` (359), `hol` (33), `openconvai` (2). The `nanda` profile from the previous recon is *also* reachable through this same broker (2,635 agents) — meaning the broker is a competing implementation of the `nanda` profile WISHMail is separately specifying.

### C-3 — Half the answer is genuinely `math`, and I verified it end to end. But the broker's schema hides that half and documents a field it does not return.

The verifiable half is real. Working from one live `hol` record I reconstructed the entire registry-to-profile chain from a mirror node with **no broker in the loop**, and every hash checked out. Full detail in §3; the three verifications:

| Claim | Verification | Result |
| --- | --- | --- |
| Broker's `metadata.registryEntry.payloadHash` | `sha256(raw HCS message bytes)` on topic `0.0.10080724` seq 6 | **MATCH** `d9407a4a...f7e2` |
| HCS-1 profile topic memo hash | `sha256(brotli-decompressed JSON)` of topic `0.0.10081296` | **MATCH** `087ed2e6...590b` |

The contradiction is what surrounds it. The published OpenAPI declares (FETCHED `GET https://hol.org/registry/api/v1/openapi.json`, 200, 261,092 bytes, `sha256 6a38959c...8eab`, `info.version 0.1.0`):

```json
  { "properties": { "profile": { "type": "object",
    "description": "HCS-11 profile document recorded for the agent.",
    "additionalProperties": true } } } ] }
```

but `GET /api/v1/resolve/{uaid}` and `GET /api/v1/agents/{uaid}` both returned 200 with **no `profile` key at all**, verified live against `uaid:aid:4ZFPnAVF...` on 2026-09-06. The SDK's own schema agrees with the live behaviour and not with the OpenAPI — `src/services/registry-broker/schemas.ts:392-394`:


The one part of the broker's answer a Verifier can check is entirely undocumented; the documented part does not exist.

### C-4 — Registering through the broker means an ORG-held key signs your registration. This collides head-on with W-2.

WISHMail invariant W-2 is "No ORG-held key ever signs a payer's testimony." Every `hol` registration on Hedera mainnet was submitted and paid by **one account**.

FETCHED `GET https://mainnet-public.mirrornode.hedera.com/api/v1/topics/0.0.10080724/messages?limit=100&order=desc` — 23 messages, **1 distinct `payer_account_id`: `0.0.10022745`**, spanning 2025-11-04T04:12:50Z to 2025-11-10T02:35:01Z. The topic carries `submit_key` (ED25519, SET) and `admin_key` (ED25519), so no third party could have written to it anyway.

Testnet is the same shape: of the 13 `hol` agents anchored on `0.0.6913983`, **every** `transactionId` begins `0.0.2659396@`.

The broker's own record refutes its own payer field. Across the 33 `hol` agents it reports four distinct `metadata.payerAccountId` values (`0.0.9297067` ×15, `0.0.10022745` ×4, `0.0.2656337` ×4, `0.0.2659396` ×4) — but for all 15 records claiming `0.0.9297067`, the `transactionId` the broker itself publishes in the same object begins `0.0.10022745@`. Whatever `payerAccountId` denotes, it is not the account that signed the consensus message.

### C-5 — `registry=hol` is not a namespace the ledger enforces. It is a string inside a hash, and one topic carries two of them.

The brief speaks of "UAID issuance under HCS-14 `registry=hol`" as though `hol` selects an issuer. It does not. `registry` is an ordinary field in the canonical object that gets hashed (`canonical.ts:50-57`), and separately a routing parameter appended after the hash (`did.ts:24-33`). Nothing binds it to a topic, an operator, or a key.

Empirically, topic `0.0.10080724` carries **20 messages with `registry=hol` and 3 with `registry=hashgraph-online`**, interleaved, all signed by the same account.

HCS-14 itself says so, at `hiero-consensus-specifications@7046156` `docs/standards/hcs-14/index.md:185`:

> `registry` = Registry namespace (e.g., "nanda", "hol", "olas")

— an example list, not a registry of registries. And at `:846`:

> Routing/source trust: consumers decide which registries or namespaces they rely on for discovery (e.g., `registry=hol`, `registry=olas`). HCS‑14 carries routing hints but **does not endorse any registry**.

### C-7 — Hedera x402 exists, is live, and is testnet-only. The x402 spec's own index has not been told.

This is the good news and it is unambiguous — see §8. `specs/schemes/exact/scheme_exact_hedera.md` is a complete 169-line scheme; Hedera USDC is a registered default asset on both networks; the default facilitator serves `hedera:testnet` today with a published fee-payer account.

But the parent scheme document does not list it. `specs/schemes/exact/scheme_exact.md:92`:

> Network-specific rules are in per-network documents: `scheme_exact_svm.md` (Solana), `scheme_exact_stellar.md` (Stellar), `scheme_exact_evm.md` (EVM), `scheme_exact_sui.md` (SUI), `scheme_exact_ton.md` (TON), `scheme_exact_starknet.md` (Starknet).

> Both EVM and Solana networks are supported by the reference implementations, e.g.:

followed by a six-entry list with no Hedera, despite `typescript/packages/mechanisms/hedera/` being a shipped package with its own npm publish workflow.

### C-9 — The mainnet `hol` registry topic declares HCS-2 in its memo and then breaks HCS-2's only MUST about message shape.

Topic `0.0.10080724` memo is `hcs-2:0:86400`. Per `hcs-2.md:209-215` that means: protocol `hcs-2`, indexed (`0` = "all messages should be read", `:219`), TTL 86400. But every one of its 23 messages carries `"p":"hcs-10"`.

`hcs-2.md:306`:

> - **`p` (Protocol)**: Must be a string matching `hcs-2`. This validates that the entry adheres to the current standard.

A conformant HCS-2 reader must reject all 23 entries. The nested profile-pointer topic `0.0.10081297` (memo `hcs-2:1:86400`) *is* conformant — its message is `{"p":"hcs-2","op":"register","t_id":"0.0.10081296"}`. So the same deployment gets it right one level down and wrong one level up.

Worse for a portable reader: the **testnet** topic for the same logical registry uses a different memo grammar entirely. `0.0.6913983` memo is `hcs-10:0:300:3` — the HCS-10 registry form from `hcs-10/index.md:179` (`hcs-10:0:{ttl}:3:[metadataTopicId]`), TTL 300. One registry, two incompatible memo declarations across two networks, both carrying identical message shapes.

### C-10 — Replay protection on Hedera x402 is a SHOULD sitting under a MUST.

`scheme_exact.md:41` (signed-payment family, "Each method MUST satisfy"):

> - **Replay**: the network's own primitive is authoritative. A consumed primitive MUST produce a settlement failure, never a success.

`scheme_exact_hedera.md:155-156`:

> - The transaction MUST:
>   - Not have been previously submitted/observed (implementations **SHOULD** perform idempotency / replay checks where possible).

Hedera's transaction-ID duplicate detection almost certainly *is* the authoritative primitive that satisfies `:41` — but the Hedera document never says so, never names the primitive, and downgrades to SHOULD. There is also no Hedera analogue of the EVM `nonce`/`validAfter`/`validBefore` triple the brief assumes: those fields exist only in the EIP-3009 authorization object, and the entire replay section of the core spec (`x402-specification-v2.md:612-619`) is written in EIP-3009 terms.

**Do answers carry a signature, content address, or consensus reference?**

- **Signature: no.** Across all 267 schemas in the OpenAPI, `signature` and `publicKey` appear only in `ProgrammableSecretsKeyRequest`, `AgentFeedbackSubmissionResponse`, `SessionEncryptionPeerSummary`, `EncryptionHandshakeSubmission`, `RegisterEncryptionKeyRequest/Response`, `AdapterRegistryAdapter`, `SubmitAdapterRegistryAdapterRequest` — chat encryption, feedback and adapter submission. **Never on a search hit, an agent record, or a resolve response.** No path anywhere mentions `signature`.
- **Content address: yes, but undocumented.** `metadata.registryEntry.payloadHash` is a real sha256 over the anchoring HCS message (verified — §A-3).
- **Consensus reference: yes, but undocumented.** `metadata.registryEntry.{registryTopicId, transactionId, consensusTimestamp, topicSequenceNumber, network, profileReference, tId}`.

Both live inside the untyped `metadata` bag; neither string appears in the OpenAPI.

### A-3. CONSENSUS OR HTTP — which half can ever be `math`

**Read from Hedera and independently re-obtainable (`math`).** Everything under `metadata.registryEntry` and `metadata.profileRegistry`. I proved this by walking the whole chain from a mirror node with no broker, starting from nothing but a UAID.

Take the live record for `uaid:aid:4ZFPnAVFTnZpPFqzRm7h1bvR9AWLYFEvZmqVEqHqA9UtBp5L5G2gbVodjpCsMV7xR9;uid=sdk-erc8004-demo-mhkld2e7;registry=hol;proto=a2a;nativeId=https://integrated-enough-moving-culture.trycloudflare.com/.well-known/agent.json`. The broker claims:

```json
"registryEntry": { "registryTopicId":"0.0.10080724",
  "transactionId":"0.0.10022745@1762262201.670410790",
  "consensusTimestamp":"1762262209.809943000",
  "payloadHash":"d9407a4a957464849b97f20e3b887f8391e58c0c4a180dc2298bbc23d6ddf7e2",
  "feeCredits":0, "topicSequenceNumber":6, "network":"mainnet",
  "profileReference":"hcs-11:hcs://1/0.0.10081296", "tId":"0.0.10081297",
  "profileSizeBytes":732 }
```

**Step 1.** `GET /api/v1/topics/0.0.10080724/messages/6` on the mainnet mirror node returns `consensus_timestamp 1762262209.809943000`, `payer_account_id 0.0.10022745` — both matching — and message bytes decoding to:

```json
{"p":"hcs-10","op":"register","uaid":"uaid:aid:4ZFPnAVF…","t_id":"0.0.10081297"}
```

`sha256` of the raw message bytes = `d9407a4a957464849b97f20e3b887f8391e58c0c4a180dc2298bbc23d6ddf7e2` — **identical to the broker's `payloadHash`.** So `payloadHash` is sha256 over the HCS message, and it is checkable by anyone.

**Step 2.** Topic `0.0.10081297`, memo `hcs-2:1:86400`, one message: `{"p":"hcs-2","op":"register","t_id":"0.0.10081296"}`.

**Step 3.** Topic `0.0.10081296`, memo `087ed2e66961ee7ee81ecda1e716f43089ebc1ac3a9d234ff5a5367e2117590b:brotli:base64`. That is the HCS-1 file-topic grammar, `hcs-1.md:56-60`:

> `[hash]:[algo]:[encoding]`
> - [hash] is the SHA-256 hash of the file being uploaded **before any compression**
> - [algo] is the compression algorithm being used, for example, `zstd` or `brotli`

Its message is an HCS-1 chunk `{"o":0,"c":"data:application/json;base64,…"}`. Brotli-decompressing the payload yields the HCS-11 profile, and `sha256` of that decompressed JSON = `087ed2e6…590b` — **identical to the memo hash**, exactly as `:58` specifies. (Two minor observations: the identical chunk appears at both seq 1 and seq 2; and `hcs-1.md:85` says "The entire file should be compressed using **zstd**" while `:71` recommends brotli for JSON and this deployment uses brotli — a reader must honour the memo's `[algo]` field, not the prose.)

The recovered profile:

```json
{"version":"1.0","type":1,"display_name":"sdk-erc8004-demo-mhkld2e7",
```

**The split, stated plainly.** *Existence and integrity* of a registration are `math`: anyone can confirm that this UAID was registered at this consensus timestamp with this exact payload, and can recover the byte-exact HCS-11 profile and check it against an on-chain hash. *Everything the broker says about the agent* — that it is findable, online, trustworthy, capable of X — is `social-committee`.

- The mainnet topic's 23 messages span **2025-11-04 to 2025-11-10** — six days, then silence for roughly ten months to the date of this recon.

### A-4. EXTENSION — where `wishmail` data can live

Three candidate slots. Only one is both durable and reachable, and it is not the same one that is both writable and readable.

**(a) `profile.properties` — on chain, hash-anchored, but the broker never returns it.**
HCS-11 `properties` is the standard's free extension point, and the live profile above proves the broker carries arbitrary keys there onto Hedera (`tags`, `agentFactsUrl`) inside a brotli-compressed, sha256-addressed HCS-1 file. `POST /register` accepts it: `"profile": {..., "additionalProperties": true}`.

But: `GET /resolve/{uaid}` and `GET /agents/{uaid}` returned no `profile` field (C-3), and a full-text scan of both live responses found **no occurrence of `agentFactsUrl`**. So anything hung here is durable and verifiable but must be read **from the mirror node**, following `registryEntry.profileReference` yourself. The broker will not hand it to you.

**(b) `metadata` — round-trips through the broker, but is off chain and unsigned.**
`AgentRegistrationRequest.metadata` is `{"type":"object","additionalProperties":true}`, as is `AgentSummary.metadata`, as is `AgentSummary` itself. Live records show the broker preserving submitted metadata keys alongside dozens it adds. Nothing here is signed, hashed, logged, or re-obtainable. The broker also rewrites this bag aggressively (`delegation*`, `trustScore*`, `availability*` are all broker-authored), so a `wishmail` key sits in the same namespace as fields the operator mutates.

**(c) `endpoints` — `{"additionalProperties": true}`, with `inboundTopicId`/`outboundTopicId` already conventional.**
The live record shows `"endpoints": {"primary":"…","inboundTopicId":"unknown","outboundTopicId":"unknown"}` — neither key is in the OpenAPI's `endpoints` property list, so unknown endpoint keys demonstrably survive. This is the natural home for `doorbell`.

**Recommendation.** Write `wishmail: {manifestTopic, x25519Pub, keyEpoch, doorbell}` into **`profile.properties`** — it is the only slot with a hash anchor, and `x25519Pub` and `keyEpoch` are exactly the fields that must not be mutable by an intermediary. Mirror a copy into `metadata.wishmail` for discoverability, and treat the mirror as an untrusted hint that must be reconciled against the on-chain profile before use. Do not treat the broker's copy as authoritative for any key material.

### A-5. UAID — how to recompute one

Fully specified and **verified reproducible**. I recomputed a live broker UAID exactly from the source below.

**Step 1 — canonicalize** (`standards-sdk@98825d12` `src/hcs-14/canonical.ts:41-63`). Normalize `registry` and `protocol` with trim+lowercase; `name`, `version`, `nativeId` with trim; sort `skills` ascending numerically. Then emit keys in this fixed order (`:50-57`):

```ts
const orderedKeys = ['skills','name','nativeId','protocol','registry','version'] as const;
…
const canonicalJson = JSON.stringify(canonicalObject);
```

Two guards fire during canonicalization (`:24-39`): for `protocol === 'hcs-10'`, `nativeId` **must** be Hedera CAIP-10; for `acp-virtuals`, EIP-155 CAIP-10.

**Step 2 — hash and encode** (`src/hcs-14/did.ts:52-64`):

```ts
const hasher = adapter.createHash('sha384');
const digestResult = hasher.update(Buffer.from(canonicalJson, 'utf8')).digest();
…
const id = base58Encode(bytes);
```

`base58Encode` is the Bitcoin alphabet (`src/hcs-14/base58.ts:5`) and is applied **raw — no multibase `z` prefix**. (`did.ts:10-13` defines `encodeMultibaseB58btc` with the `z`, but that is used only for the `src` parameter of a wrapped DID, never for the AID.)

**Step 3 — append parameters** (`did.ts:24-33`), in this fixed order:

```ts
if (params.uid) entries.push(['uid', params.uid]);
if (params.registry) entries.push(['registry', params.registry]);
if (params.proto) entries.push(['proto', params.proto]);
if (params.nativeId) entries.push(['nativeId', params.nativeId]);
if (params.domain) entries.push(['domain', params.domain]);
if (params.src) entries.push(['src', params.src]);
…
return paramString ? `uaid:aid:${id};${paramString}` : `uaid:aid:${id}`;
```

Defaults (`:36-45`): `registry` falls back to the canonical `registry`, `nativeId` to the canonical `nativeId`, and `uid` to `'0'` — matching `hcs-14/index.md:197` ("The `uid` parameter is required and shall be \"0\" if not applicable").

**Verification.** Against the live record for `sdk-erc8004-demo-mhkld2e7`, the canonical JSON

```
{"skills":[0,4,18],"name":"sdk-erc8004-demo-mhkld2e7","nativeId":"https://integrated-enough-moving-culture.trycloudflare.com/.well-known/agent.json","protocol":"a2a","registry":"hol","version":"1.0"}
```

hashed with sha384 and base58-encoded yields `4ZFPnAVFTnZpPFqzRm7h1bvR9AWLYFEvZmqVEqHqA9UtBp5L5G2gbVodjpCsMV7xR9` — byte-identical to the UAID the broker serves and to the one written on chain. The AID half of a HOL UAID is `math`.

**`uid` and `nativeId` for a Hedera account.** `src/hcs-14/sdk.ts:361-403`:

```ts
const isHedera = options.issue.method === 'hedera';
if (isHedera) {
  …
  if (!nativeId) { … nativeId = toHederaCaip10(this.network, this.operatorId); }
  if (!uid && proto === 'hcs-10' && this.network && this.operatorId) {
    …
    if (this.hcs10Client) { uid = await this.hcs10Client.getOperatorId(); }
    else { … uid = inbound ? `${inbound}@${this.operatorId}` : this.operatorId; }
  }
}
uid = uid ?? '0';
```

So for an HCS-10 agent: `nativeId = hedera:<network>:<accountId>` (CAIP-10), `uid = <inboundTopicId>@<accountId>` (the HCS-10 `operator_id` form pinned in the earlier recon at `hcs-10/index.md:652`), falling back to the bare account id, then to `'0'`.

**Warning, and it bites.** `nativeId` is **inside** the hash; `uid` is **outside** it. Change the account and the AID changes; change the inbound topic and it does not. `hcs-14/index.md:760`:

> AID identifiers are deterministic by design. Identical canonical agent data yields the same AID. … If distinct deployments require separate identifiers, bump `version` or use distinct `uid` values outside the hash; do not introduce non‑deterministic inputs into the canonical set.

And in practice the guard does not always fire. The live `hol` agent above has `proto=a2a` with `nativeId` set to an HTTPS URL, while holding a Hedera profile topic and an on-chain registration — so a WISHMail resolver **must not** assume a `registry=hol` UAID's `nativeId` is a Hedera account. It is CAIP-10 only when `proto=hcs-10`.

**Payment flows** (`:293-299`) — relevant because Hedera's ordering is not the default one's mirror image:

| Flow | Ordering |
| --- | --- |
| `authorization` (default) | verify → resource → settle → respond |
| `upfront` | settle → resource → respond |
| `escrow` | settle → resource → settle → respond |

`:299`: *"Invariant: at least one check — a verify or settle before the resource — MUST run before the resource executes."*

**Replay prevention.** `:612-619` is entirely EIP-3009-shaped:

> - **EIP-3009 Nonce**: Each authorization includes a unique 32-byte nonce to prevent replay attacks
> - **Blockchain Protection**: EIP-3009 contracts inherently prevent nonce reuse at the smart contract level
> - **Time Constraints**: Authorizations have explicit valid time windows to limit their lifetime
> - **Signature Verification**: All authorizations are cryptographically signed by the payer

The `nonce` / `validAfter` / `validBefore` triple the brief names lives only in the EVM `authorization` object (`:216-223`): `from`, `to`, `value`, `validAfter` (string, Required, "Unix timestamp when authorization becomes valid"), `validBefore` (string, Required, "Unix timestamp when authorization expires"), `nonce` (string, Required, "32-byte random nonce to prevent replay attacks").

The scheme-level rules that apply across networks are in `scheme_exact.md:41-42`:

> - **Replay**: the network's own primitive is authoritative. A consumed primitive MUST produce a settlement failure, never a success.
> - **Duplicate delivery**: the network primitive prevents double-spend, not double-delivery. … Such methods MUST deduplicate settlements atomically across every process serving `/settle`, retaining each key until its payment can no longer land.

**Hedera has none of the EVM triple.** See C-10.

### B-8. HEDERA — plainly

**Yes. Hedera x402 is specified, registered, shipped, and live — and it is testnet-only in practice.**

**Specified.** `specs/schemes/exact/scheme_exact_hedera.md`, 169 lines, added 2026-02-06 (`ae26f5e1`, "feat: Implement exact payment scheme specification for Hedera HTS FT …", author Peter Swierzy), hardened 2026-07-03 (`d00e3881`). `:48`: *"`asset`: The Hedera entity ID of the HTS fungible token. Payload (`:57-63`) is `{"transaction":"<base64>"}` — *"the Base64‑encoded, serialized, **partially signed** versioned Hedera transaction (e.g. `TransferTransaction`), signed by the client but **not yet** signed by the fee payer."* The client sets `transactionId.accountId` to the facilitator (`:17`), signs, and the facilitator co-signs as fee payer and submits (`:26`).

Facilitator MUSTs worth reading before building (`:108-161`): the transaction MUST be a `TransferTransaction` **directly**, never wrapped in `ScheduleCreateTransaction` (`:114`); `transactionId.accountId == extra.feePayer` (`:116`); only transfer operations, HBAR net sum zero, asset net sum zero (`:117-119`); the `feePayer` MUST NOT appear as a negative entry in any transfer list (`:124-125`); exactly one asset, exactly the required amount, no extra positive net transfers (`:134, 146-147`); and — the 2026-07-03 addition (`:154`) — the facilitator MUST fetch the payer's on-chain account key and verify a valid signature satisfying it, including KeyList/threshold accounts, rejecting with `invalid_exact_hedera_payload_signature_invalid`.

One design note the brief should absorb (`:165-167`): if `payTo` is an alias rather than an existing account, an HBAR transfer triggers auto-account creation **at the facilitator's expense**. The spec explicitly does not forbid it and leaves the policy to each facilitator.
