# Six traces of the Correspondent, read 2026-09-11

**Nothing here was run, signed, or spent.** This is a reading of the code at `49be94b`, against the specification at
`v0.5.13` and against what the mirror node already holds from Gates One, Two and Three. Every claim carries a
`file:line` or a recorded mirror observation. Where a trace contradicts something this repository already says, the
contradiction is stated and the record is named.

**Why these six.** Tonight's demo is the first time **goose** drives the Correspondent MCP server. Three gates have
run and every one of them was driven by a **CLI** — `app/sdk/letter.cli.ts`, `app/sdk/provision.cli.ts`,
`app/sdk/ack.cli.ts`. The goose-facing surface has never been exercised on consensus or off it, and five facts about
it were written down nowhere. One of them was believed to be able to stop the run at the first ring. It cannot; three
others can.

Register: **FETCHED** = read from the code, the pinned text or the mirror, cited. **MINE** = an inference, marked.
**RECORD** = Sonic ruled it.

## P1 — Who pays the HIP-991 ring, and does a fresh operator wallet need anything?

**Answer: the operator wallet pays, it must hold one stamp at the moment of the ring, and a brand-new wallet with
zero automatic token associations is already handled by code that runs before any ring. There is no blocker.**

### Who the payer is

`send` submits the `connection_request` through the session's own writer — `app/src/tools/send.ts:572-573`:

```ts
const ringer: Writer = ctx.ringer ?? ctx.consensus;
request = await ringer.submitMessage(coordinates.doorbell, body, TRANSACTION_MEMO.connection_request);
```

`ctx.ringer` is declared (`send.ts:129`) and **never populated in production**, deliberately —
`app/sdk/letter.ts:75` says so in as many words: the request is submitted through the session's own writer and the
doorbell's HIP-991 fee is debited from `Session.payerId`. That payer is the home's own operator wallet unless a
purchase is carrying — `app/sdk/session.ts:216-217`:

```ts
const payer   = borrowed?.signer    ?? homePayer;
const payerId = borrowed?.accountId ?? homePayerId;
```

with `homePayerId = home.config.payer.accountId` (`session.ts:206`). `Consensus.submitMessage` hands that to
`submit(client, ctx.payerId, tx, [ctx.agent], nodePin)` (`app/sdk/live.ts:322`), and `submit` sets the transaction id
under it (`app/src/ops/hedera.ts:70`). **HIP-991 debits the fee from the transaction payer**, so the stamp leaves the
operator's account and not the agent's.

This is §4.4 as D-157 amended it — `spec/WISHMAIL_SPEC_v0_5.md:567`: *"A sender that pays for itself rings in one hop,
and the fee is taken from the stamps it already holds. A sender that borrows a payer … first transfers one stamp to
that payer, bearer custody in transit and not key custody."* This deployment borrows, because the agent signs and the
operator pays (§3.5).

### The agent → operator hop, as it stands now

`app/sdk/letter.ts:198-205`:

```ts
export async function ringStamp(s: Session, willRing: boolean): Promise<string | null> {
  if (!willRing) return null;
  if (s.payerId === s.account) return null;
  if ((await payerStamps(s)) >= 1) return null;
  const ref = s.consensus.pinTransferRef();
  const settlement = await s.consensus.transferStamps(ref, s.payerId, 1, '');
  return settlement.txRef;
}
```

`payerStamps` reads the **payer's** balance, never the agent's (`letter.ts:215-220`). The transfer moves one unit
agent → payer, signed by the agent, paid by the payer (`app/sdk/live.ts:374-386`).

**The Gate Two defect was the gate, not the hop.** `ringStamp` used to ask only whether the payer held a stamp, so it
moved one even where no door would be rung and stranded it. It now takes `willRing`, and **both callers derive that
from §7.1's own lane rule** rather than a second spelling of it — `app/sdk/server.ts:283-291` and
`app/sdk/letter.cli.ts:175-179, 253`. That matters for a reply: a reply rings nothing, and a hop for a reply strands a
stamp (D-171, and the comment at `server.ts:275-280`).

### What the mirror holds, both sides of the fix

- **Before** — B's doorbell `0.0.10452149` #1, ring `0.0.10450879-1789064908-008543399`: the assessed custom fee is
  `TOKEN 0.0.10426208 · 0.0.10450879 −1 · 0.0.10426205 +1` (`app/OPERATIONS.md:2464-2474`). The payer is the operator
  and the treasury collects. *"The two-hop worked."*
- **After** — Gate Three, C's doorbell `0.0.10468687` #1: C2OPERATOR `0.0.10450880` held no `$POSTAGE` and never had,
  because B had never rung a doorbell; the stamp associated itself on arrival and the fee consumed it in the same
  second; it ends at **0** (`app/OPERATIONS.md:4396-4412`). B spent three stamps — one at the door, two as postage —
  and the treasury gained exactly three.

**The code and the ledger agree.** The payer of the ring is the operator in both, and no `$POSTAGE` remains on an
operator wallet after a ring that needed one.

### The fresh wallet — and why the feared blocker is not one

The concern was that a wallet Sonic creates himself may have `max_automatic_token_associations = 0`, where the demo
wallets were created with `-1` (`app/OPERATIONS.md:1363-1377`, `ops/demo-operators.ts`), and that the hop would then
fail with `TOKEN_NOT_ASSOCIATED_TO_ACCOUNT` **after** a ring had been paid for.

**It is already handled, by code that runs during provisioning and therefore before any ring** —
`app/sdk/mailbox.ts:270-295`:

- reads the operator from the mirror and **returns early if it already holds the token** (`:273`);
- prints `provision.autoassociates` and **submits nothing** where `max_automatic_token_associations` is `-1` or has a
  free slot (`:282-286`);
- **otherwise submits a `TokenAssociateTransaction`**, on the **home** client, paid by the operator (`:287-292`), and
  says `provision.associated`;
- refuses the whole mailbox if that association fails (`:293`).

It reads `s.homePayerId` — the operator — and **never the carried Postmaster**, deliberately: `mailbox.ts:263-269`
records that associating the Postmaster would be useless and outside the carry policy, which would refuse it,
correctly. `homePayerId` stays the operator even in a carried session (`session.ts:206, 216-217`), and the local
client is kept for exactly this (`session.ts:220-222`).

It is called once, from `generateMailbox` (`mailbox.ts:367`), and **`buy_stamp` with `provision` reaches
`generateMailbox`** at `app/sdk/counter.ts:452`. So the order on a fresh wallet is: purchase → account created →
operator associated (or found already able) → six topics → … → ring, later. The shipped config template already
tells an operator this (`app/sdk/config.template.json:27-31`): *"`generate_mailbox` associates it on first run and
says so; the association is paid by the operator and costs about 0.05 hbar."*

**So none of the three options raised is required.** (a) *the agent pays the ring itself* is §4.4's one-hop and would
need ℏ on the agent account — permissible, since what an operator funds into its own agent is that operator's affair
(CLAUDE.md §11), but it is a change and not a fix. (b) *an association at home init* already exists and is automatic.
(c) *create the wallets with unlimited auto-associations* is unnecessary; it only skips one 0.05 ℏ transaction.

**Read it anyway before the run.** `max_automatic_token_associations` is exactly the class of fact a receipt cannot
show, and Gate Three's report read it from the mirror and wrote it down for that reason (`app/OPERATIONS.md:3802-3808`).

### Two things this trace turned up that are worth recording

1. **`ensurePayerHoldsStamps` runs only inside `generateMailbox`.** An agent that brought its own topics and never
   called it has no code path that associates its operator before the first ring, and the hop would fail at the
   network. Not tonight's path — the demo provisions through the counter — but the self-provisioned path has this
   hole. **MINE.**
2. **The hop runs before `send`'s postage check.** A first contact therefore needs the agent to hold
   `postage + 1`: `send.ts:898-900` refuses `SEND_INSUFFICIENT_STAMPS` below 1 at first contact, and `:958-963`
   checks the agent's balance against postage after the hop has already left.

## P2 — Does the counter sell provisioning without a stamp bundle?

**Answer: no. The minimum provisioning purchase is one stamp plus the provisioning price. A stamps-only purchase is
the only thing an already-provisioned agent can make. To goose it is one call; on the wire it is never one.**

### `count` cannot be zero

`app/src/counter/purchase.ts:210`:

```ts
if (!Number.isInteger(count) || count < 1)
  throw new CounterRefusal('STAMP_HOLDER_INVALID', `count must be at least 1, not ${count}`);
```

and independently in pricing (`app/src/counter/pricing.ts:238`). **An omitted `count` defaults to 1** rather than
failing — `app/src/counter/server.ts:230` and `app/sdk/server.ts:215`.

This is structural and not merely a guard: leg 2 of the purchase moves `count` stamps from the treasury to the
holder's public-key alias and **is what creates the account** under HIP-542 (`purchase.ts:251-254`). A zero-stamp
provisioning would have no account-creating leg at all.

Pricing composes one hbar leg from both parts — `purchase.ts:242-264`: the count-priced stamps plus
`quote.provisioning.amount`, with the `registrationFee` as leg 3, funded by the Postmaster into the new account. On
the live list (`app/price-list-3.hedera-testnet.json:70-74`) `provisioning` is `{method: "hbar", unitPrice: "2",
registrationFee: "0.05"}`; sequence 4 repriced `unitPrice` to `"30"` after Gate One measured a mailbox at 27.78 ℏ.
Stamps are rate-priced at `0.10 USD` with a twelve-for-`1.00` bundle applied **only at exactly that count**
(`pricing.ts:240-255`).

### Stamps-only, and the returning agent

`provision: true` with an account holder is refused before anything is charged —
`app/src/counter/purchase.ts:222-231`:

> `the holder already has an account (…), so there is no mailbox to provision. Buy without `provision` — a returning
> agent keeps the one it has (D-165).`

The client picks the holder from whether an account exists at all (`app/sdk/counter.ts:275`), so a returning agent
buys stamps and nothing else. This is the idempotence CLAUDE.md §11 requires, asserted against consensus rather than
against a local file.

### One call, or two

**To goose it is one call.** `app/sdk/server.ts:208-226` handles `buy_stamp` with a single `buyStamps(...)` and
returns one `StampReceipt`; `server.ts:210-213` says *"With `provision`, this is the whole of §4.6's provisioned
path … goose sees one call, because it is one purchase."*

**On the wire it is never one.** At minimum a quote (`app/sdk/counter.ts:285-290`) and a settle carrying the buyer's
signature (`:348-358`); a provisioning purchase adds a carry leg per body and then the receipt. The four legs are
enumerated at `app/src/counter/server.ts:128-138`, and every leg that is not the receipt is returned **flagged as an
error** with its payload in `_meta` under `PAYMENT_REQUIRED` / `PAYMENT_CARRYING` / `PAYMENT_CARRIED` — which is
MCP's rule and not ours (LIMITATIONS L-5). Those codes are translated out before reaching the agent
(`app/sdk/server.ts:73-96`), which calls their appearance *"a defect in the client half"*.

**So "provision, then buy stamps" is not the shape.** Provisioning already carries stamps; a separate purchase is a
top-up and needs no `provision`.

### One finding

**The counter does not JSON-Schema-validate `buy_stamp` input.** The only `schemas(...).validate` on that path is on
the **output** receipt (`purchase.ts:449`). The advertised `minimum: 1` and `required: ["count","payment","holder"]`
(`app/src/mcp/schemas/buy_stamp.input.schema.json:8-12, 133-137`) are enforced imperatively at `purchase.ts:210` and
`pricing.ts:238`, and `count` silently defaults where the schema marks it required. Nothing is wrong on consensus;
what is true is that the published shape and the enforced shape are held together by hand. **MINE.**

## P3 — Does `send` block until the ack?

**Answer: no, and it must not. There is no ruling to make here — the specification already made it.**

### Where it returns

`send` returns at `app/src/tools/send.ts:1063-1072`, immediately after step 7:

```ts
return {
  kind: 'postmark', postmark: zero, envelope: assembled.envelope, postmarks,
  settlement, manifestLocator, lane: lane.topicId,
  ...(receipt === undefined ? {} : { receipt }),
};
```

`receipt` is `requestReceipt`'s result (`send.ts:666-747`), whose last act is the HCS-10 `transaction` operation
announcing the schedule on the lane (`:731-737`). What it carries is `ReceiptRequested {scheduleId, expirationTime,
requestSequenceNumber, requestConsensusTimestamp, manifestHash, reused}` (`send.ts:226-237`) — **the request, not the
acknowledgment.**

`Consensus.scheduleSign` (`app/sdk/live.ts:481-496`) has exactly **one** caller: `app/src/tools/ack.ts:205`. The
ScheduleSign is not on `send`'s path at all. `send.ts:1045-1048` states the principle: *"The envelope is SETTLED
before this runs and stays SETTLED whatever happens in it."*

Gate Three shows the same thing as a gap on consensus: the receipt request landed at `1789090079.500349708` and C's
signature executed at `1789098271.804108896` — more than two hours later, and `send` had long returned
(`app/OPERATIONS.md:4307-4337`).

### Why it is not open

§12's **P-14** — `spec/WISHMAIL_SPEC_v0_5.md:1821`:

> **P-14 — Affidavit, not gate.** No tool call by one agent waits on an act of another, except a first-contact
> `send`, which is bounded by a window and returns a slip when it closes. Every proof is a post-hoc witness; nothing
> in this document sits inside a caller's latency-critical path.

§6.4's own `Conformance:` note names **T-P14-1** for exactly that sentence. A `send` that blocked through the ack
would violate a named invariant with a registered test. **The alternative is closed by the specification, not by
preference.**

### The waits, for the record

- **First contact**: `MAX_ATTEMPTS` 3 × `DEFAULT_WINDOW_SECONDS` 30 = **90 s** (`send.ts:419-420`), the deadline
  recomputed per attempt (`:600-615`). **Every attempt after the ring is a re-READ and never a re-ring** — the ring
  happens once, at `:573`, outside the loop (`:415-418`). Where this process already rang, it waits one poll interval
  and looks again before believing absence (`:892-895`), which is the rule Gate One taught.
- **Every consensus write** then polls the mirror under `FRESH` — 45 s at 1.5 s (`app/src/ops/mirror.ts:18-21`) —
  including once per chunk (`send.ts:999-1026`). §6.4 step 6 has no wait of its own; `submitMessage` returns only
  once consensus has assigned a timestamp (`send.ts:1028-1029`).
- A one-chunk certified first contact can therefore take several minutes, and there is no overall deadline on the
  tool call.

### What a caller sees in between: nothing

**There is no `notifications/progress` anywhere in this repository.** The only occurrence of the string is a comment
(`app/src/tools/narration.ts:9`), which records why: goose renders tool-call cards and final payloads and does not
render progress. On the `send` path the MCP server writes exactly one line to stderr, and only conditionally
(`app/sdk/server.ts:292`). **`send` is the tool with the longest wait and the least live output.**

So the shape is already *posted, receipt requested, pending*, and `ack` is where ACKED appears. What is missing is
not the behaviour but the telling of it — see P4's sibling finding and the note on the narration template below.

## P4 — Watcher topology, and what holds a process open

### The watcher is inside the MCP server, and nowhere else

`watchDoorbell` (`app/sdk/watcher.ts:284-323`) has exactly **one** construction site in the repository:
`app/sdk/server.ts:386`. There is no separate entrypoint, no driver, and no npm script for it. It is a
self-rescheduling `setTimeout` at **5 000 ms** (`watcher.ts:312`), **not** `unref`'d, so it alone keeps the Node
event loop alive.

It is memoized with `watcher ??=` (`server.ts:386`) and started from three places — at boot (`:392`), after a
provisioning purchase creates a mailbox (`:222`), and after `generate_mailbox` (`:234`) — so there is exactly one
watcher **per process**. `app/OPERATIONS.md:2197-2205` describes the arrangement correctly: B's process is
`npm run correspondent` on B's home, *"whose doorbell watcher (D-158) is a timer beside the tools."*

Auto-accept is `tick()` (`watcher.ts:288-300`) → `answer()` (`:149-266`), which derives what is outstanding **from
consensus only** (`unanswered()`, `:69-102`). The stamp is the gate; screening is 0.6.

### It has no way out

- **`Watcher.stop()` exists at `watcher.ts:318-321` and is never called.** Dead code.
- **There is no `process.on`, no `SIGINT`, no `SIGTERM`, no `beforeExit` handler anywhere in `app/`.**
- **`app/sdk/server.ts` has no `transport.onclose` and no `server.onclose`.** Its last statement is
  `await build(box, ensureWatcher).connect(new StdioServerTransport())` (`:399`); the only `process.exit` is in the
  top-level catch (`:406`).
- `Session.close()` (`session.ts:270-273`) closes the two Hedera clients and is called only on the re-boot path
  (`server.ts:378`), to release the *previous* session.

**Consequence.** When goose closes stdio, the transport fires `onclose` and nothing is subscribed; the process does
not exit; the watcher keeps ticking, **keeps auto-accepting connection requests, keeps creating lanes, and keeps
spending the operator's ℏ** with no client attached. Restart goose and a **second** watcher runs on the same
doorbell. `unanswered()` is idempotent from consensus, but that is not process uniqueness: two watchers reading one
outstanding request can both pass it and both create a lane — **and a lane cannot be closed.** §7.1 would then choose
between two lanes that both exist. There is no lock, lease or pidfile preventing it. **MINE, and it is the likeliest
failure of the first goose restart rather than a hypothetical.**

### Process count

**Three** for a two-agent flow: `npm run counter` (Streamable HTTP, :4600) plus one
`npm run correspondent -- <home>` per agent. Watchers add none. The counter is needed only for `buy_stamp`;
`resolve`, `send`, `inbox`, `ack` and `verify` run entirely inside the Correspondent.

### The provisioning driver that does not exit — and a correction to this repository's own record

`app/OPERATIONS.md:4216-4218` attributes the Gate Three non-exit to the counter's MCP transport:

> *"`Session.close()` releases the two Hedera `Client`s; nothing closes the counter's MCP transport."*

**That diagnosis is not supported by the code, and was not on the day.** Both closes exist and both predate the gate:

- `app/sdk/counter.ts:490-492` — `finally { await client.close(); }`, present since the first Correspondent commit.
- `app/sdk/provision.cli.ts:60-61, 269-271` — an `open: Set<Session>` with a `.finally` that closes every session,
  added **2026-09-09**, the day before Gate Three.

**What actually pins a Node process here is the Hedera SDK's own network-refresh timer.** Every `Client` constructor
arms a **24-hour, non-`unref`'d `setTimeout`**, cleared only by `close()` —
`node_modules/@hashgraph/sdk/lib/client/Client.cjs:158, 165, 834-839, 864-874`. A carried boot constructs **two**
clients (`app/sdk/session.ts:223-226`). That matches the observation exactly: a process that stayed alive with no
further writes, while the rerun — which skips `buy_stamp` and so constructs no extra clients — exited in seconds.

**The leak that can be named with certainty:** `carried` (`app/sdk/counter.ts:443`) is released only by being
returned at `:466` and added to the caller's set. `buyStamps`'s `finally` (`:490-492`) closes the MCP client and not
`carried`. **Every throw between those two lines leaks two Hedera clients** — the account-mismatch throw (`:444-449`),
anything inside `generateMailbox` (`:452`), a carry-leg refusal, the receipt-loop ceiling (`:473-482`), the
`STAMP_PAYMENT_FAILED` at `:469-472`.

**What is NOT attributed, and is not guessed at:** Gate Three's first run appears to have taken the happy path, since
`register_agent` ran after `buyStamps` and landed. On that path every session is in `open` and closed by the
driver's own `finally`. **From static reading alone the specific hang of that specific run cannot be attributed**, and
this report does not attribute it. Resolving it needs one run under `--trace-exit` or a
`process.getActiveResourcesInfo()` dump at the end of `main()`.

**The gate report is not amended.** A dated section in `app/OPERATIONS.md` supersedes the diagnosis and says what is
known and what is not.

## P5 — Can the Correspondent MCP server be pointed at the modelled ledger?

**Answer: no — not from config, not from environment, not from argv. And injection alone would not be enough.**

### What the model is

`MemoryLedger` (`app/src/tools/memory.ts:97`) implements the same interfaces the live seam does: `reader(): Reader`
(`:461`) and `as(account): Consensus` (`:502`), both defined at `app/src/tools/consensus.ts:130, 171, 222`, which
`liveReader` and `liveConsensus` also return (`app/sdk/live.ts:152, 297`). The **lag knob** is
`lag(topicId, reads)` (`memory.ts:147-150`) — per-topic and counted in **reads, not seconds**: *"The newest message
is on consensus and this read does not show it, which is the whole of what ingestion lag is"* (`:466-471`). The world
builder is `conformance/support/world.ts`, construction only (`:4-7`).

### Why it cannot be pointed

- `boot()` constructs two real clients and `liveConsensus` **unconditionally** — `app/sdk/session.ts:223-238`.
  `BootOptions` (`:180-191`) has three fields — `withoutAccount`, `expectAccount`, `payer` — and none is a ledger.
  The one injectable thing at that seam is the **payer**, which is the carry seam, not a ledger seam.
- The MCP server builds `liveReader` inline at `app/sdk/server.ts:200` and `:286`, and `mirrorSource(s.mirror)` at
  `:181` and `:268`. `s.mirror` is `new Mirror(home.mirrorNodeUrl)` (`session.ts:208`).
- `CorrespondentConfig` (`app/sdk/home.ts:51-74`) has no ledger field, and `WISHMAIL_HOME` (`server.ts:361`) is the
  only environment variable this server reads.

### Why injection alone would not be enough

**Provisioning bypasses the interface entirely.** `Consensus` cannot express topic creation, account creation, token
association or an account-memo update, and these construct `@hashgraph/sdk` transactions directly:

- `app/sdk/mailbox.ts:226` (the six topic creations), `:287-290` (the association), `:441-444` (§9.2's account memo);
- `app/sdk/registration.ts:178-187`, which **builds its own client**, deliberately, so the mirror records the agent
  as payer — the one fact §9.5 reads to decide `blurred`;
- `app/sdk/watcher.ts:163-173`, the doorbell answer.

Only the chunk and register-entry submissions inside `generateMailbox` go through `Consensus`
(`mailbox.ts:313, 420`).

### What the model does and does not carry

| | Modelled |
|---|---|
| HIP-423 scheduled transactions | **yes**, with real `SchedulableTransactionBody` bytes, executing only when a required key signs, and refusing a duplicate with `IDENTICAL_SCHEDULE_ALREADY_CREATED` (`memory.ts:110-122, 302-400`) |
| HIP-991 custom fees | **yes**, in stamps, with fee-exempt keys (`memory.ts:11-14`) |
| Mirror lag | **yes** (`memory.ts:147-150`) |
| Token transfers | **yes**, one token only — which is why T-P11-1 is a named partial (`conformance/DERIVATION.md:471`) |
| The counter / §14.2 exchange | **no** — an outbound HTTP MCP call (`app/sdk/counter.ts:273`) |
| Signature verification | **no** — *"A key here is a string"* (`memory.ts:19-23`) |
| ℏ fees, throttles, expiry-as-time | **no** — so `register_agent`'s balance gate is unmodellable |
| HIP-542 alias account creation | **no** |

### The smallest change, if it is ever wanted

`readerSource()` (`app/src/tools/verify.ts:449`) already adapts any `Reader` into the `ProfileSource` that `resolve`
takes, so the **read** half is close: one optional field on `BootOptions`, the `Reader` and `ProfileSource` carried on
the `Session`, and `resolve`, `verify`, `inbox`, `send` and `ack` would run against the model unchanged. The
**write** half is the bulk — a provisioning port with two implementations — and a faked counter besides. The
precedent for the latter exists: `app/src/counter/exchange.check.ts` stands the real counter on a loopback socket
against an in-memory mirror, and says plainly that its settle leg runs the replay path because *"there is no offline
consensus node"* (`:29-36`).

**What replaces it tonight** is the DRY mode ruled for the MCP server: a server that constructs no operator client
cannot sign, whatever ledger it is pointed at.

## P6 — The fresh-home path, as the sequence it actually is

| # | Step | Implemented at | Consensus | Counter |
|---|---|---|---|---|
| 0a | copy `app/sdk/config.template.json` → `<home>/config.json`; fill `payer.accountId`, `payer.derKey`, `agent.*` | **nothing implements it** — `app/sdk/home.ts:111` tells you to copy it | no | no |
| 0b | first boot: keys born once into `keystore.json`; `store/` created | `ensureKeys` `app/sdk/keystore.ts:82-94`, from `boot` `app/sdk/session.ts:203` | **no** | no |
| 1 | `buy_stamp` with `provision: true` | `app/sdk/counter.ts:244-493`; mailbox `app/sdk/mailbox.ts:348` | yes — one 3-leg transfer, six topics, the profile chunks, the register entry, the account memo | **yes, mandatory** |
| 2 | `register_agent` — the agent signs **and pays** | `app/sdk/registration.ts:113-260` | yes, one message on the anchor | no |
| 3 | `resolve` self under `hcs14` | `app/src/resolve/hcs14.ts` | **no** | no |
| 4 | `resolve` self under `hol`, assert no `blurred` | `app/src/resolve/hol.ts` | **no** | no |

Step 4 is the acceptance test, and the reason the registration fee is funded at all —
`app/sdk/provision.cli.ts:248-253` stops the run if the agent resolves `blurred`, *"which means the registration was
not paid by its own account"* (§9.5, T-P13-4).

**Keys are born once.** `born()` refuses to overwrite an existing keystore and every epoch's X25519 key is retained
(`keystore.ts:14-25`). A fresh home is a new agent; an existing home is a returning one (D-165).

**`buy_stamp` is the only outbound call the Correspondent ever makes** — `app/sdk/counter.ts:4-7`. Everything else
runs in-process against a mirror node.

**On the MCP surface** goose has all six verbs plus the two §4.6 affordances `generate_mailbox` and `register_agent`

## Three findings on the goose surface that no gate could have caught

These are not among the six questions. They came out of the same reading, and they bear on tonight directly, because
each is reachable only from an MCP client and every gate so far was driven by a CLI.

**1. `send`'s published input schema and its handler disagree.** `app/src/mcp/schemas/send.input.schema.json`
declares `{coordinates, payload (base64), returnReceipt, window}`, requires `coordinates` and `payload`, and sets
`additionalProperties: false`. The handler reads `args['address']`, `args['payload']` as **utf8**,
`args['windowSeconds']` and `args['receiptWindowSeconds']` (`app/sdk/server.ts:256-305`). **A client that builds its
call from the published schema gets `SEND_UNRESOLVED`** (`server.ts:257`). `send` is the **only** one of the six that
disagrees — `resolve`, `buy_stamp`, `inbox`, `ack` and `verify` all match their schemas. T-P15-4's premise is that
the surface is defined once.

**2. `send`'s result does not match its own `outputSchema`.** `app/sdk/server.ts:307` returns the bare `SendResult`
as `structuredContent`, while `wrap('result', …)` (`app/src/mcp/tools.ts:84-92, 168-172`) requires `{result: …}` with
`additionalProperties: false`. The MCP TypeScript SDK caches a validator per tool and runs it on `structuredContent`.
The same class of mismatch is in `delivery.output.schema.json`, which types `returnReceipt` as the §5.8
`ReturnReceipt` where `inbox` returns the §6.5 `PendingReceipt` (`app/src/tools/inbox.ts:55-62, 74-75`) and forbids
four properties the payload carries.

**3. Ten narration sentences are dead.** `app/src/tools/sentences.json` holds `send.lane.found`, `send.ringing`,
`send.request`, `send.lane.created`, `send.manifest`, `send.assembled`, `send.affixed`, `send.chunk`,
`send.settled` and `send.slip`. **No code emits any of them** — the only live callers of `line()` are `provision.*`
(`app/sdk/mailbox.ts`), `purchase.*` (`app/sdk/counter.ts`), `register.*` (`app/sdk/registration.ts`) and
`narrative.*` (`app/src/tools/verify.ts`). So of D-162's *one template, three readers*, `send` has only the third,
and the text block a caller receives is `JSON.stringify(payload, null, 2)` — **the same JSON twice**
(`app/sdk/server.ts:49-54`). The drift check cannot catch it: `app/sdk/correspondent.check.ts:216-234` asserts that
there are more than twenty keys and that none implies delivery, and never that a key has a caller.

## Two corrections against the reading itself

A report that repeats an error found while making it is worse than no report.

1. **`pricelist3.ts` and `pricelist4.ts` DO honour `--dry-run`.** Neither file reads `process.argv`, which looks like
   the asymmetry `app/src/ops/mode.ts` was written to prevent — but both import `publishPriceList` from
   `pricelist2.js`, whose **module-level** `const dryRun = !runMode('prices').live` (`app/src/ops/pricelist2.ts:41`)
   evaluates against the same argv at import time. **Not a defect.** It is named anyway, because a dry flag honoured
   through a module-level constant reading `process.argv` across a forwarding chain is precisely the 2026-09-10
   class: correct today, one refactor from a run that prints DRY and signs. It is the reason the banner-with-argv is
   a rule and not a nicety, and the reason the server's DRY mode is being built as a property of what is
   **constructed** rather than of what is **checked**.
2. **`register_agent`'s `dryRun` is real and is the smallest instance of the same thing.**
   `app/sdk/schemas/register_agent.input.schema.json` declares it — *"report whether a registration exists and what
   would be submitted, and **submit nothing**"* — and `app/sdk/server.ts:238-249` never reads it;
   `registerAgent` (`app/sdk/registration.ts:113-118`) has no such parameter. **A goose call with `dryRun: true`
   signs, submits on the HOL anchor, and spends the agent's only ℏ.** `generate_mailbox`, two cases above in the same
   switch, honours the same flag (`server.ts:230`).
