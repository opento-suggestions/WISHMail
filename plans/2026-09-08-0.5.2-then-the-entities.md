### D-145 — `validFrom` is dropped (§G item 9)

`spec/WISHMAIL_SPEC_v0_5.md:1805` — the line `  validFrom      timestamp` inside §14.3's `PriceList`
shape block — is deleted. It is the field's only occurrence in 2,238 lines: no prose sentence, no
MUST, no `Conformance:` note and no ledger row reads it. §14.3:1794 already fixes when a price takes
effect — *"The price current at a purchase is the latest price message with a consensus timestamp
before the purchase's"* — and T-P11-4 at :1811 tests against that same clock, so a second notion of
effect would compete with the one the Verifier actually uses. It also could not have been what it
looked like: a message's bytes are fixed before consensus assigns it a timestamp.

`spec/schemas/price-list.schema.json` drops `validFrom` from `required` **and** from `properties` —
the schema carries `"additionalProperties": false`, so leaving the property defined while unrequired
would keep a field nothing reads publishable. `$id` stays `urn:wishmail:0.5:price-list`.

The ADR records what the deletion is not: not a wire-string change under §1.7, and no `PriceList`
has ever been published, so nothing on consensus is invalidated. Rejected readings go in
`## Alternatives considered`: an effective-from semantics (needs new normative prose, and T-P11-4
must then say which clock governs when the two disagree) and an informational optional field (leaves
a field in a consensus document that no rule reads).

Marker: `spec:1796` currently reads `<!-- CHANGED: D-136 -->`; it becomes
`<!-- CHANGED: D-136, D-145 -->`, following the combined-marker precedent at `:2058`.

## Phase B, Step 2 — the provisioning scripts

### Dependencies to add first

- **`ajv` ^8 (imported as `ajv/dist/2020`) and `ajv-formats` ^3** — D-143 requires the price list be
  validated against `spec/schemas/price-list.schema.json` before submission, and the Phase A′ gate
  requires it too. Neither is installed.
- **An RFC 8785 canonicalizer**, not hand-rolled. §5.1's canonical JSON is also the AAD's basis in
  Phase C and `spec/vectors/aad.json` is the court (T-P1-4), so the implementation must be one
  library used in both places. Lean, MINE: `canonicalize` (npm) — small, single-purpose, RFC 8785;
  alternative `json-canonicalize`. **The choice and its reason are recorded in `app/OPERATIONS.md`**,
  which is the requirement, not the particular package.
- **`@types/node` ^22** in `app` devDependencies. `app/tsconfig.json` sets `"types": ["node"]` and
  nothing declares the package — it reaches the tree only through `protobufjs`'s unbounded transitive
  range, so `tsc --noEmit` currently depends on a hoist accident. Global `fetch` typing comes from
  here too, so it is load-bearing for the mirror client.

Also add a `test` script; there is none in either `package.json`.

### Modules

```
app/src/ops/
  env.ts        typed .env load, path-anchored at the repo root; the only writer of .env
  identity.ts   the P-13 seam: Signer construction; the only module that touches key material
  mirror.ts     mirror-node REST: get / poll / typed shapes
  hedera.ts     SDK client, pinned transaction IDs, submit()
  record.ts     app/deployment/hedera-testnet.json — read, put, atomic write
  journal.ts    the intent journal — partial-failure recovery
  step.ts       Step / Ctx / Discrepancy / Outcome, and the runner
  report.ts     the table, the stop-and-report formatter, and the only console surface
  pins.ts       the one narrow write to spec/pins.json (D-144)
  steps/        index.ts (the forced order, in one array) + one file per entity
  provision.ts  entrypoint: flags, runner, table, exit codes
```

`mirror.ts` is separate from `record.ts` because `app/OPERATIONS.md` makes "the record is the mirror
node" doctrine and `conformance/` will reuse the mirror client and never the ops record. `pins.ts`
exists so that D-144's line around `spec/pins.json` is structural: its parameter type is
`{tokenId, treasury}` and it physically cannot write a third field.

**The `Step` contract** is what makes idempotency provable rather than asserted:

```ts
interface Step<Want> {
  key: EntityKey; title: string; kind: EntityKind; needs: readonly EntityKey[];
  want(ctx: Ctx): Want;                                    // pure, no network
  confirm(ctx, entityId, want, policy): Promise<Discrepancy[] | 'absent'>;
  create(ctx, want): Promise<Created>;                     // @hashgraph/sdk
  detail(want, rec): string;                               // the table's right column
}
```

`want()` is pure and network-free, so the same function serves the create path and the confirm path
— which is why run two cannot drift from run one. There is no third description of an entity
anywhere, and the declared `Want` is what lands in the record's `policy` field, satisfying
T-P17-1's "the policy is recorded at creation" by construction rather than by a comment.

### P-13, structurally

`identity.ts` is the only module that ever holds a `PrivateKey`. `bornHere(prefix, label)` generates
in-process, writes the private half **directly to the git-ignored root `.env`** via
`upsertEnvValue`, and returns `{label, publicKey, sign}` — the key surviving only inside `sign`'s
closure. **Nothing prints a key**, on any path; `app/OPERATIONS.md` says so in as many words.

Every step takes a `Signer`, never a `PrivateKey`, so a step cannot leak key material even by
accident: it is not holding any. The Postmaster-side functions take an agent identity of **public
material plus a signing callback**, and branch on nothing — there is no `isPostmasterOwn` anywhere.
When a customer agent is provisioned later, `sign` becomes a network round-trip to that agent and
not one line of `steps/` changes. That is D-140's "does not special-case its own agent," made
structural.

The check, added as `p13:check`:

```
git grep -nE '(AGENT|TREASURY)_DER_KEY' -- app/src | grep -v '^app/src/ops/\(env\|identity\)\.ts:'
```

must be empty, and must stay empty as the service is built. `report.ts` is the only module with a
`console` call (enforced by a `no-console` rule elsewhere), and `provision.ts` scrubs DER-shaped hex
from any uncaught stack trace before printing.

### Idempotency

`app/deployment/hedera-testnet.json` is both the ops record and the script's ledger. Each entity
carries `{kind, role, id, builtBy, signedBy, payer, transactionId, consensusTimestamp,
confirmedFrom, confirmedAt, policy}` — `signedBy` and `payer` are **role names, never keys**, and
`policy.publicKey` records public halves only.

Two questions, two authorities, and conflating them is the bug this design prevents:

| Question | Authority |
|---|---|
| Should I create this? | **the record alone** — key present or absent |
| Is what exists correct? | **the mirror node alone** — never an SDK receipt |

`record.put` flushes on every call (tmp → fsync → rename); batching writes to the end of a run
manufactures the partial-failure case. Two wait policies carry the whole lag design: `FRESH`
(30 s / 1 s) for something just created, `SETTLED` (6 s / 2 s) for something the record says was
confirmed long ago.

**Record says it exists, mirror node disagrees → stop and report. Never recreate.** Mirror nodes
have outages; ledgers do not lose topics. Auto-recreating on a 404 turns a transient read failure
into a permanent duplicate — and for the token, with no admin key, an unrecoverable one. Before
reporting, disambiguate: read the recorded creating transaction; if it is present and `SUCCESS` the
mirror node is fine and the entity really was deleted, and if that 404s too the mirror node is
degraded. Say which. Deleting a record entry is the only way to authorize a re-creation, and it is a
deliberate, diffable act.

**`--repin` guard.** If `spec/pins.json`'s `stampToken["hedera:testnet"].tokenId` is non-null and
disagrees with the record, the run stops rather than overwriting. Re-creating the token is a decision
that also requires re-pinning, and the script makes you say so.

**The acceptance test.** Run `npm run provision` twice: the second creates nothing, exits 0, prints
the same table. Then delete **`agent.manifest`** from the record — never the token, never the
treasury — and re-run: it creates a new instance of that entity type and nothing else. `--json`
emits the same report as data so the assertion is byte-comparable across runs with `status` and
`summary` removed, and run two's `summary.created === 0`.

**Partial failure — the intent journal.** `app/deployment/hedera-testnet.pending.json`, gitignored.
Every creation pins its transaction ID before submit (`setTransactionId` +
`setRegenerateTransactionId(false)`, valid duration 120 s by default) and journals it. The next
run's `resolveOrphan()` reads that transaction from the mirror node and has no ambiguous branch:
found and `SUCCESS` → adopt the entity, confirm, record, clear; found and failed → clear, create
normally; not found and past the 180 s network cap → it can never reach consensus, clear and create;
not found and inside the window → poll, never guess. Backstops where `entity_id` proves unavailable:
accounts by `?account.publickey=`, the token by the treasury's token list; topics have none, which is
exactly why the journal exists.

**Created but wrong → stop, exit 1, do not write the record entry.** Recording it would launder a
wrong entity into the ledger and every later run would call it `existing`. The journal is left in
place so a human sees the transaction ID and chooses: delete under the admin key and re-run, or amend
the declared policy.

Exit codes: 0 clean · 1 divergence · 2 blocked by an unmade ruling · 3 the probe was rejected by
testnet · 4 environment error before any transaction.

### The probe (step 05)

It settles ledger §H:343's open MINE — whether a fee collector must be associated with the
denominating token — and, under D-148, demonstrates the charged path **positively**.

1. Scratch topic, `adminKey = operator`, memo `wishmail:probe:hip991` (a scratch memo, never a
   WISHMail wire string), `CustomFixedFee` of 1 `$POSTAGE` collected by the treasury, and a **third
   throwaway key** on the fee-exempt list. First attempt without the treasury's signature; on
   `INVALID_SIGNATURE`, retry with it and record which attempt succeeded — that answers, as a side
   effect, whether a topic-fee collector must sign the create, which HIP-991 at the pin does not say.
2. `GET /topics/{probeId}` under `FRESH`. **Print the raw JSON** and record it, so
   `custom_fees.fixed_fees[0].{amount, denominating_token_id, collector_account_id}` and the
   fee-exempt list's actual field name and element shape become FETCHED rather than inferred — no
   recon in this repository has ever seen a topic that had one.
3. Exempt path: submit a one-byte message signed by the throwaway exempt key; read
   `GET /transactions/{txId}` and assert `assessed_custom_fees` is empty.
4. **The exempt list is amendable under the admin key.** `TopicUpdateTransaction` on the scratch
   topic under its admin key, replacing the exempt list with a *different* throwaway key;
   `GET /topics/{probeId}` under `FRESH` confirms the new list. This observes HIP-991 `:110-113` on
   testnet rather than reading it: the result goes into `probe.hip991` and into a dated ledger §H
   row. It is also the warrant for D-138's doorbell row standing as written — a null fee-schedule
   key freezes the fee, not the exempt list, so a P-8 rotation is met by the admin key the doorbell
   already has.
5. **Charged path, positive.** Create a scratch **stranger** account (throwaway key, minimally
   funded), associate it with `$POSTAGE`, and transfer it 1 `$POSTAGE` from the treasury, signed by
   the treasury. The stranger then submits to the probe topic **twice**: once with
   `setCustomFeeLimits` naming 1 `$POSTAGE`, once with no limit set. **Record both results verbatim**
   in the ops record and in ledger §H — whether HIP-991 charges or rejects an unlimited payer is
   unverified upstream and the doorbell path depends on the answer. On whichever succeeds, assert
   `assessed_custom_fees` shows amount 1, `token_id` = `$POSTAGE`, collector = the treasury, and
   print the raw JSON of both `/transactions` reads.
6. The stranger is recorded as `probe.stranger` and **is not deleted** — its token balance blocks
   `AccountDelete`, and the T-P7-4 fixture can reuse it. The scratch topic **is** deleted under its
   admin key, in a `finally`, on every path including the stop path.

**Stop condition.** If testnet rejects the fee configuration at step 1 on either attempt — for any
reason — **stop, exit 3, no HBAR substitute, do not proceed.** §4.4 admits no approximation. Print
the exact status name and the request as built (`tx.toString()` carries no key material).

The probe is idempotent like everything else; `--reprobe` forces a fresh one.

### Findings to report, not act on

- **`TopicMessageSubmitTransaction.freezeWith` always attaches `chunkInfo`, even for one chunk** —
  the loop runs at `s = 1` and sets `{total: 1, number: 1}`, cleared only after the signed
  transactions are built. §7.4 requires **no `chunkInfo`** on HCS-10 envelope chunks, so Phase C
  cannot use this class as-is for envelopes. This goes to **STATUS under the `HCS-10 by hand vs SDK`
  open item**. Report, do not act.
- **Every item on the design's "not verified" list becomes a ledger §H row**, dated from the probe
  run: the fee-exempt list's field name and shape; whether `GET /transactions/{id}` returns
  `entity_id`; whether `/tokens/{id}` returns `decimals` and `initial_supply` as strings or numbers;
  whether a fee collector or an exempt key must sign a topic create; the status returned when a
  submitter cannot pay; and which of `/accounts/{id}/tokens` or `/tokens/{id}/balances` the build
  uses, with the choice recorded in `app/OPERATIONS.md`.
