## Context

## The two divergences that forced rulings

**D-150 (spec change).** §4.6:578 has the Postmaster provision "the declaration registry and **profile file**," and D-146's `Conformance:` note at §4.6:585 requires *every* provisioned topic to carry the agent's key as its **admin** key. HCS-1 at the pin says the opposite of a file topic:

> "NOT include an Admin Key. HCS-1 Topics with an Admin Key will automatically be marked as invalid files, and will be ignored."
> — `docs/standards/hcs-1.md:48-49`, blob `0d8cca5…`, FETCHED recon 09-06, already recorded at ledger §H:360

So a conformant HCS-1 profile file cannot be a conformant provisioned topic. §H had the fact; nothing had noticed the collision. D-147's five-row template does not list the profile file at all, though §4.6 names it.

**D-151 (no spec change).** T-P1-5 requires an independent implementation to *open* what the reference sealed, which needs `skR` in `spec/vectors/seal.json`, exactly as RFC 9180 publishes `skRm`. `conformance/README.md:51` says "No private-key material in any fixture (P-13)"; P-13's own text at §12.2:1688 is narrower — no private key **of any agent**. The narrower reading binds.

## Phase B — the plumbing

### B1. Three rulings, in `app/OPERATIONS.md` beside the canonicalizer's

The section heading becomes **"Libraries, why each is a dependency rather than a few lines here — and the two things that are not."** Each ruling keeps the canonicalizer's paragraph shape: bolded lead, the normative hook with its sections and tests, the failure mode, then `[CC]` and the alternative considered. Two of the three reach the opposite conclusion, and that is the point of writing them in the same form.

**The seal is composed here, on `node:crypto` — RULED (Sonic, 2026-09-08).** This is the canonicalizer's argument with its conclusion reversed, and the reversal turns on one fact:

> **FETCHED 2026-09-08, rfc-editor.org/rfc/rfc9180.html.** Appendix A publishes base-mode vectors for seven ciphersuites — A.1 X25519/HKDF-SHA256/AES-128-GCM, A.2 X25519/…/ChaCha20Poly1305, A.3–A.5 P-256, A.6 P-521/HKDF-SHA512/AES-256-GCM, A.7 X25519 export-only. §7.3's DHKEM(X25519, HKDF-SHA256) / HKDF-SHA256 / **AES-256-GCM** (0x0020 / 0x0001 / 0x0002) is not among them.

The canonicalizer was a dependency because a subtly wrong composition fails **silently** and no official vector stands behind RFC 8785's edge cases. Here that hazard is answered by an official vector. §7.3's suite differs from **A.1** in one field of the key schedule's `suite_id` and one AES key length; run the same code parameterised to A.1 and it must reproduce every published A.1 value — `DeriveKeyPair`, `shared_secret`, `key_schedule_context`, `secret`, `key`, `base_nonce`, `exporter_secret`, and the seq-0 ciphertext. What A.1 cannot reach, `spec/vectors/seal.json` courts, opened by T-P1-5's independent implementation.

And the alternative was not neutral. **FETCHED 2026-09-08:** `@hpke/core` carries **CVE-2025-64767** — a race in the public `SenderContext.seal()` API that reuses the same AEAD nonce across calls, "complete loss of Confidentiality and Integrity," **CVSS 9.1 critical**, every version before 1.7.5 affected ([GitLab advisory](https://advisories.gitlab.com/pkg/npm/@hpke/core/CVE-2025-64767/)); and separately its issue #682, opened 2025-12-01 and closed 2026-01-04, reports `i2Osp` mishandling ≥32-bit integers so that computed nonces are non-interoperable and re-used at seq 2³². Two nonce defects in one library inside a year, in a single-maintainer project. **The ruling must not overstate:** neither would bite single-shot base mode at seq 0, which is all §7.3 uses. The argument is about where the hazard lives — nonce handling is exactly what the library's own history shows a library does not answer — not that this library would have broken our seal.

**The consequence, named rather than discovered.** `node:crypto` is not the browser. §14.2 fixes the WebMCP page as a *client* of the MCP server and never the resource server, and D-124 holds WebMCP unpinned by choice, so nothing shipping today seals or opens in a browser. An SDK that later runs in one ports the same eighty lines onto `crypto.subtle`, which exposes the same three primitives — X25519 `deriveBits`, HKDF, AES-GCM.

**The durable store is a few lines here, not a dependency.** §14.2 wants a record of settled payment references that survives a restart (T-P11-5, T-P11-6); it is tens of rows behind `WISHMAIL_STATE_DIR`, and `journal.ts` already established the discipline it needs — temp file, then `renameSync`, so a half-written file is never observed. `better-sqlite3` is a native build on Windows inside a five-day window and `node:sqlite` is experimental on Node 22: a build-toolchain risk taken for a keyed set that fits in a directory.

**`@modelcontextprotocol/sdk` is the one new dependency this step adds**, and it is the third ruling.

**`@modelcontextprotocol/sdk`, for the tool surface.** §14.2 makes the MCP server the x402 resource server that issues the `402` and must recognise the retry, so it needs a real HTTP transport, and MCP-B must speak to it. Not a pinned standard and not a conformance surface — D-124 holds WebMCP unpinned by choice — so the ruling says what it is and is not. Hand-rolling the framing is the hazard the canonicalizer's ruling names.

### B2. `app/src/schema/loader.ts` — one ajv registry

There is no loader today: `steps.ts::validatePriceList` reads one file, compiles a fresh `Ajv2020` per call, and resolves no `$ref`. Every schema declares draft 2020-12 and a URN `$id` (`urn:wishmail:0.5:<name>`), and **`evidence-bundle.schema.json` is the only one with cross-file `$ref`s** — five, by URN, to `envelope`, `postmark`, `settlement`, `return-receipt`, `attempted-delivery-slip` — so all fourteen must be `addSchema`'d into one instance before it compiles.

- `loadSchemas(repoRoot)` — read all fourteen, `addSchema` by `$id`, cache compiled validators by name.
- `validate(name, value): Discrepancy[]`-shaped errors, reusing `steps.ts`'s existing message form.
- `validatePriceList` is refactored onto it and must stay **behaviour-neutral**: the positive half, and D-145's negative half where `{...msg, validFrom}` is rejected by `additionalProperties`.

Reuse `env.ts::repoRoot()`, and the `ajv/dist/2020.js` + hand-unwrapped `ajv-formats` import idiom already in `steps.ts` (no `esModuleInterop`, `verbatimModuleSyntax` on, relative imports carry `.js`).

### B3. `app/src/core/` — the primitives, and the vectors

- `canonical.ts` — RFC 8785 + SHA-256; lifts `canonicalBytes` and `sha256hex` out of `steps.ts`, which then imports them.
- `aad.ts` — §7.2 exactly: `{p:"wishmail", v:"0.5", l, lane, rp, nc}`, canonicalized (RFC 8785 sorts to `l, lane, nc, p, rp, v`), SHA-256 as `id`. Plus the §5.6 rebuild — `hdr` + the arriving topic → the same bytes → the same `id`. D-127 is the seam: §7.2's short key names everywhere, never §5.5's long ones.
- `hpke.ts` — RFC 9180 base mode, single-shot, composed on `node:crypto` and **parameterised by ciphersuite** so A.1's parameters run through the same code. Three primitives: `generateKeyPairSync('x25519')` + `diffieHellman()`, `hkdfSync('sha256', …)`, `createCipheriv('aes-256-gcm', …)`. Around it, RFC 9180's own scaffolding — `I2OSP`, `LabeledExtract`/`LabeledExpand` over `"HPKE-v1" || suite_id || label`, DHKEM `Encap`/`Decap` with `kem_context = enc || pkRm`, `KeySchedule` at mode `0x00`, and `nonce = base_nonce` at seq 0. About eighty lines.
- `seal.ts` — §7.3 on top of it: `info` = ASCII `wishmail/0.5/seal`, aad = §7.2's bytes; `enc` → `ephemeralPub`, `SHA-256(ct)` → `ciphertextDigest`.
- `app/src/core/rfc9180-a1.json` + `npm run check:seal` — **the A.1 court**, transcribed from the RFC's Appendix A.1 base-mode section. The suite runs at `kem 0x0020 / kdf 0x0001 / aead 0x0001` and must reproduce `skEm`/`pkEm` from `ikmE`, `skRm`/`pkRm` from `ikmR`, `shared_secret`, `key_schedule_context`, `secret`, `key`, `base_nonce`, `exporter_secret`, and the seq-0 ciphertext. This lives in `app/`, **not** in `conformance/`, because the runner asserts `conformance/tests/` holds exactly the 83.
- `app/src/vectors/generate.ts` — writes both vector files.

**The one fiddly piece, named so it is not a surprise.** Node's `KeyObject` does not take raw 32-byte X25519 keys: a raw public half is wrapped in the X25519 SPKI DER prefix and a raw private half in the PKCS#8 prefix before `createPublicKey`/`createPrivateKey`, and raw bytes come back off the tail of a DER export. RFC 9180's `DeriveKeyPair(ikm)` — `LabeledExpand(LabeledExtract("", "dkp_prk", ikm), "sk", "", 32)` — needs exactly that raw→`KeyObject` path, and A.1 is what proves it right.

**The vectors are frozen from one run, not regenerated deterministically.** T-P1-5 wants "the reference seals and an independent implementation opens, and the reverse," and both directions work against a committed `enc`/`ct`. So `seal.json` carries `skRm`, `pkRm`, `info`, `aad`, `pt`, `enc`, `ct` — frozen — and the generator runs once.

Per **D-151**, `seal.json` declares in-file that its key material was born for the vector, is bound to no account, topic or epoch, and is no provisioned agent's key; the generator refuses any key that appears in `app/deployment/hedera-testnet.json`.

`aad.json` carries, per fixture: the header fields, the canonical AAD bytes (hex and as a string), and the `id`. Fixture lane/proof identifiers are well-formed and synthetic, and say so — no lane exists yet.

### B5. `app/src/release.ts` and `app/src/mcp/server.ts`

`release.ts` — `{ spec: '0.5.3', classes: [], profiles: {}, extensions: [] }`. §1.5:147: silence claims nothing.

`server.ts` registers the six tools of §6.1 — `resolve`, `buy_stamp`, `send`, `inbox`, `ack`, `verify` — each with an input and an output schema bound through B2's loader, each body returning `NOT_IMPLEMENTED` naming the T-IDs it will answer to (e.g. `send` → T-P7-1, T-P7-2, T-P7-3, T-P9-5, T-P10-1, T-P14-1). A build-time guard: a non-empty `release.classes` beside any `NOT_IMPLEMENTED` body is an error, so the scaffold cannot outlive a claim.

**Where the tool schemas live, and why not in `spec/schemas/`.** §18.5 fixes fourteen schema files by name; a fifteenth is a spec change, and §1.7 says a schema change without a spec change is not a change to WISHMail. The six tools' **inputs** are fixed by §6's signatures and are not §5 objects; `inbox`'s `Delivery` (§6.5) is prose with no schema either. So input schemas are a *release* artifact under `app/src/mcp/schemas/`, `$id` `urn:wishmail:app:0.5:tool:<name>:input`, `$ref`ing the spec URNs through the same ajv instance — which is what T-P15-4 is about ("the tool schemas served by every transport in the release"), a property of the release and not of the specification. Outputs bind straight to the spec URNs: `resolve` → `mail-coordinates`, `buy_stamp` → `stamp-receipt`, `send` → `postmark` | `attempted-delivery-slip`, `ack` → `return-receipt`, `verify` → `evidence-bundle` (+ `narrative`).

### B7. The P-13 gate widens

`scripts/p13-check.mjs` watches `/(AGENT|TREASURY)_DER_KEY/`. The declaration needs the agent's **X25519 encryption key**, and `AGENT_X25519_DER_KEY` slips straight past that regex. Widen to `/(AGENT|TREASURY)[A-Z0-9_]*_KEY/` — still not matching `POSTMASTER_PAYER_DER_KEY`, which the module comment deliberately permits — and give the X25519 key the same shape as the account keys: read only in `env.ts`, held only in `identity.ts` behind a `sealIdentity()` that returns a public half and an `open`, never the private key.

**The one remaining unknown, and it must be closed by a FETCH before anything is signed.** HCS-11 requires `uaid`, and computing one means HCS-14 at the pin (`docs/standards/hcs-14/index.md`, blob `969de3aa…`, split into `index.md` plus five profile files). §H:367 records the algorithm second-hand from `standards-sdk` — `base58btc(sha384(canonical JSON of skills, name, nativeId, protocol, registry, version))`, `nativeId` inside the hash and `uid` outside, parameters ordered `uid, registry, proto, nativeId, domain`, `uid` = `inboundTopicId@accountId`. CLAUDE.md §3 forbids asserting a Draft standard from anything but the blob. So: fetch at the pin, file the fetch in §H with its date, and **verify by recomputing the two live agents' UAIDs the recon already checked** — if ours reproduces theirs, the implementation is right.
