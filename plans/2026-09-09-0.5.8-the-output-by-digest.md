## The finding, and why neither candidate was the answer

A manifest must be one HCS message at or under `CHUNK_WIRE_MAX` = 1000 (§9.1, T-P9-8). §5.2 requires a `meaning.statement` and bounded it nowhere. At a real 168-character UAID the manifest did not fit — only our own demo's shape did, by three bytes.

**Raising §9.1's ceiling** buys 24 bytes. Verified rather than assumed: `@hashgraph/sdk` 2.81.0 sets `CHUNK_SIZE = 1024`, and `getRequiredChunks()` returns 1 at 1024 bytes and 2 at 1025. Past 1024 the only route is `chunkInfo`, which splits one logical message across several consensus messages — and that would cost D-96's one-message-one-locator discipline, D-163's location-by-hash lookup, and §7.4's own prohibition on `chunkInfo` for envelope chunks.

**Bounding `statement` alone** never reached `dns` and `nanda`, which MUST carry a snapshot (§9.1's table, T-P6-2).

## The ruling

The coordinates **value** inside `output` was spending the budget, and §5.2 already gave the shape as `{digest} | value`. The resolution proof carries the digest and never the value; a Verifier recovers the coordinates by the replay §11.4 already required of it and compares the digest. §9.1 then states the arithmetic and `proof.schema.json` bounds `meaning.statement` at **N = 70**.

## What the ruling forced, and what it cost

Neither of these was in the prompt, and both are consequences rather than choices:

1. **§9.2's locator gains `address`.** Its list did not name the rule's own first input. Harmless while a Verifier could read the address out of the output; fatal once the output is a digest. It also moves a UAID's 168 bytes from `output` into `inputs.locator`, so the net saving is about 110 bytes, not the ~290 a naive reading suggests.

2. **`verify`'s replay had to become real.** It stopped at the registry entry, because §9.2's rule was written against a mirror-node client and a Verifier's `Reader` could not reach the profile file. The module said so in a comment and appraised on a partial replay anyway. Under this ruling that is no longer a shortcut — the value is recoverable only by running the rule to the end — so the rule now runs over a `ProfileSource`: three reads of public data that both ports satisfy. **One rule, two readers.** And the letter fixture, which had created a profile-file topic and never written a profile into it, now stands up a real HCS-1 file. Nothing had ever read that far, so nothing had ever said it was empty.

## Where the prompt's words could not be followed literally

The ruling says the digest is "the SHA-256 of the canonical JSON of the MailCoordinates". Taken literally that is circular: MailCoordinates carries `resolutionProof.hash`, which is computed *over* the output. The digest is over the **resolved fields** — §5.3 minus `resolutionProof`, minus `trustClass` and `endorsements` (which live in `meaning`), minus `resolvedAt` (the query's clock, which no later replay reproduces). That is the ruling's substance exactly, and it is the split the code already had. Recorded in D-167 rather than silently applied.

## What still does not fit

`nanda` at its longest address is **1042 bytes, 42 over**. §9.1's retained fallback carries it, and what that costs is stated rather than hidden: a proof whose snapshot travels as a digest is replayable only while its source stands, and §9.4 says a nanda answer's source never stands. Such a proof is witnessed rather than replayable — which its permanent `blurred` already declares and which §11.4 appraises as unverified. No schema moves for it; `nanda` is not on the letter path this window.
