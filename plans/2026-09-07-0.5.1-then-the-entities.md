## Context

Two phases in one window, in this order, because the second depends on the first.

**0.5.1 comes first.** The pinned HIP-991 text is upstream of every doorbell decision — the fee
configuration must be built against the fetched sentences, not against our own prior inference —
and the T-P7-4 and T-P17-1 amendments change what provisioning must produce. §1.7 makes the window
real: *"A patch revision amends text and tests within a minor version; it changes no wire string,
and once a minor version's schemas are registered it changes no schema."* Nothing is registered
under HCS-13 — T-P9-9's digests are null — so schema-touching corrections are patch-level **now**
and become 0.6 after registration. Land them here.

**Then the entities.** `spec/pins.json` carries 32 nulls and T-P9-2 refuses a report while any pin
is unfilled, so nothing can be claimed until `$POSTAGE` exists. §14.3's MUST gates the rest:
publish a price message before charging under it, and `buy_stamp` becomes legal later.

Infrastructure only. The six-tool surface is downstream, and `HCS-10 by hand vs SDK` stays open —
it governs the operation grammar that carries envelopes, not the creation of a token or a topic.

**The through-line.** Items 1, 6 and 8 resolve into which keys exist at birth. Because we are
dogfooding, that policy becomes the template every provisioned agent inherits (§4.6). It is stated
**once**, as a table, in D-138, and everything else points at it.

### D-136 — rate-priced methods, one decision in three places (items 3, 4, 5)

It reads cleanly as one: how a rate-priced method is **priced** (§14.3's shape), **quoted**
(decimal strings), and **receipted** (§5.4). One D-number, three CHANGED sites.

**§5.4 — `StampReceipt` gains `rate`.** Draft:

```
StampReceipt                            Settlement (observed)
  ledgerTag     string                    ledgerTag           string
  tokenId       string                    txRef               string   settlement reference
  amount        integer   stamps bought   from                string   the sender's account
  txRef         string    the purchase    to                  string   the treasury
  price         {amount, currency}        amount              integer  stamps affixed
  rate?         {source, pair,            memo                string   "wishmail:" + aadHash
                 value, at}               consensusTimestamp  timestamp
  holder        string    account or
                          public-key alias
```

with a sentence after the block: *"`rate` is present exactly when the method that bought these
stamps is priced by reference (§14.3): `value` is the rate the Postmaster read and `at` is when it
read it."* Blast radius is confined to `buy_stamp`'s output — §14.2 puts the purchase off the
record ("WISHMail records postage spent, not postage bought"), so no Verifier path, no AAD, no
evidence bundle, no observed object.

**§14.3 — the shape.** `unitPrice` becomes optional and gains a sibling:

```
methods        [{method, network, asset, payTo? , facilitator?,
                 unitPrice? | rate? {source, pair, reference {amount, asset}},
                 bundles? [{count, price}]}]
```

**§14.3 — the prose** replacing `:1798`. Draft:

> `unitPrice` is the price of one stamp in the method's asset, written as a decimal string in that
> asset's natural unit — not in atomic units, which bake a network's decimals into a document a
> Verifier reads, and not as a JSON number, because the message is canonicalized (RFC 8785) and a
> float is a hazard. A bundle is a price for a count, offered to everyone alike. A method priced by
> reference to another asset carries `rate` in place of `unitPrice`: `reference` is the price of
> one stamp in the reference asset, and `source` and `pair` name what the Postmaster reads at
> purchase to convert it into the amount it quotes. A method carries `unitPrice` or `rate`, never
> both. **A bundle's price follows its method's pricing basis** — the method's own asset where the
> method is fixed-priced, the reference asset where it is rate-priced — so that the rate converts a
> bundle at purchase exactly as it converts `reference`. The buyer signs that amount and no other,
> the quote stands for the transaction's valid duration, and the receipt records the rate used and
> when (§5.4). Every number is the Postmaster's; this document fixes that there is one schedule,
> that it is on consensus before it is charged, and that it is the same for everyone (§4.5).

**The two pipes in §14.3 are read differently, and the ADR says why** (RECORD). `payTo |
facilitator` is **inclusive**: §14.2:1766 has the `PAYMENT-REQUIRED` carry "the Postmaster's
receiving address" — which *is* `payTo` — so an x402 method needs it *alongside* `facilitator`, not
instead of it. `unitPrice | rate` is **exclusive**: a method priced two ways publishes a number
nobody charges. So `price-list.schema.json` carries
`allOf: [ {anyOf: [required payTo, required facilitator]}, {oneOf: [required unitPrice, required rate]} ]`.
This corrects the `oneOf` I wrote for `payTo`/`facilitator` at the outfitting, which over-read the
pipe.

**Bundles apply to both methods** (RECORD): twelve for $1.00 on `x402-usdc` and on `hbar`. Under
the basis rule the `hbar` bundle reads "12 for 1.00 USD" and converts at purchase. T-P11-4's bundle
branch — "a bundle's price at its count" — already covers both cases once the rate applies to it,
so no test amendment.

**Why not a publication-time snapshot** (recorded as the rejected alternative): a rate-priced
method carrying `unitPrice` publishes a number nobody charges, which §14.3's own MUST forbids —
"MUST charge exactly what the price message current at the purchase yields."

**T-P11-4 needs no amendment, and that is the point.** Its sketch already reads "`count ×
unitPrice`, a bundle's price at its count, or the referenced rate applied to the reference price."
The third branch named a field that did not exist; `rate.reference` gives it a home, so three
branches now map to three fields exactly. The ADR records this as the test becoming true rather
than being changed.

**Schemas follow** (`spec/schemas/`, per §1.7 a patch while nothing is registered):
`stamp-receipt.schema.json` gains optional `rate {source, pair, value, at}` and drops the `$comment`
raising the gap, which this closes. `price-list.schema.json` moves `unitPrice` out of `required`,
relaxes the `payTo`/`facilitator` constraint from `oneOf` to `anyOf`, adds the exclusive
`unitPrice`/`rate` constraint, and gives `rate` its `reference {amount, asset}`. `$id` stays
`urn:wishmail:0.5:…` — a patch changes no wire string.

- **No submit key on the doorbell, submit key on the log** — the pinned blob's own table, not

- **TTL `60`, a deployment fact, not spec** (item 7). WISHMail reads no TTL and §9.5 makes the memo

**D-139.** §3.5:466 — "A submission to a lane, doorbell, or log MUST be signed by the key that
governs that topic, which is the agent's." On a doorbell with no submit key, no key governs it; the
sentence is vacuous there. The only coherent reading is that "the agent" is the *submitting* agent
— the sender signs its own ring — and the fee does the governing a key does elsewhere. T-P2-1 tests
lanes only, so nothing breaks. No spec change; the reading goes on the record so the ambiguity is
explainable with the agent closed.

**D-140 — accounts.** Three roles, three accounts, distinct keys.

- **Operator/payer** — `0.0.8641261`, reused (RECORD). Pays network fees for what the Postmaster
  carries and provisions (§14.1); `payTo` for the HBAR leg (§14.2); momentary bearer of the
  first-contact stamp (§4.4); **and the price topic's submit key** (D-142). Notes the 17 colour
  tokens and USDC from prior work as residue — "Start Fresh" binds code, not accounts.
- **Treasury** — new account, own key. Holds unissued `$POSTAGE`; receives affixed postage (§4.3),
  doorbell fees (§4.4), the receipt fee inside postage (§14.1). **Its key is hot** — it signs the
  stamp leg of every `buy_stamp` (§14.2). The split is containment and accounting, not cold
  custody; say so.
- **Postmaster-agent** — new account, own key, the service's own Correspondent identity.

States in so many words: this identity is an operational choice, not a spec role. §4.6's "an agent
needs an account, a doorbell, a log, a manifest topic" is written of an *agent*; §1.4 gives
POSTMASTER only "the service side of `buy_stamp`, `send`, `verify`" — no `inbox`, no `ack`, no
profile obligation — so it is a second class claim (§1.4: "An implementation MAY claim more than
one class"). P-13 is not violated because this agent is the org's own, not a customer's. **The form
the build must honour:** T-P13-1 tests that *the service's key store and code path* contain no
agent private-key material, so the agent's key lives under an `AGENT_*` namespace in `.env` the
Postmaster service never reads, and the provisioning script does not special-case its own agent.

**D-141 — `$POSTAGE`.** Fungible HTS, treasury = the treasury account, supply key held by the
Postmaster (§4.1, §3.5, D-44, now citing `hip-991.md:88` rather than inferring it).

- `decimals: 0` — **forced, not merely argued** (RECORD, the sharper reason). A HIP-991 fixed fee is
  written in *base units*, so §4.4's "a HIP-991 custom fee of exactly one stamp" is literally one
  unit only at `decimals: 0`. At any other value the normative sentence and the on-ledger fee
  diverge. The softer arguments still hold beside it: `weight = max(1, ceil(…))`, and
  `StampReceipt.amount` is `integer, minimum 1`.
- `initialSupply: 0`, `supplyType: INFINITE`, mint-on-demand. §4.3 permits burning consumed stamps
  and L-12 says this release burns nothing, so supply grows; a pre-mint invents a number.
- **Keys: supply only.** No admin, freeze, wipe, pause, KYC or fee-schedule key. Against P-2 and
  L-12: an admin key would let the Postmaster mutate the token a Verifier measures against; wipe or
  freeze would let it reach into a holder's account and unmake postage already paid.
- **The tail, stated plainly and stopped** (RECORD). With no admin key the token's treasury can
  never be changed, so loss of the treasury key is terminal for the deployment. On testnet that is
  a rebuild, and this BUILD accepts it. A mainnet deployment would need a custody procedure this
  ADR does not supply. No procedure, no on-ledger recovery path, deliberately — mainnet is out of
  scope for this BUILD and in scope for the spec.

**D-142 — the price topic's submit key is the operator key** (item 8, RECORD). The price list is
the service speaking, so its submit key is the service's signing identity — not the treasury (a
pool, hot for a different reason) and not the Postmaster-agent (a Correspondent with its own
topics). Admin key likewise the operator's. Does not disturb D-101, which fixed *that* the submit
key is the Postmaster's sole key without saying which; §19.3's Q-7 stays open unchanged, since it
asks how the supply key and this key **change hands** — handover, not birth.

**Tooling rule — SETTLED 2026-09-07, superseding the conditional rule this plan first carried.**
Every transaction is `@hashgraph/sdk`; every read is mirror-node REST. `hedera-testnet-mcp` is

`hedera-docs` is used freely for design questions; what it returns is FETCHED, cited with the
document named, and never a source the spec cites without a pin. Full statement in STATUS §5,
