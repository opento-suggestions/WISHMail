## Context

HCS-14 at the pin — `docs/standards/hcs-14/index.md`, blob
`969de3aa2fccaea10f50165f82620ae6172b017d` at commit `7046156c`, verified with
`git hash-object` against §1.6 — fixes the key order of the canonical JSON an
agent identifier is hashed from **twice, and differently**.

Its step 3, in a list the document introduces with "the following steps are
normative; implementations shall perform steps 1–6", says:

> "3. **Sort** capabilities numerically and object keys lexicographically"
> — `index.md:541`

and its reference function does exactly that:

> `const sortedJson = JSON.stringify(canonical, Object.keys(canonical).sort());`
> — `index.md:585`

But the worked example in the same document, Test Vector 1's "Canonical JSON"
block, places `skills` first and the remaining five alphabetically
(`index.md:697-706`), and Test Vector 2 does the same (`:727-736`). The two
serializations are different bytes, so they are different SHA-384 digests and
different identifiers for the same agent.

Nothing in the document decides between them, because its test vectors publish
the expected identifier as the literal placeholder `uaid:aid:{base58hash};…`
(`:709`, `:739`). So the standard courts neither reading, and the contradiction
cannot be found by reading it.

It was found by recomputation against the ledger (2026-09-08, Claude Code), and
Sonic asked for a census before ruling. FETCHED the same day, mirror-node REST
only, recorded in ledger §H:

- the testnet anchor `0.0.6913983` carries 380 messages, 366 with a `uaid:aid:`,
  spanning 2025-10-07 to 2025-11-18;
- `0.0.7124407` registered at sequence 153, **2025-10-24T22:10:46Z**,
  `proto=hcs-10`, `registry=hol`, skills `[0,4]`;
- the newest `uaid:aid:` is sequence 380, **2025-11-18T22:05:58Z**,
  `proto=a2a`, `registry=hashgraph-online`, skills `[0]`;
- **both reproduce under the example order and neither under the normative one**;
- across the fourteen newest plus `0.0.7124407`: **15 of 15 example, 0 normative,
  0 neither**, every profile readable and every HCS-1 memo digest matching.

## Decision

Ruled by Sonic, 2026-09-08, and deliberately ruled **before and independently of**
§G-12: whichever order WISHMail emits for its own declaration, the orders it
*accepts* when reading another agent's registration are both.

§9.1 gains the rule:

> A rule that recomputes an agent identifier MUST compute it under the
> lexicographic order first and, where that does not equal the identifier
> compared against, under the example's order; MUST treat a match under either
> as agreement; and MUST NOT treat a match under one as weaker than a match
> under the other. A Verifier MUST report which order matched, under
> `observations` (§11.6).
> `Conformance:` T-P6-3, T-P6-5

§9.2's and §9.5's identifier comparisons point at it. §5.10's `observations`
gains `agentIdOrder[]` and §11.6 the paragraph that says what it is: one entry
per address compared, each naming the address and the order that matched.

**The normative order is tried first**, and that ordering is the substance
rather than a detail: it makes the second a fallback rather than a preference,
so that if the upstream defect is ever fixed (§G.5b) this implementation is
already computing the fixed answer first and the fallback simply stops firing.

**Reporting it as an observation, and only as an observation**, is what keeps it
from touching anything. §11.6's observations are excluded from the evidence
digest and bear on no state or standing, so two Verifiers that read the same
registration agree on the bundle byte for byte whatever they report here (P-3),
and no appraisal moves because of it (P-12). A match under either order is
agreement; neither is weaker; the endorsement a profile's rule assigns is
unchanged.

## Alternatives considered

- **Accept only the example order**, since it is the only one deployed. Rejected:
  it would make this implementation wrong the moment the standard is fixed, and
  it discards the distinction the observation preserves.
- **Accept only the normative order.** Rejected: it makes every agent currently
  on the ledger unresolvable, which is P-5's registry-plurality in name only.
- **Accept both and report nothing.** Rejected: the fact that an incumbent is
  registered under the order the standard does not bless is worth a reader
  knowing, and §11.6 is exactly the place for a fact that must not change a
  standing. MINE; Sonic's instruction named `observations` directly.
- **Report it as an endorsement on the coordinates.** Rejected outright: §5.3's
  endorsements are a fixed enum and they move standings (P-12). This must not.

## Consequences

**A patch, 0.5.4.** No wire string moves — `v` stays `0.5`, the HPKE `info`
stays `wishmail/0.5/seal`, `schemaRef` stays at the minor version — and nothing
conforms, since T-P9-2 blocks every claim while thirty pins are null. No test is
added, moved or removed; the register stays 83 (78 core + 5 extension).

`spec/schemas/evidence-bundle.schema.json` gains
`observations.agentIdOrder`. A patch permits a schema change **only because
nothing is registered under HCS-13 yet** (`registeredSchemas` is null throughout,
T-P9-9); after registration the same addition would be 0.6. `observations` was
already open — it carries no `additionalProperties: false` — so the schema did
not forbid the field; what needed the change was §5.10's shape block, which
enumerates the fields a reader will look for.

**§A's T-P6-3 and T-P6-5 sketches gain one legacy-order fixture agent each.**
That is an expansion of a test's scope, which CLAUDE.md §4 makes a decision
rather than an edit, and this is that decision. Both fixtures must resolve, must
carry the endorsements their rule assigns and no others — a legacy-order match
is not a reason for `blurred` — and must produce an `observations.agentIdOrder`
entry naming the order.

`app/src/core/hcs14.ts` carries `matchAgentId`, which is the rule; both live
agents are vectors in `npm run check:hcs14`.

**What this does not settle:** which order WISHMail emits for its own
declaration. That is ledger §G item 12 and it is still open, because an HCS-1
file topic has no admin key and the choice is baked into an undeletable topic.
`CANONICAL_ORDER` stays `undefined` and every caller names an order.

The defect is drafted for upstream submission as ledger §G.5 item (b), and
LIMITATIONS L-7 carries the line a reader of this release needs.
