# D-154 — An undeployed ledger tag has no pin

Status:      accepted
Date:        2026-09-08
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    none — no specification sentence changes
Tests:       T-P9-2 — sketch unchanged; the count it reads falls from 30 to 28
Supersedes:  none
Spec marker: none

## Context

`spec/pins.json` is §1.6's and §18.4's machine-readable form, and its own
`_readme` states the rule T-P9-2 enforces: "A value of null is an UNFILLED pin:
the conformance suite refuses to produce a report while any pin here is null."

`stampToken` carried an entry per ledger tag rather than per deployment:

```json
"hedera:testnet": { "tokenId": "0.0.10426208", "treasury": "0.0.10426205" },
"hedera:mainnet": { "tokenId": null, "treasury": null }
```

Those two nulls were counted among the thirty that block every claim. But they
are not pins this deployment owes. §15.5 leaves `hedera:mainnet` defined and
undeployed; §4.1 fills a stamp token "at the first deployment on a network"; and
there is no first deployment on a network this version does not deploy to. The
nulls were reporting a debt that could not be paid and was not owed, and they
made the blocking count wrong in a way that mattered: a reader counting thirty
would look for two acts that no one is going to perform.

## Decision

**`stampToken` carries an entry per DEPLOYED ledger tag, and no entry at all for
a tag that names no deployment.** `hedera:mainnet` is **removed**, not set to a
sentinel. When it is deployed, its entry is added and filled in the same act.

`ledgerTags` is unchanged and still names both: §5.1 defines exactly two tags
whether or not either is deployed, an envelope naming any other is refused
(T-P9-11), and a claim is scoped to what it names (§1.5). What a ledger *is* and
what this deployment *has done on it* are different facts, and only the second
belongs in `stampToken`.

`unfilledPins()` counts what remains: **28**, the `registeredSchemas` entries,
two per schema for fourteen schemas. T-P9-2 still refuses a report, and now for
the one reason that is true.

The `_note` says why, at the place a reader meets the absence, so that a missing
key is not read as an omission.

## Alternatives considered

- **A sentinel — `"undeployed"`, or `false`, in place of the nulls.** Rejected,
  and this is the whole of it: a sentinel is a value standing for the absence of
  a value, which is the thing that was wrong. It would also have to be taught to
  `countNulls`, so the rule "a null is an unfilled pin" would acquire an
  exception, and the next reader would have to learn both.
- **Leave the nulls and subtract two wherever the count is reported.** Rejected:
  the count would then be right only where someone remembered to correct it, and
  `unfilledPins()` is read by the conformance runner, which is not a place for a
  remembered correction.
- **Remove `hedera:mainnet` from `ledgerTags` too.** Rejected: it would make
  §5.1's second defined tag invisible in the file that records §1.6, and
  T-P9-11's refusal of an *undefined* tag turns on the difference between a tag
  the specification defines and one it does not.

## Consequences

No specification sentence changes. §18.4 says the pins file carries "the stamp
token and treasury per network", and a network §15.5 leaves undeployed has no
network to be per; the sentence has no referent there, so nothing about it needs
amending. T-P9-2's sketch is unchanged — "the suite refuses to produce a report
while `spec/pins.json` … contains an unfilled pin" — and what changed is how many
there are.

The version stays **0.5.4**: no sentence, no schema, no test.

Everywhere the count is quoted moves from thirty to twenty-eight:
`conformance/README.md`, `STATUS.md`, the ledger's HOW TO RESUME line, and the
harness's own output. The harness line is now `NO REPORT — 28 unfilled pins in
spec/pins.json (T-P9-2)`.

The ledger's HOW TO RESUME still said "The stamp token pin fills at first testnet
deployment; until then T-P9-2 keeps the version unclaimable." It filled on
2026-09-08. Corrected in the same change, because a resume note that is stale
about what has already happened is worse than no note.
