Decided by:  Sonic
Drafted by:  Claude Code

Tests:       T-P11-4 — not amended; it already keys on the consensus timestamp
Supersedes:  none

## Context

Writing D-143 — the first price list — stopped on a field that could not be filled. `spec/schemas/price-list.schema.json` **required** `validFrom` and typed it as a consensus timestamp, `^[0-9]+\.[0-9]+$`. The specification mentioned it exactly once in 2,238 lines: a line in §14.3's shape block at `:1805`.

```
  provisioning?  {method, unitPrice}         the provisioned path (§4.6), if offered
  validFrom      timestamp
```

No prose sentence defined it. No MUST referenced it. No `Conformance:` note named it. No ledger row and no ADR discussed it. A required field that nothing reads is already a defect; this one was also unfillable. **A message's bytes are fixed before consensus assigns it a timestamp**, so a `PriceList` cannot carry its own — the publisher would have to know, at submission, a value the network assigns afterwards.

And §14.3 already answers the question `validFrom` looks like it answers. `:1794`:

> The price current at a purchase is the latest price message with a consensus timestamp before the purchase's; the Postmaster reads it from a mirror node at every purchase, and a Verifier reads the same message to check what was charged.

T-P11-4 tests against that same clock — "the price message current at the receipt's consensus timestamp". So the effective-date question is settled, on consensus, by the ledger's own ordering, and any meaning given to `validFrom` would be a second and competing notion of when a schedule begins.

Raised rather than patched as ledger §G item 9 (Claude Code, 2026-09-07, MINE), with publication of the first price list held until it was ruled.

## Decision

**`validFrom` is dropped** (RECORD, Sonic 2026-09-08).

The line is deleted from §14.3's shape block. `spec/schemas/price-list.schema.json` drops it from `required` **and** from `properties`: the schema carries `"additionalProperties": false`, so leaving the property defined but unrequired would keep publishable a field that no rule reads and no Verifier checks — the defect in a quieter form rather than its removal.

§14.3's reading rule is untouched and is now the only notion of effect in the document. T-P11-4 is not amended: it already tests the rule that survives.

### Why this is a patch and not 0.6

§1.7 fixes that a patch "changes no wire string, and once a minor version's schemas are registered it changes no schema." `registeredSchemas` in `spec/pins.json` is null throughout — all 28 entries — so nothing is registered and a schema correction is patch-level **now**. After HCS-13 registration the identical correction is 0.6. No wire string moves: `$id` stays `urn:wishmail:0.5:price-list`, the AAD's `v` stays `0.5`, the HPKE `info` stays `wishmail/0.5/seal`.

Nothing on consensus is invalidated, because no `PriceList` has ever been published on any network.

## Alternatives considered

- **Give it effective-from semantics** — the earliest purchase the schedule may price, letting a price change be published ahead of its effect. The most useful reading, and the one worth revisiting in a later minor version. Rejected here: it needs new normative prose, and T-P11-4 must then say which clock governs when `validFrom` and consensus order disagree. A patch window opened to fix an undefined field is the wrong place to add a scheduling feature.
- **Keep it, define it as informational, make it optional** — the Postmaster's own clock at submission. Rejected: honest about the ordering problem and it would unblock publication, but it leaves a field in a consensus document that no rule reads, which is the condition that produced this ADR.
- **Leave it and publish something plausible.** Rejected under CLAUDE.md §5: coding around a sentence the specification does not have is the thing that rule forbids.

## Consequences

§14.3's `PriceList` shape is nine lines and every one of them is read by a sentence of the document. D-143's first price list is unblocked and carries no `validFrom`; its `spec` field publishes as `"0.5.2"`.

`spec/schemas/price-list.schema.json` is the only schema this patch touches, which the Phase A′ gate confirms. The gate also checks the constraint in both directions: the exact first `PriceList` validates, and the same message **with** `validFrom` is now rejected by `additionalProperties: false`.

Ledger §G item 9 is closed. The register stays 83 (78 core + 5 extension) and the extract-and-diff passes both ways.
