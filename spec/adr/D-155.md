## Context

Step 4 registers §18.5's fourteen schemas under HCS-13. Two questions had to be
settled before it could be built, and the instruction that reached the build was
wrong about the first.

**The instruction described one shared HCS-2 registry topic** carrying a
`register` per schema, with `hcs://13/<registry>#<seq>` as the `schemaRef`.
**RECORD (Sonic, 2026-09-08): that shape was Claude's error, not Sonic's**, and
this decision says so rather than leaving the record to imply otherwise. Claude
Code cannot find where it entered — it is in neither the approved plan nor
anything written into the repository — so the attribution is recorded on Sonic's
word and the trail is not reconstructed.

The build diverged from it rather than taking it, and raised it in the gate
report instead (CLAUDE.md §5). What the pinned text says, FETCHED 2026-09-08 at
blob `07f1ac67b344d6655b98ce8196b3053fe1b4f566`, verified with `git hash-object`:

> "1. Create an HCS-1 file containing the JSON Schema definition
> 2. **Create an HCS-2 topic to manage versions of the schema**
> 3. Register the HCS-1 file in the HCS-2 topic using the register operation"
> — `hcs-13.md:136-140`

> "`topicId` is the topic ID of the HCS-2 topic managing **the schema**. …
> `hcs://13/0.0.123456#42` — References **version 42 of the schema**"
> — `hcs-13.md:230-241`

and §5.11 says the same in this document's words: "each as an HCS-1 file
registered on an HCS-2 topic that manages **the schema's** versions", with the
sequence number "that of the register operation **for the version claimed**".

The second question was whether to also register in HCS-13's **schema discovery
registry** under `p: "hcs-13"`.

## Decision

**One HCS-2 topic per schema.** Fourteen file topics, fourteen registry topics,
fourteen register operations. Ratified by Sonic 2026-09-08.

**No discovery registration.** The pin describes that registry as one that
"enables discoverability of schemas across the Hedera ecosystem" and "allows
developers to publish their schemas and make them available for others to use"
(`hcs-13.md:183`). Nothing in resolution reads it: a `schemaRef` dereferences
through the schema's own HCS-2 topic, and §9.7 — "Discovery is not resolution" —
and P-6 — a directory is "an input, never an authority" — settle what it would
be worth to us. The condition given was "if the pin requires it and not
otherwise"; it does not require it.

## Why the shape matters, and it is not fourteen topics' worth of tidiness

On a shared registry, `#42` names the forty-second registration of **anything**
— a different schema, not a later version of one. The fragment stops meaning
"version", which is the only thing §5.11 says it means, and the unpinned form
`hcs://13/<topicId>`, which §5.11 says "names whatever version is latest", names
nothing at all.

A reader dereferencing a `schemaRef` would still reach the right file, because
`t_id` is in the message — so the error would not have shown up in any test that
resolved one reference. It would have shown up the first time a single schema
was rotated to a second version, at which point the two registrations of that
schema sit at arbitrary sequence numbers with thirteen other schemas' between
them, and nothing in the topic says which pair belongs together.

That is the same failure mode as the profile-version defect of Step 3: a
structure that validates, dereferences, and is internally consistent, while
being unreadable by the rule it exists for. The cost of the shape chosen is
fourteen extra topics. The cost of the other was a locator that does not mean
what two documents say it means.

## Alternatives considered

- **One shared registry** — the instruction's shape. Lost on the above; and see
  the Context for whose it was.
- **One shared registry with the schema name in `metadata`, disambiguating by
  name rather than by topic.** Rejected: it makes `schemaRef` insufficient on
  its own, since a reader would have to fetch and inspect `metadata` to know
  which schema a reference is even about, and §5.11 gives `schemaRef` as the
  whole reference.
- **Register in the discovery registry as well, for reach.** Rejected on §9.7
  and P-6, and on the plainer ground that WISHMail is not a registry broker
  (CLAUDE.md §3): publishing to a directory nothing in this specification reads
  would be a claim about discoverability we do not make.

## Consequences

No specification sentence changes — §5.11 already required this, and the
decision records that the build now matches it. No schema, no test, no version
change: still **0.5.4**.

Step 4 stands as built: 56 steps, 14 file topics (no admin key, D-150), 14
registry topics under the operator's keys with memo `hcs-2:0:60`, 31 chunk
messages, 14 register operations. It remains **unsigned**, because §1.7's freeze
is held until the six tool bodies pass their fixtures — that condition is
unchanged by this decision and is stated in the gate report.

The `indexed` flag stays `0`. With one topic per schema and a `schemaRef` pinned
to a sequence number, every prior version must remain readable at its own
number; indexed `1` would make only the last message state and orphan every
earlier reference.
