# D-144 — `spec/pins.json` takes only what §18.4 enumerates; every other deployment fact goes to the ops record

## Context

Provisioning produces roughly a dozen durable facts: three account IDs, a token ID, a price topic ID, the sequence number of the first price message, the Postmaster-agent's doorbell, log and manifest topics, the HCS-10 memo TTL, and a creation transaction ID and consensus timestamp for each. They have to live somewhere reproducible. `spec/pins.json` is the obvious candidate and the wrong one for most of them.

§18.4 enumerates that file's contents exactly:

> §1.6 is the appendix of record for pins, and `spec/pins.json` is its machine-readable form: for each pinned standard, `{repo, commit, path, blobSha, sha256}`; for the stamp token, `{ledgerTag, tokenId, treasury}` per network (§4.1); for the minor version, the registered schema digests and wire strings (§1.7). The suite reads `spec/pins.json` and refuses to report while any pin is unfilled (T-P9-2).

Three kinds of thing, and no fourth. D-132 already applied this once, keeping the x402 facilitator out of pins and putting it in the price list and `LIMITATIONS.md` where the specification actually names it.

## Decision

**`spec/pins.json` gets exactly what §18.4 names and nothing else** (RECORD, Sonic 2026-09-07). From this phase that is one addition: `stampToken["hedera:testnet"] = {tokenId, treasury}`, plus the two HIP pins already landed by D-135.

**Everything else goes to `app/deployment/hedera-testnet.json`** — the ops record, which is also the provisioning script's idempotency ledger: the three accounts by role, the token, the price topic, the first price message's sequence number, the Postmaster-agent's doorbell, log and manifest topics, the HCS-10 memo TTL with its recon citation (D-138), and for each entity its creation transaction ID and consensus timestamp.

**`app/OPERATIONS.md` carries the method** — what was created, in what order, by which path, which key signed it, which mirror-node read confirmed it, and every DIVERGENCE from the tool a reader would expect.

**The price topic has a third home and it is not pins.** §5.10 and §14.3 put it in the conformance claim as `prices {ledgerTag, topicId}`, which is where a Verifier looks for it. A fact the specification gives a home to does not need a second one.

### Why the line is drawn there

T-P9-2 is the reason this is not bookkeeping. The suite **refuses to report while any pin is unfilled**, so every entry in `spec/pins.json` is a gate on every conformance claim. A file with that power should hold only what the specification says it holds; adding a deployment's topic IDs would make a claim contingent on facts no other implementation shares, and would quietly convert `pins.json` from "what this version is measured against" into "what this deployment happens to have built." The first is portable and the second is not.

Put the other way: **a pin is a fact about the specification version; an ops record is a fact about one deployment of it.** The stamp token straddles the line and §4.1 resolves it explicitly — "a claim MUST NOT be made against a specification version whose stamp token is unpinned for the network claimed" — which is why the token is the one deployment artifact that belongs in pins.

## Alternatives considered

- **Put every entity in `spec/pins.json`.** Rejected: it exceeds §18.4's enumeration and makes T-P9-2 gate on facts that are nobody else's business. It would also mean a re-provisioned testnet changes a file in `spec/`, which is the wrong blast radius.
- **Put the price topic in pins because a claim names it.** Rejected: the claim names it *from the claim* (§5.10), which is its home. §18.4 does not list it.
- **Keep the ops record in `.env` alone.** Rejected: `.env` is git-ignored and holds secrets, so it can hold no record anyone else can read, and the provisioning script needs a committed idempotency ledger to be re-runnable by someone who did not run it the first time.
- **A single combined deployment file under `spec/`.** MINE, rejected: `spec/` is the normative tree, and a deployment's transaction IDs are not normative. `app/` is where the implementation's own facts belong (§18.5).

## Consequences

Two of `spec/pins.json`'s 32 nulls close in this phase. **Thirty remain** — the 28 `registeredSchemas` entries, which wait on HCS-13 registration, and the two `hedera:mainnet` stamp-token fields, which wait on a network §15.5 holds undeployed. So T-P9-2 continues to block every conformance claim after this phase, which is correct and worth stating plainly: standing up the entities does not make a claim possible, it makes one *eventually* possible.

New key material goes only to `.env`, covered by `.gitignore`'s `.env*` with `!.env.example` negated back in (verified: `git check-ignore` matches `.env`, `.env.local` and `.env.testnet`). `.env.example` gains the new names with blank values. Where each private key was generated and where it lives is recorded per role in `app/OPERATIONS.md` — the *location*, never the material. No key material enters `spec/pins.json`, the ops record, a commit message, or a log line.
