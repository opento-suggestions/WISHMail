# D-170 — The hbar rate is read from Hedera's own exchange rate, so a receipt can be replayed

Status:      accepted
Date:        2026-09-09
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    none. §14.3 already fixes what a rate-priced method carries; this decides what the reference Postmaster reads.
Tests:       none added. **T-P11-4 is what it exists for** — it makes that test runnable on a rate-priced method.
Supersedes:  D-143's choice of rate source, for messages published from sequence 3 onward
Spec marker: none — no specification text changes

## Context

D-143 gave the first price list a rate-priced `hbar` method reading
`https://api.saucerswap.finance/tokens` — a DEX spot price — and D-136 had
already fixed the shape: a method carries `rate {source, pair, reference}` and
the receipt records `rate {source, pair, value, at}`, "the rate used and when".

T-P11-4 is the court for what was charged: "`buy_stamp` charges what the price
message current at the receipt's consensus timestamp yields (`count ×
unitPrice`, a bundle price, or **the referenced rate applied**)". On a
fixed-price method a Verifier re-runs that arithmetic from the message alone. On
a rate-priced one it cannot: it needs the rate the Postmaster read, **at the
instant it read it**.

**A DEX spot price cannot be re-obtained at a past timestamp by anyone.**
`api.saucerswap.finance/tokens` serves the price now and keeps no history a
stranger can query. So a receipt priced under it names a `value` and an `at`
that nothing can check — the number is true and unprovable — and P-12 is
unambiguous about what follows: "Appraised never exceeds declared. Non-replayable
evidence downgrades, never upgrades." Every rate-priced receipt this deployment
produced would be downgraded, by our own rule, for a reason we chose.

MINE, raised 2026-09-09 while landing D-169; Sonic's lean, ruled the same day.

## Decision

**The `hbar` method reads Hedera's own exchange rate, from a mirror node.**

**FETCHED 2026-09-09**, `testnet.mirrornode.hedera.com`:
`GET /api/v1/network/exchangerate?timestamp=<t>` returns the rate record **in
force at `t`** — `{current_rate {cent_equivalent, hbar_equivalent,
expiration_time}, next_rate, timestamp}` — where `timestamp` is the consensus
timestamp at which that record took effect. Verified: the query is
**deterministic** at a given timestamp, and a query at the returned record's
**own** timestamp returns that same record. At sequence 2's consensus timestamp
it returns 231081 cents per 30000 ℏ, and the query repeats.

It is the network's rate and therefore **consensus data**: any stranger holding
a receipt's `rate.at` and any mirror node obtains exactly what the Postmaster
read. That is the whole of what makes T-P11-4 runnable.

**What the receipt carries.** `rate.value` is USD per ℏ, computed in integers as
`cent_equivalent / (100 × hbar_equivalent)` and **truncated** to the scale the
pricing arithmetic uses — so the number published is the number the price was
divided by, and a replay reaches the same tinybar rather than one off. Truncation
rather than rounding is a choice with a direction: a smaller divisor makes the
price higher, so the residual rounding is against the Postmaster and never
against the buyer. `rate.at` is the rate record's **consensus timestamp**, not a
wall clock, because that is the string a Verifier passes back.

**No schema moves.** §5.4 types `rate.source`, `rate.pair` and `rate.at` as
plain strings and constrains them no further, and `rate.value` was already a
decimal string. This is a deployment decision of D-138's kind.

**It lands as `PriceList` sequence 3**, identical to sequence 2 but for
`methods[hbar].rate.source`. §14.3 makes the schedule the sequence of messages
and the price current at a purchase the latest message before it, so sequence 3
supersedes sequence 2 **by landing after it** and neither earlier message is
edited. `networks.ts` therefore records the superseded source beside the current
one: `priceListStep.confirm` rebuilds sequence 1 and compares it byte-for-byte on
every provisioning run, and a constants file that could describe only the current
source would fail that comparison the moment the source moved — with the only
"fix" being to edit a message that cannot be edited.

## Alternatives considered

- **Leave the DEX source and record the gap in LIMITATIONS.** This was the
  instructed fallback if the mirror endpoint could not be replayed at a
  timestamp. It can, so the fallback is not taken — but the gap is recorded
  anyway, for sequences 1 and 2, which stay on consensus forever.
- **Snapshot the rate into the price message at publication.** Rejected by
  §14.3's own MUST, which D-136 already read: a published rate is "a number
  nobody charges", and the schedule must price what is charged at purchase.
- **Have the receipt carry the raw `{cent_equivalent, hbar_equivalent}` instead
  of a decimal `value`.** Rejected: `rate.value` is a decimal string in a frozen
  schema, and changing what it means is a schema change in all but name. The
  integer computation is recorded here and in `pricing.ts` instead, and D-169
  makes the comparison a value comparison, which is what a replay needs.
- **Make the source a bare mirror path rather than a URL**, so no host is bound.
  Rejected as inventing a scheme: D-143 set the precedent of a full URL, any
  mirror serves the same path, and the host is the one §1.6's `networkConstants`
  already pins.

## Consequences

- `app/price-list-3.hedera-testnet.json`, submitted by `npm run pricelist3` —
  which calls `publishPriceList(options)`, `pricelist2.ts` generalised, so the
  stop that makes a message sequence N has one spelling.
- `pricing.ts::readRate` reads the network rate where the schedule names it and
  the market source where it does not, because sequences 1 and 2 name one and
  are permanent.
- `networks.ts::rateSource` gains `superseded`, and `buildPriceList` accepts the
  current source or any superseded one.
- `record.ts` gains `prices.third`; `ENTITIES.md` renders the third row and says
  the last row governs.
- **LIMITATIONS records what is not fixed**: a receipt issued under sequences 1
  or 2 is unreplayable on its rate. None exists — the counter has made no sale.
