## Context

The broker relabels an agent's registry: an agent anchored on chain as `registry=hol` is served by the broker as `registry=openconvai`. Matching on the label would make the broker's database an input.

## Decision

The record, from ledger §B row D-108, verbatim:

> **§9.5 generalized from the OpenConvAI recon.** There is no OpenConvAI registry: the word names the HCS-10 standard, a category tag in Hashgraph Online's registry metadata, and a broker label on two test fixtures; the broker relabels a `registry=hol` agent as `openconvai` and rewrites its UAID string. So: `openconvai` dropped as a registry name (an address so labelled resolves by `nativeId` under `hcs14`); anchors are `0.0.9297139` (mainnet, HCS-10 form, metadata topic names operator 0.0.9297067) + `0.0.10080724` (mainnet) + `0.0.6913983` (testnet), interleaved across both names; registrations name the agent by `uaid`+`t_id` (hol chain) or by `account_id` (HCS-10 spec shape → §9.2 from the account memo); match on identifier + `nativeId`, never the label; anchors read in full, every page (the testnet topic is 380 messages). Approved by Sonic 09-06.

## Alternatives considered

- None recorded. The ledger §B row states the decision without a fork; where a fork was closed, the row says so.

## Consequences

The rule matches on the **identifier and `nativeId`**, never on the label. A `registry` parameter is a routing hint outside the identifier, and a broker that relabels an agent does not change what the ledger recorded — a fixture whose broker label differs from its anchored parameter resolves identically (§9.5, T-P6-5). Generalized from the OpenConvAI recon, which found no OpenConvAI registry at all: the word names the HCS-10 standard, a category tag, and a broker label.
