Date:        2026-09-09
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    §5.3
Tests:       none added, moved or amended. T-P1-8 is what requires the field.
Supersedes:  none

## Context

Found by `npm run check:prefreeze`, the pre-Step-4 sweep, whose second exercise
asks one question of §5.3: does MailCoordinates carry what §6.4 step 7 and §11.4
need in order to find the **recipient's** manifest topic?

It does not. §5.3 lists `account`, `doorbell`, `log`, `x25519Pub` and `keyEpoch`,
and stops. §9.1's Declaration — the object the recipient actually publishes —
carries `manifestTopic`, and §9.2's rule reads
`properties.wishmail.{manifestTopic, x25519Pub, keyEpoch}` explicitly. So the
resolver had the field in its hand, put two of the three into the coordinates,
and dropped the first on the floor. Nothing in the specification says why.

Two rules need it, and neither can get it anywhere else.

**`send` writes there.** §6.4's step 7: "When `returnReceipt` is true, `send`
creates the scheduled receipt submission of §10.4". §10.4: the inner transaction
is "a submission of the receipt's manifest to **the recipient's manifest
topic** — a topic only the recipient's key can write to". `send`'s signature is
`send(coordinates, payload, returnReceipt, window?)`, and `coordinates` is
everything it is told about the recipient. Without the field, step 7 cannot be
built from `send`'s own inputs.

**A Verifier reads there, and this is the half that cannot be worked around.**
§10.4's MUST: "A return receipt MUST be the execution of a scheduled submission
to the recipient's manifest topic". T-P1-8 checks it: "the executed submission's
postmark is on the recipient's manifest topic". To check that, a Verifier must
know *which* topic is the recipient's. §11.4 tells it which topic the submission
actually wrote to — that is in the schedule's record — but nothing tells it which
topic the recipient's *is*. The only replay-stable record of what an envelope
resolved to is the resolution proof's output, and the output is this object.

The alternative — re-resolve the recipient now and compare — answers at the
Verifier's clock. §11.6: an observation "bears on no state or standing", and P-3
requires the same scope and window to yield the same evidence from any Verifier
at any time. A recipient that rotated its declaration after the letter was sent
would make T-P1-8 fail for one Verifier and pass for another. So re-resolution
cannot be the source.

## Decision

§5.3's MailCoordinates gains `manifestTopic string — the agent's manifest topic
(§9.1)`, between `log` and `x25519Pub`, and `mail-coordinates.schema.json` gains
it as **required** rather than optional. The declaration requires it (§9.1), the
rule reads it (§9.2), and coordinates without it cannot satisfy T-P1-8, so an
optional field would be a hole that validates.

The resolver's declaration guard gains it beside the two it already checked. A
profile whose `properties.wishmail` lacks a manifest topic is not a declaration,
and T-P6-3 already says such a profile resolves to `RESOLVE_NOT_FOUND` rather
than to coordinates with a hole in them.

**No new MUST and no new test.** T-P1-8 already states the requirement this field
makes checkable; the field is what lets an implementation satisfy a test that was
already registered. This is D-161's shape exactly — a field added under an
existing test, with the existing test named as the court.

## Alternatives considered

- **`send` re-reads the declaration at step 7.** Rejected. It answers `send`'s
  half and not the Verifier's, and it introduces a second resolution at a second
  time: the receipt would be scheduled to whatever topic the recipient declared
  at step 7, which need not be the topic the resolution proof bound at step 2.
  The envelope's AAD commits the resolution proof's hash; a receipt owed to a
  topic that proof does not name is a receipt the chain does not reach.
- **The Verifier takes the topic from the schedule record and checks nothing
  else.** Rejected: that makes §10.4's MUST and T-P1-8 unenforceable — any topic
  the recipient's key can write to would satisfy it, which is every topic the
  recipient owns.
- **The Verifier re-resolves at appraisal.** Rejected: §11.6 and P-3, above.
- **Optional rather than required.** Rejected: a conforming implementation could
  then emit coordinates that make T-P1-8 impossible, and the suite would have no
  sentence to point at.

## Consequences

- `spec/schemas/mail-coordinates.schema.json` gains a required property. **A
  schema change, admissible as a patch only while `registeredSchemas` is null**
  (§1.7, D-161's reasoning). It lands before Step 4's signature for that reason.
- No wire string moves. MailCoordinates is a tool result and a manifest's
  `output`; it carries no protocol identifier.
- Every resolution manifest's `output` grows by the field, and therefore every
  resolution proof's **hash changes**. Nothing is published against an old one:
  no envelope has been assembled on `hedera:testnet`.
- Measured on the live declaration, the field costs 31 bytes on the wire and
  takes the `hcs14` first-form manifest from 966 to **997 against §9.1's
  1000-byte limit**. That is not this decision's defect — the manifest was
  already over at every address longer than an account id — but this decision is
  what made it impossible to keep ignoring. Raised as **ledger §G-17**, unruled.
- `app/src/resolve/hcs14.ts`, `app/src/tools/send.ts` and the letter fixture
  carry the field; the resolver's guard checks all three of §9.2's fields.
