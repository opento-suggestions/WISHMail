## Context

§4.6's normative sentence is about ownership:

> A provisioned account, topic, or profile MUST be owned by keys the agent generated. The Postmaster MUST NOT retain any key to it.

T-P17-1's row read it as being about both keys: "Every provisioned topic has admin/submit keys set to the agent's keys per declared policy; policy recorded at creation."

**No doorbell can satisfy that.** A doorbell is an HCS-10 inbound topic, and its whole function is to accept a `connection_request` from a stranger. A submit key set to the agent's key makes it unreachable by exactly the party first contact exists for. §4.4 says as much in its own terms — the doorbell "is not a public forum" because it charges a stamp, not because a key gates it. The fee is the gate.

The pinned standard is not silent on this, which was worth checking rather than reasoning from observed practice. FETCHED 2026-09-07 from `docs/standards/hcs-10/index.md` at `7046156c`, blob `0cb5d2eb…` (git-hash and SHA-256 both reproduce `spec/pins.json`):

> **`index.md:113`** | **Inbound Topic** | Channel for receiving connection requests | Public (No Key), Submit Key, or Fee-gated (HIP-991) |
> **`index.md:114`** | **Outbound Topic** | Public record of an agent's actions | Has submit key (only agent can write) |

with the three inbound options spelled out at `:119-122` and repeated in the creation workflow at `:857-860`. §4.4's MUST selects the third.

## Decision

**T-P17-1 is loosened to match §4.6.** The row now reads:

> Every provisioned topic has its keys set at creation per the declared policy for that topic type, and the policy is recorded at creation.

"Owned by keys the agent generated" means the **admin** key; the sketch over-read it. The shapes move out of the row and into the policy the row points at.

**The policy — stated once, here.** Because the reference Postmaster provisions its own agent identity by the same path a customer's agent takes, this table is the template every provisioned agent inherits (§4.6, the Postmaster-provisioned path):

| Topic | Memo | Submit key | Admin key | Fee schedule key | Fee | Exempt list | Warrant |
|---|---|---|---|---|---|---|---|
| doorbell (HCS-10 inbound) | `hcs-10:0:60:0:<agentAccount>` | **none** — public | agent | **none** | HIP-991, one `$POSTAGE`, collector the treasury | the agent's own key | `index.md:113`; §4.4; D-137 |
| log (HCS-10 outbound) | `hcs-10:0:60:1` | agent | agent | — | none | — | `index.md:114` |
| manifest topic | `wishmail:manifest:1` | agent, sole | agent | — | none | — | §9.1 |
| lane (HCS-10 connection) | HCS-10's connection memo | threshold of exactly the two agents' keys | the acceptor's declared policy | — | none | — | §7.1 |

**No fee schedule key on the doorbell.** Sonic, 2026-09-07: "Omit it. No key means the fee is immutable at birth, which is P-17's whole doctrine and §4.4's 'exactly one stamp' made structural. A Postmaster-held key would be authority (P-2); an agent-held key would let a conforming doorbell drift out of conformance later. Immutable, ADR'd, done." RECORD. HIP-991 makes this one-way and that is the intent: "If the topic was created without a Fee Schedule Key, the key cannot be added later" (`hip-991.md:97`, pinned by D-135).

**The owner's key on the exempt list at creation**, which is how the doorbell satisfies D-137's outcome. HIP-991 sets the list at creation, caps it at ten, and does not populate it by default: "the Fee Exempt Key List will not include the Admin Key, Submit Key, or Fee Schedule Key, unless explicitly provided" (`:126`).

**The HCS-10 memo TTL is a deployment fact, not specification.** WISHMail reads no TTL, and §9.5 makes the memo bind nothing. `60` is the value recon observed on every live inbound and outbound topic — testnet inbound `0.0.7124410` `hcs-10:0:60:0:0.0.7124407`, testnet outbound `0.0.7124409` `hcs-10:0:60:1`, mainnet inbound `0.0.10058322` `hcs-10:0:60:0:0.0.10058320`. It is recorded in `app/deployment/hedera-testnet.json` with that citation, and the specification stays silent; if the pinned HCS-10 text later defines a TTL, the operational value moves and no document changes.

**Not a version change.** Loosening a test to match landed text invalidates nothing — §1.7's minor-bump trigger is a change that "would invalidate a previously conforming implementation," and this widens rather than narrows. No implementation conforms in any case (T-P9-2).

## Alternatives considered

- **Amend §4.6 to say "admin key" explicitly.** Rejected: §4.6 already says "owned by," which is the admin key; the defect was in the row's paraphrase, not in the sentence.
- **Give the doorbell a submit key and gate first contact some other way.** Rejected: it defeats first contact, and §4.4 makes the fee the gate.
- **Keep a fee schedule key so the fee could be re-denominated after a token migration.** Rejected by Sonic, above. Note the asymmetry this leaves, which is the right one: the admin key survives, so the **fee is immutable while the exempt list stays amendable**.
- **Take TTL `86400`** — Claude Code's first draft, MINE, and wrong. The `86400`s recon observed are on registry and HCS-2 topics, a different topic type; on inbound and outbound topics the observation is unanimously `60`.

## Consequences

The suite's provisioning check reads each topic type against its own row rather than against one shape that fits none of them. A doorbell with a submit key now fails T-P17-1 as clearly as one with a Postmaster key does, and for the stated reason.

Because this is the dogfooded template, the table is load-bearing beyond this deployment: the Postmaster-provisioned path of §4.6 produces exactly these shapes for a customer's agent, and the provisioning script does not special-case its own. D-47 holds throughout — the Postmaster pays, the agent signs, and no key of the Postmaster appears on any of these topics.
