# D-165 — An agent outlives the demo: a home directory, and idempotency against consensus

Status:      accepted
Date:        2026-09-09
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    none — no specification sentence changes
Tests:       none added, moved or amended. T-P8-3, T-P7-5 and T-P11-5 are the
             existing courts for what this rule protects.
Supersedes:  none
Spec marker: none (a reference-implementation decision; CLAUDE.md §11 carries it)

## Context

D-159 gives the provisioning order and D-156 gives the roles, and between them
they describe an agent's *first* run: keys are born in its process, an account is
bought for its public key, topics are created, a profile is declared, a
registration is submitted. Neither says what happens on the second run.

That silence is dangerous in a specific way. Every act in the provisioning order
is a consensus act that costs something and that a reader can see: a doorbell is a
topic, a registration is an entry on a public anchor, an account is an account. An
implementation that decided "already provisioned?" from a local file would, on a
wiped directory, ring a second doorbell and submit a second registration — and
§9.5 assigns `vague` where more than one registration names an address, so the
agent would degrade its own resolution by restarting.

And an agent that regenerated its keys on boot would be a different agent every
time it started: a new account, a new address, a new everything, with the previous
run's coordinates still declared on consensus and pointing at a key nobody holds.
§7.6 and L-1 already require every epoch's X25519 key to be **retained**, because
an envelope sealed under a retired epoch must still open (T-P8-1, T-P8-2).

## Decision

**The Correspondent home directory is the agent's identity.** It holds three
things, and the boundary between them is the boundary of D-156's config rule:

- **config** — the operator's payer, the network, runtime locations. The
  operator's, from the operator's own file or environment, never from code.
- **keystore** — the account key, and every epoch's X25519 key, retained.
- **the durable store** — sent envelopes for F-3 retry, pending receipt requests,
  the inbox cursor.

A fresh home is a new agent; an existing home is a returning one. **Keys are born
once**, on first run, into the keystore; every later boot loads them.

**Every provisioning verb is idempotent against consensus, not against local
state.**

- `generate_mailbox` resolves the agent's own address under `hcs14` first, and
  does nothing if coordinates already exist.
- `register_agent` resolves under `hol` first, and does nothing if a registration
  by this account already exists.
- `buy_stamp` with `provision` refuses if the holder's account already exists; a
  returning agent buys without `provision`.

This is CLAUDE.md §9's rule — write the reader with the writer — applied to
provisioning: **the resolver is the reader**, and it is already built, already
run against our own address, and already the thing a stranger would use to check
us. A local file is a cache of consensus and never an authority over it.

**Lanes are reused, never re-rung.** §7.1 already fixes the earliest-created open
lane between two agents as *the* lane, for `send`, for `inbox` and for replay, so
a second letter to the same recipient rings nothing. The doorbell watcher decides
what to answer by reading the doorbell for requests with no `connection_created`,
so it too is idempotent from consensus and a restart mid-handshake answers the
same ring once.

**Rotation stays out of the MVP, and nothing built here may make it harder.** No
local assumption that there is exactly one epoch: the keystore is keyed by epoch
from the first run, holding one entry, and holding two later is a write and not a
migration.

## Alternatives considered

- **A local `provisioned: true` marker.** MINE, and the obvious shortcut.
  Rejected: it is the exact failure above — a wiped or copied directory rings a
  second doorbell and submits a second registration, and `vague` is what a reader
  sees for it.
- **Regenerate keys on boot and re-provision each run.** Rejected: it makes every
  restart a new agent, orphans the prior declaration on consensus, and contradicts
  §7.6 and L-1, which retain every epoch's key so a retired-epoch envelope still
  opens.
- **Ask the Postmaster whether the agent is provisioned.** Rejected: it makes the
  Postmaster an authority on the agent's identity, which is the broker dependency
  P-4 forbids and which §9.7 refuses for the HOL broker for the same reason.
- **One key file per agent, no directory.** Rejected: the durable store and the
  retained epoch keys have to live somewhere, and splitting them across three
  places makes "what is this agent" unanswerable by looking.

## Consequences

- The Correspondent gains a home directory whose path comes from the operator's
  configuration; a filled config stays gitignored and `npm run p13:check` is what
  keeps it that way (D-156).
- Three provisioning affordances gain a resolve-first step, which costs one mirror
  read each and makes them safe to run twice — which is what `app/OPERATIONS.md`
  already asserts of every provisioning step by running each one twice.
- No specification sentence changes. §7.1, §9.5 and §4.6 already say all of this
  about consensus; what is new is the rule that the implementation asks consensus
  rather than a file.
- The keystore is keyed by epoch from the first run, so rotation is a write.
