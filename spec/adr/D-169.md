# D-169 — Decimal-string amounts compare by value, not by spelling

Status:      accepted
Date:        2026-09-09
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    §14.3 (§5.4 by its own pointer)
Tests:       none added. **T-P11-4's sketch is amended** to say how it must compare.
Supersedes:  none
Spec marker: CHANGED: D-169 on §14.3

## Context

D-136 fixed every price as a **decimal string** — "not in atomic units, which
bake a network's decimals into a document a Verifier reads, and not as a JSON
number, because the message is canonical JSON (§5.1) and a float is a hazard."
It did not say how two of them are compared, and nothing else did either.

`check:exchange`, run for the first time on 2026-09-09, found what that leaves
open: the published schedule prices a bundle at `"1.00"` and the counter's
receipt says `"1"`. Both are the same amount. The counter's arithmetic is in
integers at a fixed scale (`pricing.ts`), so what it emits is the **normalised**
decimal — the value — and not the string the message happened to carry.

T-P11-4 is the court for what was charged: "`buy_stamp` charges what the price
message current at the receipt's consensus timestamp yields". Its body does not
exist yet. Written the obvious way — comparing the receipt's `price.amount` to
the schedule's `price` as strings — **it would fail a receipt that is exactly
right**, and it would fail every receipt this implementation produces.

## Decision

**An amount written as a decimal string is compared by numeric value and never
by spelling.** `1`, `1.0` and `1.00` are one amount, and a receipt need not echo
the schedule's spelling of one.

It holds for every decimal-string amount the specification defines: a method's
`unitPrice`, a bundle's `price`, `rate.reference.amount`, `provisioning.unitPrice`
and `provisioning.registrationFee` in §14.3, and a receipt's `price.amount` and
`rate.value` in §5.4 — which reaches them by its own existing pointer, "a decimal
string in the ledger's natural unit as every other amount in a price is (§14.3)".

The sentence lands in **§14.3**, where the form is fixed, rather than in §5.4,
because §5.4 already defers there and one sentence in one place is the whole of
the rule. Its `Conformance:` note names **T-P11-4**, and §A's sketch for that
test is amended to say the same thing where whoever writes the body will read it.

## Alternatives considered

- **Say nothing and let each test decide.** Rejected: the one test that would
  decide has not been written, and the decision would then be made by whoever
  wrote it, silently, in a comparison operator.
- **Require the receipt to echo the schedule's literal.** Rejected on two
  grounds. It would make a receipt a function of how a message was typed rather
  than of what was charged; and it would force the counter to carry the source
  string alongside its arithmetic, which is a second representation of one
  number — the thing D-136 was avoiding when it forbade atomic units.
- **Fix a canonical form for amounts** — say, always the normalised decimal —
  and require both sides to emit it. Rejected as more than is needed: it would
  make the committed `PriceList` at sequence 1 non-conformant for spelling
  `"1.00"`, and that message is on consensus and cannot be edited (§14.3: a new
  schedule is a new message).

## Consequences

**A patch, 0.5.10.** No wire string moves, no schema changes, and no test is
added — §1.7 permits it after the freeze precisely because it touches neither.
The register stays at 86.

- §14.3 carries `CHANGED: D-169` and one sentence.
- §A's T-P11-4 sketch gains the note, with the worked example (`"1.00"` against
  `"1"`) so the trap is visible rather than described.
- No implementation changes. `pricing.ts` already compares in integers, and
  `check:exchange` already asserts the normalised form and says why beside the
  assertion.
