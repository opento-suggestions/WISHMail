# D-175 — `resolvedAt` is query time reported beside the coordinates, not a value bound into the proof's inputs

Status:      accepted
Date:        2026-09-10
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    §5.3
Tests:       none. No test is added, moved, or amended.
Supersedes:  none
Spec marker: CHANGED: D-175 on §5.3

## Context

§5.3's `MailCoordinates` glossed one of its own fields:

> `resolvedAt       timestamp    query time, as bound into the proof's inputs`

That phrase is false of this specification's own §5.2, which fixes a proof's
`inputs` as `{digest, locator, snapshot?}` — a closed set, and **none of the
three is a query clock**. `digest` is over what was read; `locator` is where a
Verifier re-obtains it; a `snapshot` is bytes that are not re-obtainable. §9.2's
locator does carry a `consensusTimestamp`, but that is *the registry entry's*
timestamp — "the registry entry current at the resolution's consensus timestamp"
— and not the moment the query ran.

So this implementation binds `resolvedAt` nowhere in `inputs`, and it was right
not to. §10.2 gives the reason that holds unconditionally: a digest containing
the query's clock could never be matched by a replay at another clock, which is
the whole mechanism. The gloss described something no profile does and nothing
should.

Raised while landing §10.2's digest domain at 0.5.9, as ledger §G-18, and left
unpatched until ruled.

## Decision

**RECORD (Sonic, 2026-09-10), reading (a), folded into the 0.5.12 patch:** one
sentence closes it. §5.3's gloss now reads

> `resolvedAt       timestamp    query time, reported beside the coordinates`

which is what `resolvedAt` has always been and what every profile actually does
with it.

**Text only.** No schema moves, no wire string moves, no test is added or
amended, and **§10.2 is untouched** — its exclusion of `resolvedAt` from the
resolution digest rests on its own reason and never on §5.3's phrase. §1.7's bar
is not approached: there is no conformance test to invalidate, because this
changes none.

## Alternatives considered

- **(b) The locator gains a `resolvedAt` field**, making the old phrase true.
  **Rejected (RECORD).** It costs bytes against §9.1's budget, and it buys the
  phrase's truth by putting a clock inside a locator — the one thing §10.2 says
  a replay can never reproduce.
- **(c) `resolvedAt` is already implied by the locator's `consensusTimestamp`.**
  **Rejected (RECORD)**, and it is simply false: that timestamp is the registry
  entry's, not the query's — and §9.3's and §9.4's locators carry a `queryTime`
  and a `fetchTime` instead, which are different fields again.

## Consequences

- §5.3's gloss is one line shorter of a claim it could not support. Nothing in
  `app/` changes: the resolver already reported `resolvedAt` beside the
  coordinates and excluded it from the digest
  ([hcs14.ts:494-517](app/src/resolve/hcs14.ts#L494-L517)), which is why this is
  a gloss fix and not a defect.
- **The asymmetry the finding really names is kept as an observation, not
  repaired.** §9.3's and §9.4's locators carry the query's own clock — a
  `queryTime` and a `fetchTime` — while §9.2's and §9.5's carry neither. So the
  two off-consensus profiles satisfied the old phrase and the two consensus ones
  never could. After (a) none of the four is obliged to, and what remains is not
  an inconsistency but a fact about off-consensus inputs: a DNS answer or a
  fetched document can only be re-obtained *as of* a moment, and a consensus
  entry can be re-obtained by its own locator forever.
- Closes ledger **§G-18**, its finding kept unedited beneath the ruling.
