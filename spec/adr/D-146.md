# D-146 — §4.6's `Conformance:` note names the admin key

Status:      accepted
Date:        2026-09-08
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    §4.6
Tests:       T-P17-1 — amended in §A of `spec/CONFORMANCE_TESTS_v0_5.md` to match the amended note
Supersedes:  none — completes D-138, which left this sentence standing
Superseded:  the `Conformance:` note refined by D-150 — the admin-key rule gains an exception for a standard whose pinned text forbids an admin key, which is HCS-1's case for the HCS-11 profile file. Everything this decision says about *why* the admin key is the agent's stands unchanged.
Spec marker: CHANGED: D-146, D-150 on §4.6

## Context

D-138 found that §A's T-P17-1 row over-read §4.6. The row demanded that every provisioned topic have "admin **and submit** keys set to the agent's keys", and no doorbell can satisfy that: §4.4's MUST selects HCS-10's fee-gated inbound option, and a topic that must accept a stranger's `connection_request` has no submit key at all (`index.md:113`, D-138). The row was amended.

The specification's own sentence was not. `spec/WISHMAIL_SPEC_v0_5.md:584` still read:

> `Conformance:` T-P13-1; T-P17-1 — every topic the suite provisions has its admin and submit keys set to the agent's keys per the declared policy, and the policy is recorded at creation.

D-138 declared `Spec marker: none — no specification sentence changes`. **That was wrong**, and the consequence is not cosmetic: the specification governs (CLAUDE.md §1), so as landed no doorbell could be provisioned conformantly at all. The provisioning phase was about to build against a sentence forbidding what it builds.

Raised rather than patched as ledger §G item 10 (Claude Code, 2026-09-07, MINE): a spec sentence is Sonic's ruling, not Claude Code's.

## Decision

**`:584` names the admin key explicitly** (RECORD, Sonic 2026-09-08). It now reads:

> `Conformance:` T-P13-1; T-P17-1 — every topic the suite provisions has its **admin key set to the agent's key** and its remaining keys set at creation per the declared policy for that topic type, and the policy is recorded at creation.

§A's T-P17-1 row is amended in the same change to the same words, so the spec/register divergence that produced this defect does not survive its fix.

### Why the admin key is named rather than left to the policy

The alternative was to adopt §A's row verbatim — "its keys set at creation per the declared policy for that topic type" — which is one-for-one with the register and needs no ledger edit. It lost because it under-tests the MUST directly above it. §4.6:583:

> A provisioned account, topic, or profile MUST be owned by keys the agent generated. The Postmaster MUST NOT retain any key to it.

D-138's own reading is that "owned by keys the agent generated" means the **admin** key — that is the sentence on which its whole table rests. If the `Conformance:` note delegates every key to the declared policy, a policy could name a non-agent admin key and pass, and §4.6's MUST goes untested at its own line. That is the same class of defect D-137 corrected: a sketch under-testing an already-normative sentence.

The amended note keeps both halves. The admin key is fixed by the MUST; everything else — a submit key, its absence, a fee, an exempt list — is the declared policy's business, per topic type, which is exactly what D-138's table and D-147's fifth row supply.

### Scope

**§4.6 and T-P17-1 govern the topics the suite provisions *for an agent*.** The Postmaster's own price topic is infrastructure, not a provisioned agent topic: its submit and admin keys are the operator's by D-142, and §4.6 has nothing to say about it. Without this sentence the amended note would read as demanding an agent admin key on a topic that by ruling has none.

## Alternatives considered

- **Adopt §A's row verbatim.** Rejected for the reason above: simpler and one-for-one, but §4.6:583's MUST would go untested at its own `Conformance:` line.
- **Amend §A's row back to the spec's text.** Rejected: that reinstates the over-read D-138 removed and re-breaks the doorbell.
- **Leave `:584` and note the divergence.** Rejected: the specification governs, so the divergence is not a note, it is a rule forbidding a conforming doorbell.
- **Hold it for a later minor version.** Rejected: no conforming implementation exists to invalidate (T-P9-2 blocks every claim while pins are null), so it is patch-level under §1.7, and the provisioning phase needs the sentence right before it builds.

## Consequences

The repository's fourth `CHANGED` marker, `<!-- CHANGED: D-146 -->`, sits above §4.6's `:583`–`:584` paragraph. §18.2's ADR index gains a D-146 row, because this amends a sentence of the document — the criterion §18.2 states for itself.
