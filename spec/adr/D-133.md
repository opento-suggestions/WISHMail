# D-133 — `resolve` is one profile, one resolution, one proof; D-33's set-valued return does not carry

Status:      accepted
Date:        2026-09-07
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    §6.2, §7.2, §9.1 (confirmed as written — no specification text changes)
Tests:       none added (T-P5-1, T-P5-2, T-P12-1 and T-P12-3 already bind `resolve`)
Supersedes:  D-33 (its set-valued return)
Superseded:  none
Spec marker: none — this decision confirms §6.2 and amends no sentence

## Context

Found during the D-1 – D-41 ADR backfill of 2026-09-07. D-33, carried from `provenance/WISHMAIL SPEC v0 3.md` §13 and dated 2026-09-04, reads: "Multi-profile `resolve` returns a set; the sender chooses and declares; reference implementation baseline by default, configurable."

§6.2 of the frozen 0.5.0 text fixes the signature as `resolve(address, profile?) -> MailCoordinates`, with the postcondition "`MailCoordinates` with a resolution proof whose hash is computed and whose manifest is returned to the caller" — one profile, one set of coordinates, one proof. No row in ledger §B recorded the change between the two, so the repository held a carried decision and a frozen specification that disagreed, with nothing saying which governed or why. Raised as a decision candidate, MINE, 2026-09-07.

## Decision

The sender still chooses — that half of D-33 stands and is what §6.2's optional `profile` argument is for. What does not carry is the set-valued return. **One profile, one resolution, one delivery, one message send, one proof.** RECORD (Sonic, 2026-09-07).

§6.2 is confirmed as written. No specification sentence changes.

## Alternatives considered

- **Amend §6.2 to return a set, honouring D-33 as carried.** Rejected. It would make `resolve` return several proofs where the envelope can bind exactly one, and the AAD binds one resolution proof hash and no other (§7.2). The choice has to happen before the proof is made, not after.
- **Leave the divergence unrecorded, since 0.5.0 already governs.** Rejected: a carried ADR that contradicts the frozen text with no ruling beside it is exactly the kind of seam the ADR set exists to close.

## Consequences

The one-to-one chain through the whole document is now stated where an implementer will look for it: one stamp buys one envelope to one witnessed-resolved address (P-10); the AAD names one lane and one resolution proof (§7.2); a settlement stamps one envelope and no other (§4.3, T-P7-2); a return receipt binds one envelope and one postmark and cannot be re-worn (P-1, §10.4). `resolve` returning one resolution is that chain's first link, not an isolated signature choice.

A multi-profile implementation is unaffected in capability: it calls `resolve` once per profile. What it may not do is hand the Assembler a set and let assembly pick, because by then the proof's manifest is published and its hash is what the AAD commits (§6.4 steps 2–3).

`spec/adr/D-033.md` is updated to point here: `Status` stays `carried`, and its `Superseded` field and Consequences now name D-133 instead of recording an open divergence.

§18.2's ADR index in the specification is not extended to D-132 – D-134. It indexes the decisions that shaped the specification's text, and these three shape none of it; extending an appendix of the frozen document would be a specification edit carrying `CHANGED` markers for no change. MINE, procedural, reversible on Sonic's word.
