# D-151 — The vectors' key material is no agent's key

Status:      accepted
Date:        2026-09-08
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    none (§7.3 and §12.2 are read, not amended)
Tests:       T-P1-5 (unblocked; sketch unchanged), T-P13-1, T-P13-2 (gate widened)
Supersedes:  none
Spec marker: none — no specification sentence changes

## Context

T-P1-5 makes `spec/vectors/seal.json` the court of §7.3 and states the test as: "HPKE
vectors; reference seals / independent opens, and the reverse." The reverse direction is
the one that bites. An independent implementation cannot *open* what the reference sealed
without the recipient's private key, which is why RFC 9180 publishes `skRm` beside every one
of its own Appendix A vectors, along with `ikmE`, `skEm` and the derived key schedule.

`conformance/README.md:51` had written the governing rule as:

> **No private-key material in any fixture** (P-13; T-P13-1, T-P13-2).

That sentence is wider than P-13. P-13's own text, §12.2:1688, reads:

> **P-13 — Never hold the soul.** No private key of any **agent** — decryption, topic, or
> account — is ever held by the Postmaster, carried by any tool input or schema field, or
> accepted by an agent from any other party. Keys are born in the agent's process;
> provisioning delivers coordinates and never a secret.

Read as `conformance/README.md` wrote it, T-P1-5 is unsatisfiable and the specification
contains a test no conforming release can run. Read as P-13 states it, there is no conflict at
all. Raised by Claude Code, 2026-09-08, while planning the vectors; Sonic ruled the same day.

## Decision

The narrower reading binds: P-13 forbids the private key **of an agent**, and a key born for a
test vector is no agent's key. It is bound to no account, no topic and no epoch; it opens
nothing that was ever sent; and no provisioned agent ever holds it. `spec/vectors/seal.json`
therefore carries `skRm` and the rest of the material an outside implementer needs, and
declares in the file itself what that key is and is not, so a reader meets the reasoning where
the key is rather than in a decision record.

Three things enforce it rather than assert it:

1. The vector generator **refuses** any key that appears in `app/deployment/hedera-testnet.json`.
   A vector key and a deployment key can never be the same bytes by accident.
2. `conformance/README.md`'s sentence is narrowed to "no key of a **provisioned agent**."
3. `scripts/p13-check.mjs` is widened. It watched `/(AGENT|TREASURY)_DER_KEY/`, and
   `AGENT_X25519_DER_KEY` — the encryption key §9.2's declaration needs, and the first
   non-Hedera key this build generates — walks straight past that regex. It now watches
   `/(AGENT|TREASURY)[A-Z0-9_]*_KEY/`, which still does not match `OPERATOR_DER_KEY`: the
   operator is the Postmaster's own payer under D-47, not an agent, and the gate's module
   comment already says why it is deliberately excluded.

Point 3 is a hole in the gate that existed independently of this ruling and would have opened
the moment the declaration generated an X25519 key. It is closed in the same change because it
is the same subject.

## Alternatives considered

- **Keep the wide sentence; put the opening keys in a separate file the suite reads.** MINE,
  and rejected: it is the same fact with more ceremony, and it makes `seal.json` not
  self-contained for an outside implementer, which is the one thing T-P1-5 exists to test.
- **Publish only public halves, ciphertext and expected plaintext.** Rejected: it satisfies
  "the reference seals" and silently drops "an independent implementation opens," which is
  half the test.
- **Amend P-13.** Rejected: P-13 is correct as written. What was wrong was a house document
  paraphrasing it more strongly than the invariant states, which is exactly the failure
  CLAUDE.md §6's register discipline is meant to catch.

## Consequences

No specification sentence changes and no schema changes, so this is not a version change of
its own; it rides in the 0.5.3 patch that D-150 forces. `spec/vectors/seal.json` and
`spec/vectors/aad.json` can now be generated, which unblocks T-P1-4 and T-P1-5 and, through
them, every class — T-P1-4 is keyed to `all`.

An implementer reading `spec/vectors/seal.json` will find a private key in a file in this
repository. The file says why, and this decision is what it points at. The rule that still
holds without exception: no key of a provisioned agent appears anywhere but `.env`, which is
git-ignored, and it is read in `app/src/ops/env.ts` and held in `app/src/ops/identity.ts` and
nowhere else.
