# D-161 — The Step 4 freeze is ordered after one last schema change: `buy_stamp` takes `provision`, and `StampReceipt` records it

Status:      accepted
Date:        2026-09-09
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    §5.4, §6.3
Tests:       none added, moved or amended. T-P11-4 is the court for the price.
Supersedes:  none
Spec marker: CHANGED: D-161 on §5.4, §6.3

## Context

§4.6 gives the Postmaster-provisioned path and says what the agent gets from it:
"The agent receives coordinates and receives no secret." §14.3's `PriceList`
carries an optional `provisioning {method, unitPrice}`, so the path is priced on
consensus like everything else the Postmaster sells.

But §6.3's signature was `buy_stamp(count, payment, holder)`. There was no way
for a buyer to ask for the provisioned path, and no way for the receipt to
record either that it was bought or what the agent received. A path the
specification prices and describes had no surface, and the object that witnesses
a purchase could not witness this one.

Separately, Step 4 — the HCS-13 registration of §18.5's fourteen schemas — has
been built and held since 2026-09-08. Registration is §1.7's freeze of
`spec/schemas/`: after it, a schema change is 0.6.

## Decision

**`buy_stamp` gains `provision = false`. `StampReceipt` gains an optional
`provisioning` line.** The line carries the price and the entities the Postmaster
created — `account`, `doorbell`, `manifestTopic` always; `log` where one was
made; `declRegistry` and `profileFile` under the native profile. That is exactly
what §4.6 promises the agent receives: **coordinates, and no secret** (P-13).

Presence is exact: `provisioning` is present when and only when the purchase
also bought the provisioned path. The schema cannot check that, for the same
reason it cannot check `rate`'s presence — the receipt does not carry the
request that asked for it, as it does not carry the method that priced it — so
the schema's `$comment` says so and the tool holds it.

**No new `TOOL_REASON`.** A Postmaster that publishes no provisioning price
refuses under `STAMP_METHOD_UNSUPPORTED`, and §6.3's preconditions say so.
Inventing a code for one precondition would be inventing vocabulary
(CLAUDE.md §4).

**And this is why the freeze is ordered where it is.** §5.11 requires every
chunk to carry a `schemaRef` that resolves through HCS-13 to the Chunk schema
its release registered, and that reference is baked into chunk 0 at assembly.
So Step 4 must sign **before the first letter**, and any schema change must
therefore land **before Step 4**. This is the last schema change 0.5 will ever
admit, and it is being taken now rather than discovered later.

**Why a patch may change a schema at all.** §1.7: a patch revision "changes no
wire string, and *once a minor version's schemas are registered* it changes no
schema." `registeredSchemas` in `spec/pins.json` is null throughout — 28 unfilled
pins, T-P9-9 — so nothing is registered and the condition has not yet bound.
After Step 4 signs, the identical addition would be 0.6. The version stays
**0.5.5**.

## Alternatives considered

- **Leave `buy_stamp` alone and let provisioning be a separate act.** This is in
  fact what the MVP does — the agent self-provisions with a borrowed payer
  (D-159) — but it leaves §4.6's second path with no tool surface at all, and
  the freeze is the last moment it could be given one without a minor version.
- **Carry only the price on the receipt.** Rejected: a buyer who bought
  provisioning needs to learn its doorbell, and a receipt that records the
  charge without the product is a receipt for nothing readable.
- **Carry the whole `MailCoordinates`.** Rejected as redundant and wrong-shaped:
  coordinates carry a resolution proof and a `resolvedAt`, which a purchase does
  not produce. The entities are what the Postmaster made; the declaration and the
  proof are the agent's own act afterwards.
- **Defer the whole thing to 0.6.** Rejected on Sonic's ruling, and on the
  observation that 0.6 has no schedule while the freeze has one.

## Consequences

§5.4's shape block gains the line and a paragraph beside `rate`'s; §6.3 gains
the parameter, the precondition, and a paragraph in Behavior; both carry
`CHANGED: D-161`. `spec/schemas/stamp-receipt.schema.json` gains `provisioning`
as an optional object with `price`, `account`, `doorbell` and `manifestTopic`
required within it.

No test is added, because no MUST is added. T-P11-4 remains the court for what
was charged, now including the price list's `provisioning` entry.

**Ordering, which is the operative half of this decision:** the StampReceipt
line lands, then an instance of each of `StampReceipt`, `ReturnReceipt` and
`ConformanceClaim` is constructed and validated, then `v0.5.5` is tagged, then
Step 4 signs, then the first letter. Signing Step 4 fills the 28 pins and closes
`spec/schemas/` for the life of 0.5.
