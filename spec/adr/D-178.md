# D-178 — `structuredContent` is exactly what §6 names; `_meta` is observation; the text block is prose

Status:      accepted
Date:        2026-09-11
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    none. No normative text changes. This governs `app/`'s MCP surface, not the specification.
Tests:       `npm run check:outputs` — new, 41 assertions. No register row is added; the register stays at 87.
Supersedes:  none
Spec marker: none — no paragraph of `spec/WISHMAIL_SPEC_v0_5.md` moves, and no version event follows.

## Context

A tool's published `outputSchema` and what its handler puts in
`structuredContent` are two separate artefacts, and nothing in this repository
made them agree. Twice they did not, and both times on the surface a real client
actually reads.

**`send`, found 2026-09-11.** §6.4 says "`send` then returns chunk 0's
`Postmark`", and the published `outputSchema` is a `oneOf` over two registered §5
objects, each `additionalProperties: false`. The handler returned its whole
internal `SendResult` — `{kind, postmark, envelope, postmarks, settlement,
manifestLocator, lane, receipt?}` — which the registered Postmark schema forbids
twice over. A client building its expectations from the published schema would
have rejected the first letter it ever received.

**`inbox`, found 2026-09-12 and LIVE.** `app/src/mcp/schemas/delivery.output.schema.json`
declares `payload` as `{"type":"string","contentEncoding":"base64"}`; the handler
returned the internal `Delivery`, whose `payload` is a Node `Buffer`. In goose
session `20260912_4` at 01:22:29 it crossed the wire as
`{"type":"Buffer","data":[84,104,105,…]}` and rendered the letter as a list of
decimal byte values. Four further keys — `lane`, `chunkPostmarks`, `detail`,
`openedUnderEpoch` — are forbidden outright by a schema that is
`additionalProperties: false`.

Neither was reachable from a CLI, because a CLI reads the text block. Neither was
reachable from `check:mcp`, which compiles every schema and validates no
instance. Both needed real bytes through a real shaping, which is why three clean
gates driven by CLIs did not find them and the first gate driven by goose did.

## Decision

**One rule, for every verb this MCP surface publishes:**

- **`structuredContent` carries exactly what §6 names, and nothing else** — the
  §5 object in the one field the published schema wraps it in.
- **`_meta` carries the evidence the implementation also holds.** It is not
  discarded and none of it is secret; it travels where no schema claims it is
  the tool's output.
- **The text block carries the prose** — the card, for whoever is reading rather
  than parsing.

**And the shaping is a function, not a habit.** `app/sdk/structured.ts` holds one
entry per verb; the handler and the court read the *same* function, so a court
cannot court its own restatement.

## Why

**A schema a surface publishes is a promise, and the promise is what a client
builds against.** MCP validates `structuredContent` against the tool's
`outputSchema` at the client. A handler that returns something else is not
returning extra information; it is breaking the contract it advertised, at the
one party that trusted it.

**Nothing is lost by narrowing, and that is checkable rather than hopeful.** Of
`inbox`'s four forbidden keys, two are duplicates of fields already inside the
object it carries: `lane` is `envelope.lane` and `openedUnderEpoch` is
`envelope.keyEpoch`, both REQUIRED by §5.5. A wire shape with two spellings of
the lane is a wire shape where they can disagree. `detail` says of itself that it
is not part of §6.5's shape — "a reason code is not a diagnosis". And
`chunkPostmarks` is real evidence that is *not* a §5.7 Postmark, lacking
`ledgerTag`, `topicId`, `envelopeId` and `chunkIndex`, so publishing it inside a
§6 output would put a non-§5 shape into the §6 surface.

**`_meta` is the right home because §14.2 already uses it that way.** The
counter's quote rides in `_meta` and never in `structuredContent`
(`check:exchange`), for exactly this reason: it is real, it is wanted, and no
schema says it is the output.

**CLAUDE.md §9's rule applies to shapes as much as to readers.** "A schema
validates a document against its shape, not against a rule that reads it", and
every writer is built in the same step as its reader. The reader here is the
client's validator, and until `check:outputs` there was none on this side.

## Consequence

- `app/sdk/structured.ts` is new and all six verbs route through it, `verify`
  included — its shape is right today, but the handler spread whatever `verify`
  returned into a wrapper that is `additionalProperties: false`, so the day a
  third field is added the break would have been at a client.
- `app/sdk/outputs.check.ts` is new: **the twenty-third `check:*`**. It reads the
  verb list from the server rather than restating it, so a seventh verb arrives
  with no producer and fails.
- `app/src/mcp/schemas/delivery.output.schema.json` corrects `returnReceipt`,
  which named `urn:wishmail:0.5:return-receipt` and could never have been one.
- **No specification text moves and no version event follows.** The tool input
  and output schemas under `app/src/mcp/schemas/` are release artifacts in the
  `urn:wishmail:app:0.5:` namespace; §18.5 fixes the fourteen in `spec/schemas/`
  by name and none of these is among them. `spec/pins.json` records no digest for
  them and `app/src/ops/schemas13.ts` registers only `spec/schemas/`, from the
  committed git blob. So §1.7's "a change to a registered schema is a new minor
  version" is not engaged.

## Alternatives

**Widen `delivery.output.schema.json` to admit the four keys.** Rejected. That
file exists precisely to spell §6.5's prose — "`{envelope, opened, payload?,
reason?, returnReceipt?}`" — and widening it would make the one file whose job is
to track that sentence disagree with it. It would be a specification change
wearing an implementation change's clothes, and it would bless two spellings of
the lane.

**Declare `payload` as `oneOf [string, {type:'Buffer', data:[...]}]`.** Rejected:
it publishes one language's internals as protocol, and §6.1/T-P15-4 requires
every transport to expose the same schema.

**Leave `_meta` out and drop the extra evidence.** Rejected. The postmarks, the
lane and the diagnosis are what a caller actually wants; the defect was never
that the implementation held them, only that it promised them under a schema that
described something else.
