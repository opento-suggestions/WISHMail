# D-141 — `$POSTAGE` is `decimals: 0`, infinite supply, minted on demand, and carries a supply key and no other

Status:      accepted
Date:        2026-09-07
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    §4.1, §4.2, §4.3, §4.4, §3.5 (no sentence changes; the parameters §4.1 leaves open)
Tests:       T-P7-4, T-P11-1, T-P9-2 — none amended; each constrains a parameter below
Supersedes:  none
Superseded:  the operator-held supply key by D-148, which moved it to the treasury. `initialSupply: 0` was superseded by D-148 and **restored at creation by D-149**, which mints the 10,000 float to the treasury as its own recorded step rather than as a birth parameter; every other parameter here stands
Spec marker: none — no specification sentence changes

## Context

§4.1 fixes what the stamp *is* — "one token, `$POSTAGE`: a fungible token on the Hedera Token Service, identified by the token ID pinned below, whose unit is a stamp," with its supply key held by the Postmaster — and fixes nothing about how it is created. Decimals, initial supply, supply type and every key beyond the supply key are open. Each is a parameter that cannot be changed afterwards without an admin key, so each is decided once, here, before the transaction is built (RECORD, Sonic: "Every parameter the spec doesn't fix … gets an ADR ruling").

## Decision

| Parameter | Value | Where it comes from |
|---|---|---|
| Type | fungible, HTS | §4.1, stated |
| Name / symbol | `WISHMail Postage` / `POSTAGE` | §4.1's token name |
| `decimals` | **0** | forced by §4.4, below |
| `initialSupply` | **0** | below |
| `supplyType` | **INFINITE** | below |
| Treasury | the treasury account (D-140) | §4.1, §4.3, §4.4 |
| Supply key | the Postmaster's | §4.1: "Its supply key is held by the Postmaster" |
| Admin, freeze, wipe, pause, KYC, fee-schedule keys | **none** | below |

### `decimals: 0` is forced, not merely preferred

A HIP-991 fixed fee is written in the denominating token's **base units**. §4.4's MUST is "a HIP-991 custom fee of **exactly one stamp**, in the stamp token, collected by the treasury." At `decimals: 0` a fee `amount` of 1 *is* one stamp and the normative sentence and the on-ledger fee are the same fact. At any other value they diverge: at `decimals: 2` a doorbell whose fee is one stamp carries `amount: 100`, and a doorbell whose fee reads `amount: 1` charges a hundredth of a stamp — a thing §4.4 does not contemplate and T-P7-4 would have to be rewritten to describe (RECORD, Sonic's sharper reason, 2026-09-07).

The softer arguments hold beside it and are recorded because they are independent: §4.2's `weight = max(1, ceil(ciphertext_bytes / OUNCE_BYTES))` yields whole stamps, and `StampReceipt.amount` is `integer, minimum 1` in `spec/schemas/stamp-receipt.schema.json`. A stamp is a countable object in every place the specification touches it. Fractional postage is not a thing WISHMail has.

### `initialSupply: 0`, `supplyType: INFINITE`, minted on demand

§4.3 permits the Postmaster to burn consumed stamps from its treasury and calls a burn "bookkeeping"; L-12 records that this release burns nothing. So supply only ever grows, and a finite cap would be a number this document would have to justify and a future deployment would have to migrate past. A pre-mint is worse: it invents a supply figure with no basis, and it puts stamps in existence that no one bought, which makes the treasury balance stop meaning "postage sold and not yet consumed."

Minting on demand keeps the invariant readable: **stamps come into existence when they are bought and leave circulation when they are consumed.** The supply key is exercised inside `buy_stamp`, which is downstream of this phase; this phase creates the token with none.

### Keys: the supply key, and nothing else

The default answer to any further key is **none** (RECORD, Sonic: "any admin/freeze/wipe/pause key needs a justification that survives P-2 and L-12, and the default answer is none"). None of them clears that bar:

- **Admin key.** It would let the Postmaster mutate — rename, re-key, re-treasury, change fees on — the very token a Verifier measures postage against. P-2 says nothing the Postmaster says is a postmark; an admin key would make what the Postmaster says about the token retroactively load-bearing. A Verifier that reads the token's properties at replay must read the same properties the sender read at settlement, and only immutability guarantees that.
- **Freeze and wipe keys.** Either lets the Postmaster reach into a holder's account and unmake postage already paid for. §4.3 makes an affixed stamp a fact of the ledger and F-3 explicitly protects the orphan case — "the letter is still stamped, still on the counter" — which a wipe key would falsify at will. A bearer unit (§4.1) that the issuer can confiscate is not a bearer unit.
- **Pause key.** It would let the Postmaster halt settlement globally, which is a broadcast-shaped power over every correspondent at once and is refused on the same ground.
- **KYC key.** It would gate who may hold postage, contradicting §4.5's uniform postage and P-11 directly.
- **Fee-schedule key on the token.** No custom fee is set on `$POSTAGE` at all, so there is nothing for it to schedule; the doorbell's fee is a property of the *topic* (HIP-991), not of the token, and D-138 already omits the topic's fee-schedule key for the parallel reason.

The supply key survives because §4.1 requires it: "the Postmaster is whoever holds it." It is the one authority the specification grants, and it is the reason Q-7 (§19.3, how the supply key changes hands) is open and stays open.

### The tail: this is terminal, and the BUILD accepts it

With no admin key the token's treasury can never be changed. **Loss of the treasury key is therefore terminal for the deployment** — every unissued stamp is stranded, no doorbell fee can be collected, and the token cannot be re-pointed at a new account. On `hedera:testnet` that means a rebuild: new token, new pins, new price list, a new claim.

This BUILD accepts that (RECORD, Sonic 2026-09-07: one sentence, "No procedure, no on-ledger recovery path, deliberately"). A mainnet deployment would need a custody procedure, and this ADR does not supply one. §15.5 already holds `hedera:mainnet` as defined and undeployed; the custody gap is one more reason it is.

## Alternatives considered

- **`decimals: 8`, matching HBAR's convention.** Rejected: it breaks §4.4's "exactly one stamp" as an on-ledger quantity, for the reason above. Convention is not a reason to make a normative sentence untrue.
- **A finite `maxSupply`.** MINE, rejected: any cap is arbitrary, and reaching it would strand the service. §4.3's burn permission makes supply a flow, not a stock.
- **Pre-mint a working supply into the treasury.** MINE, rejected: it invents a number and destroys the reading of the treasury balance.
- **Keep an admin key "just for the hackathon," to allow a fix.** MINE, rejected, and this was the tempting one. The token is pinned into `spec/pins.json` and named by every claim; a token that can be mutated after a Verifier has measured against it is not a fixed point, and the whole of §9's replay reasoning assumes a fixed point. A mistake in the token's parameters is better fixed by creating a new token and re-pinning — which is visible — than by an admin key nobody can see was not used.
- **Keep a wipe key for abuse response.** Rejected on P-2 and on §4.1's bearer property; abuse response that reaches into accounts is exactly the authority a courier must not have.

## Consequences

The token is created in one transaction signed by **both** the treasury key (a token's treasury must sign its creation) and the payer, with the supply key set to the Postmaster's. That is the second reason the treasury account precedes the token in the forced order; the first is that §4.1 requires a treasury at creation.

Verification reads the token back from the mirror node — not from the SDK receipt — and asserts `treasury_account_id`, `decimals: 0`, `supply_type: INFINITE`, `supply_key` set, and `admin_key`, `freeze_key`, `wipe_key`, `pause_key`, `kyc_key`, `fee_schedule_key` all null. Those six nulls are the check that this ADR was honoured, and they are the reason it is worth stating a key posture as an absence rather than as an intention.

`spec/pins.json` gains `stampToken["hedera:testnet"] = {tokenId, treasury}` and nothing else (§18.4, D-144). Two of its 32 nulls close; 30 remain, so T-P9-2 still blocks every claim, correctly.

This ADR is the concrete instance of the DIVERGENCE recorded in `app/OPERATIONS.md`: `create_fungible_token_tool` exposes one boolean about the supply key and no parameter for any of the six keys ruled absent here, so the posture could not be *stated* through it, let alone claimed. `@hashgraph/sdk@2.81.0` states all of it.
