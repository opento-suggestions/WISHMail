# D-149 — The HIP-991 probe is wholly disposable, and `$POSTAGE` is born at zero and minted as a step

Status:      accepted
Date:        2026-09-08
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    §4.1, §4.3, §4.4 (no sentence changes; deployment facts and a probe method)
Tests:       T-P7-4 — not amended; the probe observes both of its halves before a doorbell exists
Supersedes:  D-148's probe warrant and its `initialSupply: 10000` at creation; D-141's `initialSupply: 0` is restored at creation, with the float arriving by a recorded mint
Superseded:  none
Spec marker: none — no specification sentence, no schema and no test changes

## Context

D-148 raised `$POSTAGE`'s `initialSupply` from 0 to 10,000 on one stated warrant: that the HIP-991 probe could then fund a stranger and demonstrate T-P7-4's charged half **positively**, rather than negatively as a stranger failing for want of a stamp. The probe was to run on the real token and the real treasury.

Designing the probe's gate report showed why it should not. A probe that shares the deployment's token binds the first thing this build writes to consensus to the entities every later conformance claim depends on, and it does so before anything about the fee configuration has been observed at all. If the fee configuration is wrong, the wrongness is attached to `$POSTAGE` itself — a token that, by D-141's key posture, has no admin key and can therefore never be corrected.

With the probe moved off the real token, D-148's warrant for the pre-mint no longer carries. The question was whether the pre-mint survives on its remaining grounds.

A second question surfaced in the same report. HIP-991 charges the fee to the submitting account (`hip-991.md:101`, ledger §H) and a Hedera transaction has one payer, so "the operator pays every network fee" (D-47) and "a funded stranger is charged one unit" cannot both hold of the same submission. §4.4 describes the sender transferring a stamp *to the Postmaster*, which then pays the doorbell fee — which is why D-140 makes the operator the momentary bearer of the first-contact stamp and why the operator must be associated with `$POSTAGE` at all. Two readings, and they create different entities.

## Decision

Three rulings (RECORD, Sonic 2026-09-08).

### The probe is wholly disposable

It creates **its own treasury account, its own token, its own topic and its own stranger**. The real `$POSTAGE`, the real treasury and the Postmaster-agent's topics are not created, touched or named by it. Nothing permanent is created for it and nothing it creates is kept.

It **mirrors the real shape exactly** — the token's parameters and key posture, the topic's memo-less doorbell policy under D-138, the one-unit fee collected by its own treasury, the exempt list — because a probe that proves something about a different shape proves nothing about the template, and the template is what it exists to prove.

It writes **nothing** to `app/deployment/hedera-testnet.json` and nothing to `spec/pins.json`. Those are the ledgers of what the deployment keeps, and the deployment keeps none of this. `app/OPERATIONS.md` is the whole record of the probe: every entity ID, transaction ID, consensus timestamp and mirror-node read that carries an observation.

The probe gets **its own gate report before any signature** — what it creates, what it asserts, what it reads back, what it leaves on the network — because it is the first time this build writes to consensus, and the record should show that was known in advance. Nothing is signed until Sonic says so.

### `$POSTAGE` is born at `initialSupply: 0` and the float is minted as its own step

The token is created with **`initialSupply: 0`**, which is D-141's value restored. The provisioning script then mints **10,000 units to the treasury as a separate, recorded step**, with its own transaction ID and consensus timestamp in the ops record.

**`supplyKey` remains the treasury's**, unchanged from D-148 and for D-148's reason: the supply lands in the treasury, the treasury's key is already hot for §14.2's atomic purchase, and one key does one job rather than the operator holding minting authority over a balance it cannot move.

The float itself survives D-148's lost warrant on its remaining grounds: a supply the Postmaster-agent can ring and be rung with before `buy_stamp` exists as a mint path, and a known quantity to read back. What changes is *how it arrives*. A birth parameter is a fact about a transaction nobody looks at again; **a mint is an act, with a transaction ID a Verifier can replay** (P-3), and it makes the supply key's first use visible on consensus rather than folded into the token's creation. It also keeps §4.1's `INFINITE` and mint-on-demand literally true of the deployment rather than true-with-an-exception, which is what D-141 was protecting when it wrote "a pre-mint invents a number".

This applies to the probe token too. The probe mirrors the template, and the template is now birth-at-zero followed by a mint, so the probe's token is created the same way and its mint is one more thing the probe observes before the real one is attempted.

### The probe observes the charged path under both payers

Rather than choosing a reading of `:101`, the probe makes the answer an observation. It submits twice on the charged path:

1. the **stranger as payer** of its own submission, holding the unit; and
2. the **operator as payer**, carrying the stranger's unexempted signature — §4.4's own shape.

`GET /api/v1/transactions/{id}` is read for both and **which account was actually debited the unit is recorded verbatim**. One extra transaction settles §4.4's routing question and the fee mechanism in the same run.

## Alternatives considered

- **Keep D-148's pre-mint at creation, re-grounded** (the drafted lean). Rejected in favour of the mint as a step: the grounds hold either way, but a birth parameter cannot be replayed as an act and does not exercise the supply key.
- **Revert to `initialSupply: 0` with no float at all**, leaving T-P7-4's charged half until `buy_stamp` exists. Rejected: the doorbell is created long before `buy_stamp`, and a doorbell whose fee has never been seen to be assessed is a doorbell nobody has tested.
- **Run the probe on the real `$POSTAGE`** (D-148's shape). Rejected: it binds the deployment's uncorrectable token to the first unobserved write to consensus.
- **Give the probe token an admin key so it can be deleted.** MINE, rejected: it would stop the probe from mirroring D-141's key posture, which is the thing under test. The residue is accepted instead, and written down.
- **Choose a reading of `:101` and test only that.** Rejected: the record would then carry an inference where an observation was available for one transaction.

## Consequences

`spec/adr/D-148.md` gains `Superseded:` for its probe warrant and its `initialSupply: 10000`, and keeps its text; its supply-key ruling stands. `spec/adr/D-141.md`'s pointer is corrected: D-148 moved the supply key and raised the initial supply, and D-149 restores the initial supply at creation while the float arrives by mint.

**The probe leaves an inert token and its treasury on `hedera:testnet` permanently.** The token carries no admin key, so `TokenDelete` cannot be used; a token's treasury cannot be deleted while the token exists. The topic is deleted under its admin key on every path. This is the price of mirroring the key posture honestly, it is paid on a test network, and `app/OPERATIONS.md` says so rather than leaving a reader to wonder what the second `$POSTAGE`-shaped token is.

Ledger §H gains the probe's rows when it runs: the collector-association question, currently MINE, becomes FETCHED; the mirror node's actual name and shape for the fee-exempt list becomes FETCHED rather than an inference from a protobuf field name; whether `GET /transactions/{id}` returns `entity_id` is answered for the provisioning journal; and `:101`'s payer is observed under both readings.

The v0.5.2 tag's message summarises D-148 as pre-minting `$POSTAGE`. That was true of 0.5.2 and stays in the tag: D-149 changes no specification sentence, no schema and no test, so the text v0.5.2 names is unaffected and the tag is not moved.
