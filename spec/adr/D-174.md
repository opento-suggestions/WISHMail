# D-174 — The Outbound Connection Created record is written on BOTH parties' logs, because the pin cannot be made to say one thing

Status:      accepted
Date:        2026-09-10
Decided by:  Sonic

## Context

**FETCHED 2026-09-10** from the pinned blob itself — `docs/standards/hcs-10/index.md`
at commit `7046156c85eaaf29e149fa10232964d33a58d34e`, git blob sha
`0cb5d2eb6b98e12e4b44fa8c4fea6e10937b615a`, **verified equal to the sha
`spec/pins.json` carries**, so this is the pinned text and not a later revision.

HCS-10's outbound topic carries three operations (`index.md:524-620`), each with
its own transaction memo. The *Outbound Connection Created* operation
(`index.md:558-588`, memo `hcs-10:op:4:2`) **contradicts itself about which party
writes it**:

| Where | What it says | Which party |
|---|---|---|
| `index.md:529` | "Record of a connection created **by the agent**" | acceptor |
| `index.md:560` | "Recorded on an agent's Outbound Topic when it successfully processes a `connection_request` and creates a new Connection Topic" | acceptor |
| `index.md:585` | `confirmed_request_id` — "the sequence number of the `connection_created` message **received** on the agent's inbound topic, confirming the connection request" | requester |
| `index.md:586` | `connection_request_id` — "the sequence number of the original `connection_request` **sent by this agent**" | requester |
| `index.md:587` | `operator_id` — "the agent that **confirmed** the connection (**the recipient of the original request**)" | requester |

`requestor_outbound_topic_id` (`:584`) is redundant under the requester reading
and load-bearing under the acceptor's, which is a sixth piece of evidence and
points the other way from the prose.

**This is C-6's class of defect** (ledger §H): a pinned Draft standard whose
prose and whose field table point opposite ways. P-9 makes conformance to the
blob rather than to a reading of it, so there is no reading this project is
entitled to call the right one.

## Decision

**RECORD (Sonic, 2026-09-10), closing ledger §G-24:** for this MVP build, write
the record on **both** parties' outbound logs — the acceptor's when it answers,
the requester's when it learns the lane — each with the pinned transaction memo,
each carrying the required fields **under the reading that has that party
writing it**. Cost: one message per party. **A strict reader under either
reading finds the record it expects.** The contradiction is recorded FETCHED and
**not resolved**: the implementation satisfies both readings rather than choosing
between them.

## What the records buy, and what they do not

**RECORD (Sonic, 2026-09-10), correcting an overreach of this project's own first
wording**, which said such records would make the home's address book
*unnecessary*:

> **The outbound records are the primary enumeration path from the fix forward;
> the home's address book is the fallback for lanes whose records predate the fix
> or were never completed; consensus is the only authority on whether a lane
> exists.**

Going forward the walk is: own log → the target's doorbell → the
`connection_created` naming that request → the lane, shortened to one hop where
the requester-side record is there.

**Three things keep the fallback necessary rather than merely nice.**

1. **A2's lane with B is a permanent counterexample.** Its one outbound record is
   in the inbound shape, names itself, and cannot be edited, so A2 can find
   `0.0.10464056` only by knowing it wrote to B — and **every lane rung before
   this fix, on any deployment, is in that class.**
2. **The requester-side record is written when the requester LEARNS the lane**,
   which is a submit→learn window like every other. A ring answered while the
   sender's process was down, or a write that failed after the lane landed,
   leaves the acceptor's doorbell holding the truth and the requester's log
   holding only the request. Enumeration through the request record still works;
   the one-hop path is **best-effort, not guaranteed**.
3. **Neither log is authoritative.** §7.1's rule is the `connection_created` on
   the doorbell; the outbound records are HCS-10's convenience and this
   project's conformance, not the source. **Whatever `lanesOf` starts from,
   every candidate is confirmed against the counterparty's doorbell before it
   counts** — which is what the code already does, structurally, rather than by
   an added check.

## How each half fills the five required fields

**The acceptor's** (`outboundConnectionCreatedByAcceptor`, written by
`sdk/watcher.ts`): `outbound_topic_id` its own log; `requestor_outbound_topic_id`
the requester's, read from the requester's HCS-11 profile through the same
`resolveHcs14` a `resolve` call uses; `confirmed_request_id` the sequence number
of the `connection_created` it has just posted on its own inbound topic — it
*receives* none, and that is the only acceptor-side reading of `:585` available;
`connection_request_id` the sequence number of the request it answered, the same
number its `connection_created` carries as `connection_id`; `operator_id` itself,
because under this reading the writer is the confirmer.

**Two of those five are strained**, and the strain is the contradiction rather
than a choice made here. It is recorded, not smoothed over.

**The requester's** (`outboundConnectionCreatedByRequester`, written by
`tools/send.ts`): `outbound_topic_id` its own log; `requestor_outbound_topic_id`
its own log again — **redundant, which is itself evidence for the other reading**,
written because the field is required and not because it adds anything;
`confirmed_request_id` the sequence number of the answer on the *acceptor's*
door, which is why `Lane` now carries it; `connection_request_id` its own ring's
sequence number, exact and available to no one else; `operator_id` the acceptor,
which is what `:587` says and what an acceptor's own record could not say.

## Order, failure, and idempotency — the three properties that make this safe

- **The doorbell's `connection_created` goes first and the log record second.**
  §7.1 binds a lane by the answer on the doorbell. A failure after that line
  leaves the lane born, announced and findable, which is the whole reason for
  the order.
- **Neither write is fatal.** In the watcher every failure is returned as
  `outboundRecordSkipped` and none throws: an exception there would make the
  error handler the last word on a lane that exists, and the next tick would not
  re-answer it, because the doorbell now holds the answer. In `send` a failure
  is swallowed deliberately — **a log entry must never cost a letter**, and the
  lane is open with the ring's stamp already spent.
- **Both are idempotent from consensus, never from local state** (D-165's rule
  applied to a log): each reads its own log for a `connection_created` naming
  this lane before writing. A duplicate would make an agent's own log disagree
  with itself about how many lanes it has.

A requester that declares no outbound topic is not an error either: the acceptor
skips its record with a stated reason, because `requestor_outbound_topic_id` is
required and cannot be invented.

## Alternatives considered

- **Pick the acceptor reading** (prose and table). MINE, rejected: it duplicates
  what the acceptor's own doorbell already holds and leaves a requester with no
  consensus record of its own lanes at all — the thing that raised §G-24.
- **Pick the requester reading** (three of five field descriptions). MINE,
  rejected: it makes the prose and the operation table wrong, and P-9 makes
  conformance to the blob, not to the majority of its sentences.
- **Write neither and wait for upstream.** Rejected: this deployment rings real
  doorbells now, and a lane opened today can never be recorded retroactively —
  §G-24 exists *because* A2's lane is already past repair.
- **Ask upstream first.** Not an alternative but a parallel: the issue text is
  drafted in `provenance/` in §G-24's own shape — file, line, the two readings,
  no opinion — for Sonic to send or not.

## Consequences

- `ops/hcs10.ts` gains `TRANSACTION_MEMO.outbound_connection_created`
  (`hcs-10:op:4:2`, `index.md:576`), the two body builders, and
  `outboundCreatedRecordFor` — the idempotency reader both writers consult.
- `sdk/watcher.ts`'s `answer()` returns `outboundRecord` or
  `outboundRecordSkipped`, so a run of record can say what landed and what did
  not. `tools/send.ts`'s `Lane` gains `answerSequenceNumber`.
- `check:hcs10` is **63 assertions**: every required field on both records, the
  memo, and the three places the two readings part. `check:letter` is **187**,
  up from 155: both logs hold their record after a first contact, in their own
  shapes, and a second letter records nothing twice.
- **`check:letter`'s modelled acceptor writes the record too**, which is
  CLAUDE.md §12's rule applied before it could bite: a model that did not would
  diverge from the wire on a field a strict reader now looks for — the same
  defect the lane memo `hcs-10:1:60:3` was.
- **The acceptor's write has no offline court for its behaviour**, only for its
  shape: `answer()` takes a `Session` and a network. It fires for the first time
  live in Gate Three, and the gate report says what it is expected to look like
  on both logs before it runs.
- **One outbound record already on consensus predates all of this and is not
  repaired**: A2's log `0.0.10462708` #1, in the inbound shape with two required
  fields absent. Named in LIMITATIONS L-1. Rewriting a consensus record is not
  available and manufacturing one would be worse.
- Closes ledger **§G-24**, its finding kept unedited beneath the ruling. The
  contradiction stays on the record as a fact about the pinned text.
