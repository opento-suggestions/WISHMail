## Context

D-70 requires a declaring agent to use the HCS-2 registry, and the incumbent HCS-10 agents in the wild all use a direct HCS-1 memo. Refusing to read them would have made the native profile unable to resolve the agents that exist.

## Decision

The record, from ledger §B row D-107, verbatim:

> **`hcs14` accepts a direct HCS-1 memo** (`hcs-11:hcs://1/<file>`) as a second form: the file is `math` (hash-anchored, immutable) but the account→file binding at `resolvedAt` is a memo whose past values are not re-obtainable, so the rule assigns `blurred` and carries the memo as a snapshot. Declaring under `hcs14` still requires HCS-2 (D-70 stands for WISHMail's own agents — rotation history, T-P8-3). UAID comparison is on identifier + `nativeId`; parameters outside the hash are routing hints (HCS-14 `index.md:846`). Why: both live HCS-10 ("OpenConvAI") agents declare this way and HCS-11's own example does; without this form WISHMail cannot address an incumbent. Approved by Sonic 09-06.

## Alternatives considered

- None recorded. The ledger §B row states the decision without a fork; where a fork was closed, the row says so.

## Consequences

`hcs14` accepts `hcs-11:hcs://1/<fileTopic>` as a second form **for reading**. The file is `math` — hash-anchored and immutable — but the account-to-file binding at `resolvedAt` is a memo whose past values are not re-obtainable, so the rule assigns `blurred` and carries the memo it read as a snapshot (§9.2, T-P6-3). Declaring still requires the HCS-2 form (D-70), and a fixture that declares with a direct memo fails the RECIPIENT suite (T-P8-3).
