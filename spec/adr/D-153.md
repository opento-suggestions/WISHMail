## Context

D-152 settled which canonical key orders a rule **accepts** when it recomputes
someone else's agent identifier: both, the lexicographic one first, with the
match reported as an observation. It deliberately did not settle which order
WISHMail **emits** for its own declaration, and that stayed open as ledger §G
item 12, because the two questions have different stakes: acceptance is a
reading rule that can be changed in a release, while emission is written into an
HCS-1 file topic, which HCS-1 forbids an admin key precisely so that "data
cannot be deleted" (`hcs-1.md:48-49`). What we emit, we emit permanently.

Sonic asked for a census before ruling. FETCHED 2026-09-08, mirror-node REST
only, recorded in ledger §H:

| agent | sequence | consensus | protocol | registry | reproduces under |
|---|---|---|---|---|---|
| `0.0.7124407` | 153 | 2025-10-24T22:10:46Z | `hcs-10` | `hol` | example |
| newest on the anchor | 380 | 2025-11-18T22:05:58Z | `a2a` | `hashgraph-online` | example |

and across the fourteen newest `uaid:aid:` registrations plus `0.0.7124407`:
**15 of 15 under the example order, 0 under the normative one, 0 under neither**,
every profile readable and every HCS-1 memo digest matching.

## Decision

**WISHMail emits its own `uaid` under the example's order — `skills` first, then
`name`, `nativeId`, `protocol`, `registry`, `version`.** Ruled by Sonic,
2026-09-08. Ledger §G item 12 is closed.

`CANONICAL_ORDER` in `app/src/core/hcs14.ts` is `'example'` and is the default
of `canonicalAgentJson`, `agentIdHash` and `uaid`, so no caller in the build
names an order any more. The parameter remains, because reading another agent's
registration means computing both, and `npm run check:hcs14` keeps both live
agents as vectors under explicit orders.

**D-152 stands unchanged.** Emitting one order does not narrow what we accept.

## Why this is coherent and not merely pragmatic

The pragmatic argument alone would be uncomfortable: it would have WISHMail
follow a worked example over a sentence the standard marks normative, on the
ground that everyone else does. What makes it coherent is that we are also
saying so upstream.

Ledger §G.5(b) drafts the defect for submission: that step 3 and the reference
function should be amended **to the example's order**, because the example's
order is what every deployed implementation computes and changing it would
orphan every identifier already on the ledger; and that `{base58hash}` should be
replaced in both test vectors with the computed value, so the next implementer
finds the answer in the document. We are not quietly conforming to the majority;
we are emitting what we have argued in public should be normative, and D-152's
fallback means we lose nothing if the argument fails.

The alternative reading — emit the normative order and wait for the world to
follow — has the same shape as inventing a deployment artifact to make a claim
true, which STATUS §1 already refuses in another context: it would make our
declaration correct against a sentence and wrong against every reader.

## The counter-argument, as Claude Code wrote it

Recorded because it is real and because a reader deciding what to trust should
see what lost, in the words it lost in (ledger §G item 12, MINE):

> **(b) emit the normative order**, on the ground that step 3 is the sentence
> the standard marks normative, that an upstream fix (G.5b) would make it right,
> and that D-152's fallback means incumbents can still resolve us — the cost
> being that we would be the only agent on the ledger they need the fallback
> for.

Two things weigh against it, and the second is the one that decides. The first
is reach: D-152's fallback is *ours*, and an incumbent resolver that implements
only what HCS-14's normative step says would compute one identifier, find it
disagreed, and fail — the fallback protects agents we read, not agents who read
us. The second is permanence: acceptance can be widened in a later release,
emission cannot, because the identifier is inside a file whose topic has no
admin key. Where one choice is reversible and the other is not, the irreversible
one goes to what is observed rather than to what is asserted.

## Consequences

No specification sentence changes, no schema changes, no test is added, moved or
amended; the register stays 83 and the version stays **0.5.4**. This is a
deployment decision of the same kind as D-138's provisioning template: §9.1
governs comparison and is unchanged, and nothing in §9.2's "Declaring under it"
fixes a key order.

The `hcs14` declaration is unblocked. What it writes is permanent: an HCS-1 file
topic has no admin key, so the identifier this decision chooses is the one that
stands, and a change of mind is a new profile file registered as a new entry
with the old one still readable (§9.2:1284).

If the upstream proposal succeeds, this decision needs no revisiting — the
emitted order becomes the normative one and D-152's fallback stops firing on its
own. If it fails, `spec/pins.json` pins HCS-14 by blob, so a later revision of
the standard reaches us only through a deliberate re-pin (§1.6, L-7).
