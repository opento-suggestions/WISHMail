## Context

§14.3 requires a price message on consensus before anything is charged under it, and fixes that the numbers are the Postmaster's: "Every number is the Postmaster's; this document fixes that there is one schedule, that it is on consensus before it is charged, and that it is the same for everyone (§4.5)." §19.2 holds the numbers open as Q-6. This ADR records the deployment's first schedule, which is the message that makes `buy_stamp` legal at all.

## Decision

**The numbers** (RECORD, Sonic 2026-09-06 and 2026-09-07, ledger §E Q-6): **$0.10 per stamp**, and a **bundle of 12 for $1.00**. The bundle is offered on **both** methods (RECORD, Sonic 2026-09-07: "The bundle applies to both methods").

**The shape**, per §14.3 as amended by D-136:

```jsonc
{
  "spec": "0.5.1",
  "stampToken": { "ledgerTag": "hedera:testnet", "tokenId": "<created>", "treasury": "<created>" },
  "methods": [
    { "method": "x402-usdc", "network": "hedera:testnet", "asset": "0.0.429274",
      "payTo": "0.0.8641261", "facilitator": "https://x402.org/facilitator",
      "unitPrice": "0.10", "bundles": [ { "count": 12, "price": "1.00" } ] },
    { "method": "hbar", "network": "hedera:testnet", "asset": "0.0.0",
      "payTo": "0.0.8641261",
      "rate": { "source": "https://api.saucerswap.finance/tokens", "pair": "HBAR/USD",
                "reference": { "amount": "0.10", "asset": "USD" } },
      "bundles": [ { "count": 12, "price": "1.00" } ] }
  ],
  "validFrom": "<unresolved — see below>"
}
```

**The `x402-usdc` method is fixed-priced.** Its asset *is* the unit the price is quoted in, so `unitPrice` is literal: `"0.10"` USDC per stamp, `"1.00"` for twelve. It carries `payTo` **and** `facilitator`, which is the inclusive reading of §14.3's first pipe (D-136): §14.2 has the `PAYMENT-REQUIRED` carry "the Postmaster's receiving address," so an x402 method needs `payTo` beside its facilitator, not instead of it. The facilitator is FETCHED and live — `GET https://x402.org/facilitator/supported`, 2026-09-07, returning `{"x402Version":2,"scheme":"exact","network":"hedera:testnet","extra":{"feePayer":"0.0.9185802"}}` with testnet USDC `0.0.429274` at 6 decimals, matching the mirror node (D-132).

**The `hbar` method is rate-priced and carries no `unitPrice`.** HBAR's price in dollars moves, and the schedule is written once; a published `unitPrice` in HBAR would be a number the Postmaster does not charge, which §14.3's own MUST forbids ("MUST charge exactly what the price message current at the purchase yields"). So it carries `rate`: `reference` is $0.10 USD per stamp, and `source` and `pair` name what is read at purchase to convert it. **The bundle's price follows the method's basis** (RECORD, Sonic: "a bundle price follows the method's pricing basis") — so `"1.00"` on the `hbar` method reads "twelve for one US dollar," converted at purchase by the same rate that converts `reference`, and not "twelve for one HBAR."

**`asset: "0.0.0"` for HBAR is inherited, not invented** (RECORD, Sonic 2026-09-07). SaucerSwap's `/tokens` response returns HBAR as `id: "0.0.0"` (FETCHED 2026-09-07, alongside `priceUsd: 0.08246267`), and that endpoint is the `rate.source` this very message names — so the price list adopts the identifier of the shape it reads, and a reader of the price list and a reader of the rate see one HBAR. It corroborates independently: the pinned x402 Hedera `exact` scheme uses `0.0.0` for HBAR in tinybars (`recon/hol-x402-recon-2026-09-06.md:352`), so the convention is the same on both sides of the purchase.

**`provisioning` is omitted.** §4.6 makes the provisioned path optional and D-57 makes provisioning never required; this deployment offers no priced provisioning in this window, and an omitted optional field says that more honestly than a number would.

**Only these two methods, and the POSTMASTER claim is deferred on T-P16-1** (RECORD, Sonic 2026-09-07). The MVP BUILD covers pre-funded Hedera accounts only. §14.2's MUST — "At least one method the Postmaster offers MUST require no pre-funded Hedera account of the buyer" — is therefore unmet by this deployment, and **no non-Hedera method is invented to make the claim true.** The deferral is stated in `LIMITATIONS.md` where §15.5 expects it and in `STATUS.md` §4. The underlying contradiction between §14.2:1766 and `LIMITATIONS.md:63` is a spec question logged in ledger §G item 8, deliberately not patched in 0.5.1.

### `validFrom` — unresolved, and reported rather than ruled

The schema requires `validFrom` and types it as a consensus timestamp (`^[0-9]+\.[0-9]+$`, seconds.nanos). **The specification defines it nowhere.** It occurs exactly once in the whole document — as a line in §14.3's shape block at `:1805` — and no sentence, ledger row, or prior ADR says what it means. Worse, the plan's working assumption ("the message's own publication timestamp") is not implementable: a message's bytes are fixed before consensus assigns it a timestamp, so it cannot contain its own.

And §14.3's reading rule does not use it. Currency is defined against the **message's** consensus timestamp: "The price current at a purchase is the latest price message with a consensus timestamp before the purchase's." A `validFrom` that meant anything different would be a second, competing notion of when a price takes effect.

This is a specification gap, not a build choice, so it is raised for ruling and not decided here (CLAUDE.md §5). The candidates, MINE:

1. **Informational, set to the Postmaster's clock at submission.** Smallest change, no spec text; but it publishes a number nothing reads, in a required field.
2. **Drop it from the shape and the schema.** Honest — the reading rule already works without it — but it removes a field from a shape block, which under §1.7 is a schema change, patch-level only while nothing is registered.
3. **Give it meaning: the earliest purchase this schedule may price**, letting a Postmaster post a schedule ahead of its effect. Most useful, largest change: it needs prose, and it needs T-P11-4 to say which of the two timestamps governs when they disagree.

The first `PriceList` is not published until this is ruled. Nothing else in Phase B depends on it — the token, the topics and the probe all precede publication.

## Alternatives considered

- **Publish an `hbar` `unitPrice` snapshotted at publication time.** Rejected in D-136: it publishes a number nobody charges.
- **Offer the bundle on `x402-usdc` only.** Rejected by Sonic: the bundle applies to both.
- **Read the `hbar` rate from a testnet HBAR/USDC pool ratio.** MINE, rejected on the evidence: testnet USDC `0.0.2202688` prices at `0.0147` on SaucerSwap — pool noise, not a dollar. The read is HBAR's own `priceUsd`, which is why `pair` is `HBAR/USD` and not `HBAR/USDC`.
- **Add a third, non-Hedera method to satisfy T-P16-1 now.** Rejected by Sonic explicitly: the deferral is stated rather than dodged.

## Consequences

The message is published on the price topic (D-142) after the token exists, since it names the token. It is validated against `spec/schemas/price-list.schema.json` before submission and byte-compared after, by reading it back from the mirror node — `GET /api/v1/topics/{id}/messages` — rather than trusting the receipt.

`buy_stamp` becomes legal only once this message is on consensus (§14.3's MUST). The rate **reader** is `buy_stamp`'s and is downstream of this phase; two shape facts are recorded in ledger §H for whoever writes it: the singular `/tokens/{id}` endpoint rejects `0.0.0` ("Token ID 0.0.0 is not valid"), so the read is the list filtered to `id === "0.0.0"`; and the field is `priceUsd`. Whether that needs the 09-06 fallback order — a fixed unit price at HBAR = $0.07 if the source fails — is a finding for the code phase, not built on now.
