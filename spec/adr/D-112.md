## Context

HCS-14 forms a NANDA agent's `nativeId` as a domain, and a `urn:ai:email:` identity has no domain that names the agent — so WISHMail would have had to invent the rule.

## Decision

The record, from ledger §B row D-112, verbatim:

> **§16.4 (NANDA email-identity `nativeId`) struck as an extension; held in §16.8 and proposed upstream.** Sonic 09-06: "proposing it is a good move — even if they don't accept or merge it in the window, it highlights what the spec is still." Verified from the NANDA recon §5.1 (FETCHED 09-06, hiero @ `7046156c`): `hcs-14/index.md:187` defines `nativeId` with "domain for A2A/NANDA"; `:373` says an A2A agent's `nativeId` SHOULD be its agent-card domain; no text on either side addresses `urn:ai:email:` — a definition-bullet example, not an uppercase MUST, so the rule would have filled a gap HCS-14 owns rather than broken a requirement. The rule has no consumer in the core: §9.4 resolves from URN + host and forms no UAID; §9.2/§9.5 need a Hedera-account `nativeId`. Until HCS-14 states a rule, WISHMail forms no UAID for such an agent. T-P5-4 dropped; §16.5–§16.9 renumbered §16.4–§16.8. Proposal text to HCS-14 is a repo item, not spec.

## Alternatives considered

- State the forming rule in WISHMail as an extension — rejected: the rule belongs in HCS-14's own text, and inventing it here would be WISHMail defining another standard's identifier.

## Consequences

Struck as an extension, held in §16.8, and proposed upstream to HCS-14: the URN as `nativeId`, the index host as `domain`. Until HCS-14 states one, WISHMail forms no UAID for such an agent and the `nanda` profile resolves without one (§9.4). T-P5-4 was dropped from the register with it. Sonic: proposing it is worth doing even if it is not merged in the window, because it shows what the specification is still missing.
