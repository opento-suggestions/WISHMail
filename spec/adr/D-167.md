# D-167 — The resolution proof carries its output by digest, and §9.1 allocates the manifest's byte budget

Status:      accepted
Date:        2026-09-09
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    §5.2, §9.1, §10.2, §11.4
Tests:       none added. T-P9-8 is the court for the budget; T-P6-1 and T-P6-2
             are the court for the digest, unchanged.
Supersedes:  none
Spec marker: CHANGED: D-167 on §5.2, §9.1, §10.2, §11.4

## Context

Closing ledger §G-17, raised by the pre-Step-4 sweep on 2026-09-09. §9.1 requires
a manifest to be one HCS message at or under `CHUNK_WIRE_MAX` = 1000 bytes
(T-P9-8, §7.4, D-96). §5.2 requires a `meaning.statement` and bounds its length
nowhere. Nothing reconciled the two, and at a real address the manifest did not
fit. Measured on the live declaration with the resolver's 190-character
statement: `hcs14` at an account address 997 — three bytes of headroom; at a real
168-character UAID from the anchor 1153; under §9.2's second form 1056; `hol` at
that UAID 1056. Only the shape our own demo uses fitted.

The sweep offered two candidates and Sonic ruled neither.

**Raising §9.1's ceiling above `CHUNK_WIRE_MAX`** buys 24 bytes and no more.
**FETCHED 2026-09-09**, and confirmed two ways: `@hashgraph/sdk` 2.81.0 sets
`CHUNK_SIZE = 1024` (`lib/transaction/Transaction.cjs:63`), which
`TopicMessageSubmitTransaction` takes as its chunk size; and observed directly,
`getRequiredChunks()` returns 1 at 1024 bytes and 2 at 1025. Past 1024 the only
route is `chunkInfo` — splitting one logical message across several consensus
messages — which would mean a manifest reader must reassemble a chunk group
before hashing it, a reference must name the first message of a group rather than
a message, and D-96's one-message-one-locator discipline is gone. Rejected for
this window rather than deferred.

**Bounding `statement` alone** does not reach the two profiles that MUST carry a
snapshot (§9.1's table, T-P6-2): `nanda` was over with the statement at zero.
Necessary but not sufficient.

## Decision

**The coordinates value is what was eating the budget, so it stops travelling.**

§5.2 already gives `output` as `{digest} | value`, and §10.2's "the output is the
coordinates" names *what the output is*, not how the manifest carries it. Ruled:
**the resolution proof's manifest carries `output` as `{digest}`** — the SHA-256
of the canonical JSON of the coordinates the rule resolved — and never as a
value. A form §5.2 already admitted; the ruling makes it the only form for this
proof. §10.4's and §10.5's outputs are untouched.

**The court is unchanged.** §11.4 already required a Verifier to *replay*:
re-obtain the inputs at `inputs.locator`, run the profile's rule at its pinned
revision, and produce coordinates. It compared them to the carried value; it now
hashes them and compares to `output.digest`. Same replay, same inputs, same rule,
same failure on mismatch. T-P6-1 is untouched — the digest is inside the hash.

**D-166 survives.** `manifestTopic` reaches a Verifier by the same replay, at the
proof's own locator and timestamp, so T-P1-8 still has a replay-stable source and
§11.6's bar on deciding a standing from an observation is still respected.

**And then §9.1 writes the budget down.** Computed per profile at each profile's
own worst case — the largest address its grammar admits, and only the
endorsements its own rule can assign — the remainders are `hcs14` 131, `hol` 72,
`dns` 267, `nanda` 205. **N is the smallest: 70 bytes**, and
`proof.schema.json` gives `meaning.statement` a `maxLength` of 70. The binding
case is `hol` at a UAID with §9.2's locator beside its own (§9.5), the largest
locator this document defines.

**Two things this forced that are worth recording as consequences, not
footnotes.**

**The locator gains `address`.** §9.2's "Inputs and locator" list did not name it.
That was harmless while a Verifier could read the address out of the output; it is
fatal once the output is a digest, because the address is the rule's own first
input — "parse the address to an account" — and a locator that cannot re-obtain
the rule's input cannot re-obtain the inputs, which is what §5.2 says a locator is
for. Adding it also moves the 168 bytes of a UAID from `output` to
`inputs.locator`, so the saving is smaller than a naive reading suggests: about
110 bytes at an account address and about the same at a UAID.

**`verify`'s replay had to become real.** It stopped at the registry entry,
because the rule was written against a mirror-node client and a Verifier's
`Reader` could not reach the profile file; the module said so in a comment and
appraised on a partial replay anyway. That is no longer a shortcut — under this
ruling the value is recoverable *only* by running the rule to the end. So §9.2's
rule now runs over a `ProfileSource`: three reads of public data that both a
mirror node and a `Reader` satisfy. One rule, two readers, and they cannot drift.
The letter fixture, which had created a profile-file topic and never written a
profile into it, now stands up a real HCS-1 file — because the reader is what
says whether the writer wrote anything (CLAUDE.md §9).

## Alternatives considered

- **Raise §9.1's ceiling.** Rejected above: 24 bytes, then `chunkInfo`.
- **Bound `statement` alone.** Rejected above: necessary, not sufficient.
- **Drop `address` from the coordinates.** Refused by the sweep and not revisited:
  §10.2 is "the proof that an address became these coordinates", and §5.3 fixes
  `address` as "the typed address, as resolved". The ruling drops nothing — it
  carries the whole value by its hash, `address` included.
- **Digest the whole of §5.3's MailCoordinates**, as the ruling's prose says.
  Refused as literally stated, and this is the one place the implementation does
  not follow the prompt's words: MailCoordinates carries `resolutionProof.hash`,
  which is computed *over* the output, so a digest over the whole object would
  contain itself. The digest is over the **resolved fields** — §5.3 minus
  `resolutionProof` (the proof's own reference), `trustClass` and `endorsements`
  (which live in `meaning`), and `resolvedAt` (the query's clock, which no later
  replay reproduces). That is the ruling's substance exactly, and it is what the
  code already separated.

## Consequences

- `spec/schemas/proof.schema.json`: `meaning.statement` gains `maxLength: 70`;
  `output`'s description names the digest form. **Schema changes, admissible only
  while `registeredSchemas` is null** (§1.7, D-161's reasoning), which is why
  this is 0.5.8 and lands before Step 4.
- Every resolution proof's hash moves again. Nothing is published against an old
  one: no envelope has been assembled on `hedera:testnet`.
- Statements shorten everywhere. The resolver's is 68 bytes, the slip's 66 —
  §10.5's own required words fit inside the budget with four bytes to spare — and
  the receipt's 57.
- Measured after the ruling, wire form, at each profile's short and longest
  address: `hcs14` 725 / 882, `hol` 790 / 790, `dns` 841 / 866, `nanda` 995 /
  1042. **`nanda` at its longest address is 42 bytes over**, and §9.1's
  snapshot-to-digest fallback is what carries it — kept deliberately for this.
  What it costs is stated in §9.1 rather than hidden: such a proof is witnessed
  rather than replayable, which `nanda`'s permanent `blurred` already declares
  (§9.4) and which §11.4 appraises as unverified. No schema moves for it, and
  `nanda` is not on the letter path this window.
- A manifest read off its topic is no longer a document a person can read. Sonic
  ruled that loss acceptable for this build, and §5.2 says so plainly rather than
  leaving a reader to discover it.

## Addendum — 2026-09-09, §10.2 names the domain (0.5.9)

**The text this decision needed and did not land with.** §10.2 said the output is
"the coordinates, carried as the digest of their canonical JSON" and stopped —
and "the coordinates" is §5.3's MailCoordinates, which carries
`resolutionProof.hash`, which is computed over the output. Read literally the
sentence was circular, which is exactly what "Alternatives considered" above says
it must not be. The reasoning was in this ADR; it was not in the specification,
and the specification is what binds.

§10.2 now names the domain positively — `address`, `profile`, `ledgerTag`,
`account`, `doorbell`, `log` where present, `manifestTopic`, `x25519Pub`,
`keyEpoch` — with the four exclusions each given the place it already lives, and
§11.4 cites the same nine. **Sonic's reason for listing them positively, and it
is the right one:** an implementer of a fifth profile then knows what to hash
from §10 alone, without reading an ADR.

One word of the ruling's wording was not taken. Sonic gave the last exclusion as
"not `resolvedAt` (in inputs)", following §5.3's own gloss. This implementation
binds `resolvedAt` nowhere in `inputs` — §5.2 closes `inputs` at
`{digest, locator, snapshot?}` and none of the three is a query clock — so §10.2
gives instead the reason that holds unconditionally: a digest containing the
query's clock could never be matched by a replay at another clock. The gloss
itself is raised as ledger §G-18, unruled, and blocks nothing.

A text-only patch: no schema moved, and `schemas:plan` is unchanged.
