## Context

A specification that names one kind of implementation makes every implementer build everything. WISHMail needed classes so that a reader can build only what they intend to be, and a claim can say which.

## Decision

The record, from ledger §B row D-42, verbatim:

> Conformance classes: VERIFIER is the shared floor; CORRESPONDENT, RECIPIENT, POSTMASTER stand on it; every class includes VERIFIER, none includes another; resolution profiles are an orthogonal axis. RECIPIENT (receive-only, PO box) is a class.

## Alternatives considered

- One undifferentiated 'conforming implementation' — rejected: it would oblige a keyless Verifier to build a Postmaster.
- Nested classes, each including the one below — rejected: a Correspondent need not receive and a Recipient need not send; only VERIFIER is common to all.

## Consequences

VERIFIER as the shared floor is what makes P-3 and P-4 testable at every level: every class must be able to reconstruct from public data. RECIPIENT exists as a class so that a post-office box is a conforming thing to build. Profiles are an orthogonal axis, so a claim names classes and profiles separately (§1.4, §1.5).
