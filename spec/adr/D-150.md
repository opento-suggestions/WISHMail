## Context

§4.6:578 lists what the Postmaster pays to create on the provisioned path: "the account,
the doorbell, the log, the manifest topic, and — under the native profile — the
**declaration registry and profile file**." D-146 then amended §4.6's `Conformance:` note
so that it read:

> `Conformance:` T-P13-1; T-P17-1 — every topic the suite provisions has its admin key set
> to the agent's key and its remaining keys set at creation per the declared policy for
> that topic type, and the policy is recorded at creation.

HCS-1, at the pin (`docs/standards/hcs-1.md`, blob `0d8cca5f0adac613a149244e769672ea3060328a`,
commit `7046156c`), says the reverse of a file topic. FETCHED 2026-09-06, recorded at ledger
§H:360 and quoted in `recon/pins-recon-2026-09-06.md`:

> "- include a Submit Key. HCS-1 Topics without a Submit Key will automatically be marked as
> invalid files, and will be ignored.
> - NOT include an Admin Key. HCS-1 Topics with an Admin Key will automatically be marked as
> invalid files, and will be ignored. This ensures that data cannot be deleted, reducing risk
> for all participants in the protocol."
> — `hcs-1.md:48-49`

The fact was already in the ledger. What nobody had noticed is that it collides with D-146's
note. As landed, an HCS-11 profile file could not be provisioned conformantly by either
reading: give it the admin key T-P17-1 demands and HCS-1 ignores the file; withhold the admin
key and T-P17-1 fails. §9.2:1284 puts a MUST on the agent — "MUST set its account memo to
`hcs-11:hcs://2/<registryTopic>` … register each profile version there" — and §9.2's rule
reads that registry's current entry, which "points at an HCS-1 file." So the whole `hcs14`
declare surface, the native profile, was unreachable.

D-147's provisioning template does not list the profile file at all; it has five rows —
doorbell, log, manifest, declaration registry, lane — and §4.6 names a sixth artifact.

Found by Claude Code, 2026-09-08, while planning the declaration. MINE at the finding;
Sonic ruled the same day.

## Decision

§4.6's `Conformance:` note is amended to except the case where the standard a topic serves
forbids an admin key. It now reads:

> `Conformance:` T-P13-1; T-P17-1 — every topic the suite provisions has its admin key set
> to the agent's key, **except where the standard the topic serves forbids an admin key, in
> which case it carries none and the key that standard requires is the agent's**; its
> remaining keys are set at creation per the declared policy for that topic type; and the
> policy is recorded at creation.

The exception is **objective**: it turns on the pinned standard's text and not on anything a
declared policy says. That is what keeps D-146's own reason intact — D-146 rejected adopting
§A's row verbatim precisely because it would leave "a declared policy free to name a non-agent
admin key and still pass" — and an implementation cannot reach this exception by declaring a
policy, only by serving a standard whose pinned text forbids the key. Ownership, which is what
§4.6:583's MUST is actually about, survives in the one key HCS-1 does require: the submit key,
which is the agent's.

§A's T-P17-1 row is amended to the same words, as D-146 amended it, so the spec/register
divergence that produced D-146's defect does not survive this fix either.

D-147's template gains a **sixth** row: the HCS-1 profile file topic — sole submit key the
agent's, **no admin key**, no fee, no exempt list. D-147's five rows are unchanged.

## Alternatives considered

- **Read T-P17-1 as governing only topics whose type admits an admin key, and record the
  reading without amending the text.** MINE, and the lean carried into the plan. It lost
  because the reading is not in the sentence: a reviewer with the specification in front of
  them would read the note as written and find the deployment in breach of it. A requirement
  that needs an unwritten gloss to be satisfiable is a defect in the requirement.
- **Store the HCS-11 profile somewhere other than an HCS-1 file.** Not available: §9.2's rule
  dereferences the registry entry to an HCS-1 file, and P-9 is strict conformance to the
  pinned blobs.
- **Declare under the direct-HCS-1 memo form instead**, avoiding the registry. Not available
  either: §9.2:1284 requires the HCS-2 form for declaring, and T-P8-3 explicitly fails a
  fixture that declares with a direct-HCS-1 memo, because its prior declarations would not be
  resolvable (D-70).
- **Hold the profile file and provision only the registry topic and account memo.** Lost
  because a registry whose entry points at nothing does not resolve, so nothing downstream of
  the declaration could be exercised.

## Consequences

**This is a specification change, and therefore version 0.5.3** — a patch under §1.7. No wire
string moves (`v` stays `0.5`, the HPKE `info` stays `wishmail/0.5/seal`, `schemaRef` stays at
the minor version), no schema changes, and nothing conforms: T-P9-2 blocks every claim while
thirty pins in `spec/pins.json` are null. That is D-134's and D-146's reasoning, unchanged. No
test is added, moved or removed; the register stays 83 (78 core + 5 extension) and the
extract-and-diff passes both ways.

`spec/adr/D-146.md` and `spec/adr/D-147.md` gain reciprocal pointers and keep their text.

What an implementer must now do differently: an HCS-1 file topic provisioned for an agent is
created with the agent's key as its **sole submit key and no admin key at all**, and its
declared policy records that the absence is HCS-1's requirement and not a choice. Because
HCS-1 forbids the admin key in order that "data cannot be deleted," such a topic is
permanent — a profile file cannot be withdrawn, only superseded by a new registry entry
(§9.2:1284, "prior entries stay on the registry topic").

Nothing here reaches the price topic, which is Postmaster infrastructure outside §4.6 and
T-P17-1 by D-146's scope sentence, nor the doorbell, whose absent submit key is D-138's
separate matter.
