## Context

Found during the outfitting read-through of 2026-09-07. The specification and the ledger described T-P15-3 as two different tests.

§1.5 names it for a requirement: "A claim MUST NOT name a class whose suite did not pass in full. `Conformance:` T-P15-3."

Ledger §A sketched it as something else: "The declaration's `report` field resolves to a report artifact produced by the suite whose digest matches."

Three problems in the one sentence. It used **declaration**, which D-74 and §2.3 reserve for what an agent publishes under a profile so that it can be resolved (§9.1) — the object §1.5 is about is a **claim** (§2.2, §5.10 `ConformanceClaim`). It named a **`report` field** that no object has: §5.10 gives the claim `suite {version, date, reportDigest}`. And it recorded a digest check while the requirement it answers to is that a claim names no class whose suite did not pass. `LIMITATIONS.md`'s "Classes claimed" row already cited T-P15-3 the way §1.5 does, so the ledger sketch was the outlier. Raised as a decision candidate, MINE, 2026-09-07.

## Decision

The sketch follows the D-74 reserve and records the substance. RECORD (Sonic, 2026-09-07).

Ledger §A's T-P15-3 row now reads:

> A **claim** names no class whose suite did not pass in full: for every class the claim names, the report reached through `suite.reportDigest` is one the suite produced, its digest matches, and it records that class's suite as passed in full. A claim naming a class whose report records a failure, or naming a report the suite did not produce, is rejected.

*Declaration* is gone, *claim* is the object, `suite.reportDigest` is the field §5.10 actually gives it, and the digest check is kept as the mechanism by which the requirement is answered rather than as the requirement itself.

## Alternatives considered

- **Rename *declaration* to *claim* and stop.** Rejected: it would leave the sketch describing a digest check while §1.5 requires something the digest alone cannot show — a matching digest proves the report is the suite's, not that the class passed.
- **Replace the sketch with §1.5's sentence alone, dropping the report artifact.** Rejected: the report and its digest are how a claim is checked at all, and no other test covers them. T-P15-1 checks that the claim validates against its schema and that every test it names exists; nothing else reaches the report.
- **Amend §1.5 to match the ledger.** Rejected: the specification's sentence is the correct one, and the ledger is not normative.

## Consequences

The ledger's §A row changes and the specification does not. §1.5's requirement, its `Conformance:` note, and §5.10's `ConformanceClaim` shape all stand as written; `spec/schemas/conformance-claim.schema.json` already carries §1.5's rule as the description of `classes` and needs no change.

**This is not a version change.** §1.7 makes a new minor version of "a change to a conformance test that would invalidate a previously conforming implementation". Nothing conforms: §1.6's stamp-token pin is unfilled and T-P9-2 blocks every claim (`spec/pins.json` carries 32 nulls). And the amended sketch does not move the test — it brings the sketch onto the requirement the test always answered to, which is §1.5's and was never the ledger's to set. The register stays at 83 (78 core + 5 extension); no test is added, moved, or removed, and the extract-and-diff is unchanged in both directions.

§18.2's ADR index is not extended to D-132 – D-134, for the reason given in D-133.
