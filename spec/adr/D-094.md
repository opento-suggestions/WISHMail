## Context

A memo rule that applied to every operation would have put a memo where HCS-10 defines none, which is a divergence dressed as strictness.

## Decision

The record, from ledger §B row D-94, verbatim:

> **Memo rule bounded to what HCS-10 defines**: `connection_request`, `connection_created`, `message`, `close_connection` carry `hcs-10:op:<op>:<topic type>`; the `transaction` op has no enum slot and no memo at the pin (recon C-5, O-4), so it carries none. §6.1 and T-P9-5 amended (`CHANGED`). Note C-4: HCS-10's two inverse "topic type" enums — WISHMail uses the *transaction-memo* enum (0=registry, 1=inbound, 2=outbound, 3=connection), the one HCS-10's own worked example uses.

## Alternatives considered

- None recorded. The ledger §B row states the decision without a fork; where a fork was closed, the row says so.

## Consequences

FETCHED at the pin: `connection_request`, `connection_created`, `message` and `close_connection` carry `hcs-10:op:<op>:<topic type>`; the `transaction` operation has no enum slot and no memo, so it carries none. The rule is bounded to what HCS-10 defines, in both directions — carry it where defined, carry none where not (§6.1, T-P9-5). HCS-10 has two inverse topic-type enums; WISHMail uses the transaction-memo one.
