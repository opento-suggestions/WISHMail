## Context

Closing ledger §G item 16, raised by Claude Code on 2026-09-09 and found by
`npm run check:freeze` — a check written to build one instance of each of the
three schemas Step 4 would otherwise register unexercised. It found instead that
**nothing in this repository had ever validated a manifest against
`spec/schemas/proof.schema.json`**, and that when one finally was, `meaning.uri`
was the field that would not hold.

The contradiction, as §G-16 stated it and as the ruling accepts it:

- §2.2 defined a canonical location as "the structured locator, recorded in a
  proof's meaning, at which **the proof's manifest** is found on consensus data",
  and §5.2 gave `{ledgerTag, topicId, sequenceNumber}` as what "names one
  message". So `meaning.uri` was a message locator, and the message it named was
  the proof's own manifest.
- §5.1 hashes `meaning` into the proof. §6.2 computes that hash at `resolve`
  time. §6.4 step 2 publishes the manifest **afterwards**, and the AAD has
  already bound the hash.

A manifest therefore cannot carry its own publication locator. There is no order
of operations that fixes it: publish, re-hash with the locator, republish —
and the second publication has a different sequence number than the first, so the
proof is wrong again, and the AAD bound the first hash anyway.

The schema caught two of the three writers only by accident, which is the part
worth recording. The slip passed because it named its own log entry — a real
message, and not the manifest. The receipt passed because it named a sequence
number **nobody can know**: §10.4 has the sender pre-fill the manifest inside a
`ScheduleCreate` whose inner submission executes only when the recipient signs,
so the number was invented. The resolver failed outright, because it named the
HCS-1 profile file, and an HCS-1 file is a topic with no sequence number at all.
One defect showing three ways.

## Decision

**Reading (B), corrected.** `meaning.uri` names neither the message nor the
evidence: it names **the topic the manifest is published on**, and the manifest
is found there by hash. §5.2 now separates two shapes it had been calling one
thing:

```
location   {ledgerTag, topicId}                   a proof's meaning.uri
locator    {ledgerTag, topicId, sequenceNumber}   one message
           {ledgerTag, txRef}                      one transaction
```

A **location** says where a manifest is published and not which message it is;
the manifest at a location is the message on that topic whose body recomputes to
the proof's hash. A **locator** names one thing on consensus, and is what a
*reference* carries — `rp.u` in the AAD (§7.2), `resolutionProof.uri` in
coordinates (§5.3), the executed submission for a receipt (§10.4) — and what
`inputs.locator` carries.

**Every writer knows its location before it writes**, which is what makes the
ruling implementable at all: the sender's manifest topic for the resolution proof
and for the slip; the recipient's manifest topic for the receipt, which the
sender already targets in the `ScheduleCreate` because that is the topic the
inner submission writes to. An agent knows its own manifest topic before it
resolves anything, and knows the sequence number of nothing it has not yet
submitted.

§9.1's existing sentence — "a Verifier need not attribute a manifest: its hash is
bound into the AAD, and a manifest that recomputes to that hash is the one the
envelope meant, whoever published it" — needed no change. It stops being a remark
about attribution and becomes the lookup rule.

New MUST, §11.1:

> A Verifier MUST appraise no higher than unverified a proof whose manifest it
> does not find at the proof's canonical location: where no message on the topic
> that location names recomputes to the proof's hash, the proof's manifest is not
> on consensus where the proof says it is, and the reason is reported. A
> reference reaching a manifest on some other topic does not answer the lookup;
> it is the location the proof itself carries that must hold it.
>
> `Conformance:` T-P6-7

**T-P6-7, and why P-6 rather than P-1** (MINE, stated so it is reversible).
P-6's own text is that "the proof's manifest is on consensus before the
envelope" — a failed lookup denies exactly that. P-1 is binding, and binding
failures yield *unbound*: every P-1 row in §11.5's table does. A manifest that
cannot be found leaves the envelope bound and stamped and its address
unappraised, which is *unverified*. The reason sits below the reference check and
above the replay check in §11.5's order, because a manifest nobody can find is a
weaker failure than one that will not replay.

## Alternatives considered

- **Reading (A): §2.2 is right and the writers are wrong.** Rejected: it requires
  publishing a manifest, re-hashing it with its own locator, and republishing —
  which §6.4's step order and the AAD's binding forbid, and which does not
  terminate.
- **Reading (B) as first stated: `meaning.uri` is the location of the evidence
  the proof is about.** This is what the code had taken. Rejected in favour of the
  correction: the evidence is already in `inputs.locator`, so this made
  `meaning.uri` a duplicate of a field the proof already carries, and left the
  proof with no statement at all about where its own manifest could be found —
  which is the one thing §11.1's lookup exists to check.
- **Drop `uri` from `meaning` entirely and let the reference carry everything.**
  Rejected (MINE): a reference is written by whoever names the proof, and a proof
  that says nothing about where it lives can be pointed at a copy on any topic by
  anyone. Keeping the location inside the hash is what makes the lookup a check
  rather than a dereference.
- **Make `sequenceNumber` optional in the schema.** Rejected: it makes the
  distinction invisible to a reader and lets a writer put in a number that means
  nothing, which is what the receipt was already doing.

## Consequences

- `spec/schemas/proof.schema.json`: `meaning.uri` becomes `{ledgerTag, topicId}`,
  both required, closed. **A schema change, and admissible as a patch only while
  `registeredSchemas` is null** (§1.7; D-161's reasoning). This is why it lands
  before Step 4's signature and not after: after registration, the identical
  change is 0.6.
- Wire strings are unchanged. `meaning.uri` is not a wire string: it is a field of
  a manifest, and manifests carry no protocol identifier of their own beyond
  `{p: "wishmail", t: "manifest"}` (§9.1), which does not move.
- `app/src/core/proof.ts` gains the `ProofLocation` shape and every writer sets
  `meaning.uri` to a manifest topic: the resolver to the resolving agent's own,
  the slip to the sender's, the receipt to the recipient's.
- `verify` gains the lookup: the topic `meaning.uri` names is read for a message
  whose body recomputes to the proof's hash, and its absence is `T-P6-7`.
- `ack` becomes buildable. It could not be built while this was open, because the
  receipt manifest it signs is pre-filled inside the schedule and had no honest
  value for `meaning.uri`.
- **What the code had taken before this ruling:** reading (b) as originally
  stated — the resolver naming the HCS-1 profile file topic, the slip naming its
  own log entry, the receipt naming a fabricated sequence number 7. All three now
  name a manifest topic.
