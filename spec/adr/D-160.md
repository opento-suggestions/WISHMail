# D-160 — A Verifier reads orphans from the treasury, and reports only the senders in its scope

Status:      accepted
Date:        2026-09-09
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    §11.2
Tests:       T-P3-6 added
Supersedes:  none
Spec marker: CHANGED: D-160 on §11.2

## Context

Three sentences of the frozen text required something a fourth made
unreachable, and the contradiction was raised as ledger §G item 15 on
2026-09-09 while `verify` was being built.

§5.10 gives every `EvidenceBundle` an `orphans` array of `Settlement`. F-3
defines an orphan as postage affixed where no chunk of the envelope it names
ever lands. §13.3's row for F-3 reads "settlement, no chunk … reported as
orphans". §11.4 repeats it: "A settlement that counts for no envelope in scope
is an orphan and is reported under `orphans` (F-3)."

But §11.2's ingestion table reached a settlement by exactly one route —
`hdr.st`, a field of chunk 0 — and the table was closed by its own next
sentence: "Nothing on that list is chosen by the Verifier or supplied to it.
Each is named by something already read, beginning from the lane."

An F-3 orphan has no chunk. Therefore no `hdr.st`. Therefore no route. The one
thing §5.10 requires under `orphans` was the one thing the ingestion rule could
not see, and `verify` was built to the narrow reading with the reasoning in the
module head rather than coding around it.

## Decision

**§11.2's table gains a row, and the row is filtered.**

```
the treasury's inbound transfers      the stamp token's treasury            settlements that count for no
in the stamp token, over the window   (§1.6 pin; §14.3 PriceList)           envelope: reported under orphans
```

It is the **one row not named by something already read**, and it has to be:
an envelope that was never posted names nothing at all. Its treasury is the one
§1.6 pins and the price list carries (§14.3). A settlement is not on a topic, so
it has no sequence to be ordered by; it is in the window by **its own consensus
timestamp**, and the row's prose says so.

**Filtered.** A settlement read by that row is reported only where its `from` is
a sender in scope — an account that is party to a lane in scope, or that appears
as `settlement.from` among the envelopes reconciled. A stranger's orphan is not
this correspondence's business, and the sender's own retry already sees it.

The filter is also what keeps P-3 honest. An unfiltered read of a treasury makes
a bundle a function of the whole ledger's traffic in the window rather than of
the scope, so two Verifiers running at different times against a busy treasury
would produce different bundles for the same scope — which is exactly the
determinism P-3 requires and §11.7's digest depends on.

**The new MUST:**

> A Verifier MUST report under `orphans` every settlement in the window, from a
> sender in scope, that no canonical chunk in scope names.
> `Conformance:` T-P3-6 — a fixture in which a sender in scope affixes postage
> under a `wishmail:` memo and posts no chunk against it carries that settlement
> under `orphans`, with every reconciled envelope's state and standing
> unchanged; a settlement in the same window from an account not in scope is not
> reported.

## Alternatives considered

- **(b) Read F-3's "reported under `orphans`" narrowly**: only a settlement some
  `hdr.st` led the Verifier to that no envelope in scope validly claims — the
  T-P7-2 double-claim and the partial envelope — leaving F-3's pure form
  invisible to a lane scope, and stating that in LIMITATIONS. This is what the
  code took while the item was open. Lost because it makes §5.10's `orphans`
  and §13.3's row false about the case they were written for, and because
  LIMITATIONS is for what a deployment does not do, not for what a
  specification cannot say.
- **The unfiltered row.** Lost on P-3, above.
- **Filter by the window alone and let the scope carry an explicit account
  list.** Rejected as the same thing with a supplied input: §11.2's discipline
  is that nothing on the list is supplied to the Verifier, and "a sender in
  scope" is derived from what was already read.

## Consequences

§11.2 carries `CHANGED: D-160`, gains the row, the two prose paragraphs, and the
MUST. §A gains **T-P3-6**; with D-157's T-P2-4 the register moves from 83 to 85
(80 core + 5 extension) and the extract-and-diff passes both ways.

**No schema change.** `orphans` is already `[Settlement]` in §5.10 and in
`spec/schemas/evidence-bundle.schema.json`.

`app/src/tools/verify.ts` changes from the narrow reading to this one, and its
scope already carries the stamp token — put there when `verify` was built, for
exactly the P-3 reason this decision names.

T-P3-2's exception corpus lists "an orphan"; that fixture's construction now
follows from this decision, and T-P3-6 is the test that isolates it.

**A patch under §1.7**: no wire string, no registered schema, and nothing
conforms while T-P9-2 blocks every claim.
