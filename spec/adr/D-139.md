# D-139 — On a doorbell, "the key that governs that topic" is the submitting agent's

Decided by:  Sonic
Drafted by:  Claude Code
Sections:    §3.5, §4.4 (no sentence changes; a reading is recorded)
Tests:       none — T-P2-1's scope is unchanged
Supersedes:  none

## Context

§3.5 states the Postmaster's whole posture in one sentence, at `spec/WISHMAIL_SPEC_v0_5.md:469`:

> The Postmaster pays; the agent signs. A submission to a lane, doorbell, or log MUST be signed by the key that governs that topic, which is the agent's. The Postmaster MAY be the transaction payer and MUST NOT be a signer of that key.

It names three topic types. Two of them have a governing key: a lane's submit key is a threshold of exactly the two agents' keys (§7.1, P-17), and a log's submit key is its agent's (`index.md:114`). **A doorbell has none.** D-138 fixed that it carries no submit key at all, because §4.4's MUST selects HCS-10's fee-gated inbound option (`index.md:113`) and a submit key on top of it would make the doorbell unreachable by exactly the strangers first contact exists for.

So on a doorbell there is no key that governs the topic, and the clause "which is the agent's" has no referent. Read strictly, §3.5 imposes a MUST that names nothing — and read carelessly, it says the *owner's* key must sign a stranger's `connection_request`, which would abolish first contact.

## Decision

**On a doorbell, "the key that governs that topic" is the key of the agent making the submission — the sender signs its own ring — and the fee does the governing that a key does elsewhere.**

This is the only reading under which all of §3.5, §4.4 and D-138 are simultaneously true. The sentence's force is unchanged where it has a referent: on a lane and on a log, the topic's own key must sign, and the Postmaster must not be a signer of it. On a doorbell the sentence's *purpose* — that the Postmaster never signs in an agent's place — survives intact, because the stranger signs its own request and the Postmaster is payer only (§4.4's second paragraph, D-47). What does not survive is the reading that some topic-resident key authorizes the submission, because on a doorbell no such key exists.

The gate on a doorbell is economic, not cryptographic. §4.4 says so in its own terms: the doorbell "is not a public forum" because "it charges one stamp to ring," not because a key admits or refuses. P-7 is satisfied by the fee.

**No specification sentence changes.** §3.5 is not wrong about lanes or logs, and rewriting it to enumerate the doorbell case would put a mechanism in a section that is about posture. The reading is recorded here so that the ambiguity is explainable with the agent closed (CLAUDE.md §7), and so that a reviewer who notices the vacuity finds it already noticed.

## Alternatives considered

- **Amend §3.5 to except the doorbell.** MINE, rejected: it adds a sentence to fix an ambiguity no test turns on, and §1.7 makes even a patch a cost. The reading costs nothing and is checkable here.
- **Read "the agent's" as the doorbell owner's key.** Rejected: it abolishes first contact, contradicts §4.4, and no HCS-10 inbound topic in the pinned standard works that way.
- **Give the doorbell a submit key so the sentence has a referent.** Rejected in D-138 for the same reason, from the other direction.
- **Treat the sentence as covering only lanes and logs, and say nothing about doorbells.** MINE, rejected as insufficient: silence is what produced the ambiguity. Naming the submitting agent as the signer is a positive statement a test could be written against if one is ever wanted.

## Consequences

**Nothing breaks and no test moves.** T-P2-1, the test §3.5 names, reads "every lane message the suite produces is signed by the sending agent's submit key; a submission bearing only Postmaster keys is rejected at the network" — lanes only. It never reached the doorbell, which is why the vacuity survived the freeze unnoticed.

For the provisioning script this settles who signs a first-contact `connection_request`: the sender's key, with the Postmaster as payer, which is also what makes D-137's exemption work. HIP-991 waives a fee **by signature** (`hip-991.md:110-113`, pinned by D-135), so when the owner answers on its own doorbell it is the owner's signature on the submission — present because §3.5 puts it there — that meets the exempt-key list and assesses zero. The two decisions interlock: D-137 is only implementable because the signer is the submitting agent.

**A sibling defect is raised separately and not ruled here.** §4.6's `Conformance:` note at `:584` still reads "every topic the suite provisions has its **admin and submit** keys set to the agent's keys per the declared policy" — the same over-read D-138 removed from the ledger's T-P17-1 row but, as landed, not from the specification. That is a text defect requiring a ruling, not a reading, and it is reported as a decision candidate rather than folded in here.
