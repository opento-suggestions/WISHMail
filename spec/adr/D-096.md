## Context

HCS-10's only size rule is 'exceeding 1KB → use HCS-1', stated nowhere in bytes and never in RFC 2119, so 1024 was an inference and not a reading.

## Decision

The record, from ledger §B row D-96, verbatim:

> **`CHUNK_WIRE_MAX` = 1000 bytes** (was 1024, D-62). HCS-10's only size rule is "exceeding 1KB → use HCS-1" — never in bytes, never RFC 2119 — and Sonic reads the maintainer's word as chosen: WISHMail abides in the 1k and does not delegate to HCS-1. Budgets re-measured: chunk 0 ≈ 172, middle ≈ 510, last ≈ 567 B of ciphertext (`data` as a JSON string). §7.4, T-P9-7 amended (`CHANGED`); T-P9-8 now bounds manifests by `CHUNK_WIRE_MAX` symbolically. Sonic's call over Claude's lean, 09-06.

## Alternatives considered

- None recorded. The ledger §B row states the decision without a fork; where a fork was closed, the row says so.

## Consequences

`CHUNK_WIRE_MAX` = 1000 bytes on the whole `message` operation as UTF-8 JSON, one HCS message per chunk, no `chunkInfo` (§7.4, T-P9-7). Sonic reads the maintainer's '1KB' as chosen rather than approximate: WISHMail abides inside the 1k and does not delegate to HCS-1. Recorded as L-7 — the limit is stated in a unit the standard never fixed, and this release picks the conservative reading.
