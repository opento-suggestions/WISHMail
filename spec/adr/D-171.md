## Context

§7.1 said two things that cannot both be obeyed.

> "A lane is bidirectional: either party sends on it." — §7.1 ¶6

> "The lane an envelope binds to MUST have been created in answer to a
> connection request on the doorbell **its resolution proof yielded**." — §7.1's
> MUST, `Conformance:` T-P10-2

An HCS-10 lane's `connection_created` sits on the **acceptor's** doorbell. So for
a first letter the two sentences agree, and for a reply they do not: the reply's
recipient is the original requester, whose doorbell never held anything, while
the lane the two agents share — and which either may write to under its threshold
key — is invisible to the discovery rule and forbidden by the MUST.

This was found by the dry run of Gate Two checkpoint two's reply, **before any
signature**, and confirmed from the mirror rather than inferred: lane
`0.0.10464056` was created by B in answer to A2's ring, so its
`connection_created` is on B's doorbell `0.0.10452149` at sequence 2, and **A2's
doorbell `0.0.10462704` holds zero messages**. The reply was held at the gate and
raised as ledger §G-21. Nothing was signed and nothing was rung.

## Decision

**RECORD (Sonic, 2026-09-10).** An envelope is bound to a lane **iff** the lane's
submit key is a threshold over exactly the two parties' keys **and** the lane's
`connection_created` is on the doorbell of one of the two parties and names the
other. First contact is found on the recipient's doorbell via the AAD's
resolution proof, as before; a reply is found on the sender's own doorbell,
naming the recipient, because the sender is the agent that answered. The reply
rides the lane already open and rings nothing.

The submit-key clause is not decoration. It is what makes reading *either*
doorbell safe: without it, a third party could post a `connection_created` on its
own doorbell naming a victim and offer the lane for binding. With it, the lane
provably belongs to exactly those two agents, because a Hedera topic key names
the keys it was created with and follows no account whose key later changes.

**A Verifier resolves nobody.** RECORD, Sonic, on a route raised the same day:
the lane's memo is HCS-10's connection-topic memo
`hcs-10:1:{ttl}:2:{inboundTopicId}:{connectionId}` (FETCHED at the pin,
`docs/standards/hcs-10/index.md:279`), which names the doorbell the lane was born
on; that doorbell's own memo `hcs-10:0:{ttl}:0:{accountId}` (`index.md:246`)
names its owner; the `connection_created` on it naming this lane, submitted under
that owner's `operator_id`, names the other party; and the pair must equal the
envelope's two parties — the recipient from the resolution's coordinates, the
sender from the settlement's `from` (§7.2's fourth weld). Four reads of public
consensus data, and **the same walk in both directions**, because a lane has one
birth however many letters cross it.

Checked against the live lane before it was written down, and it holds both ways:
`D` = `0.0.10452149`, its owner `O` = `0.0.10452127` (B), the requester it names
`R` = `0.0.10462700` (A2). For the original letter
`{coordinates.account, settlement.from}` is `{B, A2}`; for the reply it is
`{A2, B}`. The same set.

## Why this is a patch, 0.5.11, and not 0.6

**First and structurally.** §1.7's bar is "a change to a conformance test that
would invalidate a previously conforming implementation". The text this amends
was **self-contradictory**, so it fixed **no determinate conforming behaviour**:
there is no behaviour an implementation could have had that this takes away.
Making a contradiction determinate invalidates nothing that could have been
relied on.

**Second, as fact.** `RELEASE.classes` is empty, no test body is expanded, and no
release claims any class — so there is no previously conforming implementation at
all.

**Third, as precedent.** D-157 added a MUST inside a patch and D-169 fixed a
comparison rule inside one, both after the freeze, both touching neither a wire
string nor a registered schema. Neither does this: no schema moves, no wire
string moves, and no row is added to §A.

## Alternatives considered

- **(b) The MUST is directional and bidirectionality is narrower than it reads** —
  a reply is first contact from the other side: B rings A2's door, spends a stamp
  at A2's HIP-991 fee, and a second lane opens between the same two agents.
  **Rejected (RECORD).** A lane cannot be closed retroactively, so "a second
  letter to the same recipient rings nothing" would be false forever; an ordinary
  two-way correspondence would cost two lanes, two doorbell fees and two
  `connection_created` records; and §7.1's own "earliest-created" rule would then
  pick a different lane for each direction.
- **Resolve the sender to obtain its doorbell** — the mechanism §G-21 assumed.
  **Rejected (RECORD)** in favour of the memo walk: it costs a second resolution,
  and it would make the reply's binding check depend on a claimed profile more
  deeply than it must.
- **Do the memo walk outside the claimed-profile branch, so a claimless Verifier
  can run it.** MINE, not taken: the recipient's account comes from the
  resolution replay, so the check cannot run without it — and moving what *can*
  run would change bundles whose digests are printed in runs of record.

## Consequences

- §7.1's discovery rule and its MUST, §11.4's binding paragraph, §11.5's reason
  table (which gains a `T-P17-2 → unbound` row), §11.2's ingestion table (whose
  doorbell row is now found from the lane's memo), §6.4's `SEND_LANE_INVALID`
  gloss, §12.2's P-10 and §13.2's F-11 are amended.
- `send` finds a lane from both doorbells; it needs no new resolution, because an
  agent knows its own doorbell.
- **The check is dark under a release that claims no profile**, exactly as
  T-P1-10 is, because the recipient's account is what the replay yields. Recorded
  in LIMITATIONS L-1 and not widened to hide it.
- **Enumeration, and what a wiped home forgets.** An agent lists the lanes it
  *accepted* from its own doorbell, and the lanes it *requested* by resolving the
  correspondents its home records and reading their doorbells. The home is the
  address book; consensus remains the only authority on the lane (D-165). A wiped
  home forgets who it wrote to, not what it wrote: the lanes survive on
  consensus, the enumeration does not. Nothing in `verify` depends on it either
  way, because a Verifier reads by lane.
- Leaves open **§G-24**: whether this implementation writes HCS-10's *Outbound
  Connection Created* record, whose own text disagrees about which party writes
  it. Under the requester reading, that record would make the address book
  unnecessary.
