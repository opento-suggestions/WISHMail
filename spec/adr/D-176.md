# D-176 — §11.4's unrequested receipt gets its own court, T-P1-12

Status:      accepted
Date:        2026-09-10
Decided by:  Sonic
Drafted by:  Claude Code
Sections:    §11.4
Tests:       **T-P1-12 added** under P-1. The register goes 86 → 87 (82 core + 5 extension).
Supersedes:  none
Spec marker: CHANGED: D-176 on §11.4

## Context

§11.4 states a requirement and named no test for it:

> "A receipt for an envelope whose header did not request one counts, and the
> reason names it (§8.6)."

§1.3 is unconditional — there is no requirement without a test — and no row of
§A was about §8.6's unrequested receipt. T-P1-7 is receipts witnessed before the
nth chunk or on an envelope standing unstamped or unbound; T-P1-8 is the
mechanism; T-P1-9 is `ack`'s refusal. None of them is this.

**What the code did meanwhile, and it was the right thing to do.** `verify`
reported `T-P12-2`, which is §11.5's own sanctioned answer for a condition its
table does not name — "a Verifier that finds a condition this table does not
name has found a defect in this specification, and reports … with the reason
`T-P12-2`". So the gap appeared in the Verifier's own output instead of being
papered over with a test identifier that means something else. Raised as ledger
§G-23.

## Decision

**RECORD (Sonic, 2026-09-10), folded into the 0.5.12 patch:** the test row is
added, because a MUST does not stay without a court. §11.4's sentence gets its
own row in §A rather than borrowing `T-P12-2`.

**T-P1-12**, registered under **P-1** — beside T-P1-7, T-P1-8 and T-P1-9, the
receipt tests that already live there, P-1 being the invariant that "a return
receipt binds to one envelope and one postmark and cannot be re-worn":

> **T-P1-12** | P-1 | VERIFIER | A fixture receipt for an envelope whose
> `hdr.rr` is false is reported with `receipt.status` = `acked` and a reason
> naming it unrequested; the envelope's state and standing are unchanged from
> the same correspondence without it, and the reason is not borrowed from a test
> about something else.

§11.4's sentence cites it — "`(§8.6, T-P1-12)`" — and `verify.ts` reports it in
place of `T-P12-2`.

**§11.5 offering `T-P12-2` was never wrong**, and the distinction is the whole
of the finding: §11.5 sanctions it for *a condition this table does not name*,
which is a different thing from a condition this specification **does** name and
forgot to register. The first is a Verifier reporting a gap honestly. The second
is a gap.

## Why no row is added to §11.5's table, and that is not an omission

An unrequested receipt yields **no standing**. §11.5 is explicit: "the receipt
does not lower it — an invalid receipt is a fact about the receipt — and nothing
raises it." §11.5's table is the table of checks that *yield a standing*, and
this check yields none. Its reason therefore belongs to `receipt.reasons`, where
`verify` puts it, and not to the envelope's `appraised.reasons`. The code carries
the same separation already: `REASON_ORDER` and `REASON_STANDING` are §11.5's
table, and `RECEIPT_REASON_ORDER` is the receipt's own ordering — T-P1-12 joins
the second and not the first.

## Why this is a patch, 0.5.12, and not 0.6

§1.7's bar is "a change to a conformance test that would invalidate a previously
conforming implementation". **A row is added and none is changed**: no existing
test's condition, sketch or identifier moves, so nothing an implementation
already passed stops passing. And as fact, there is no previously conforming
implementation at all — `RELEASE.classes` is empty and no test body is expanded.
No schema moves and no wire string moves. D-157 is the precedent for adding a
requirement inside a patch after the freeze.

## Alternatives considered

- **Loosen §11.4 instead**: make "the reason names it" read "and is reported as
  unrequested", removing the requirement for a reason. Recorded in §G-23 and not
  taken: it costs a field nobody has, and it would make the bundle silent about
  something a reader of a receipt wants to know.
- **Keep borrowing `T-P12-2`.** Not taken: it is the correct report for an
  *unnamed* condition, and after this decision the condition is named. Leaving it
  would make the Verifier report a specification defect that no longer exists.

## Consequences

- §A gains one row; the register is **87** (82 core + 5 extension).
  `conformance/register.mjs`'s `EXPECTED_TOTAL` follows it, `conformance/tests/`
  gains one stub, and the stub **fails**, like the other eighty-six — a stub that
  passed would be a test that is not yet written telling the suite that it is.
  The harness line becomes `register 87 · files 87 present · passed 0 · failed 87`,
  which is still correct output and not a defect (§1.5: `RELEASE.classes` is
  empty, so this release claims nothing).
- `verify.ts` reports `T-P1-12` for the unrequested receipt and `T-P1-12` joins
  `RECEIPT_REASON_ORDER`. **That ordering is a filter, not a sort**, so a reason
  absent from it would be silently dropped — which is why the constant is
  amended in the same change as the value.
- Closes ledger **§G-23**, its finding kept unedited beneath the ruling.
